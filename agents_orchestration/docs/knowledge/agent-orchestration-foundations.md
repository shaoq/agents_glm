## 0. 核心认知

Agent Orchestration 的本质，是：

> **在目标、约束和运行状态持续变化的情况下，对 Agentic System 的执行过程进行受约束的动态控制。**

编排需要持续回答六个问题：

1. **Who**：下一步由哪个 Agent、工具、工作流或人执行？
2. **What**：执行哪个任务或子任务？
3. **When**：串行、并行、延迟、重试还是暂停？
4. **With what context**：向执行者提供哪些状态、证据、历史和权限？
5. **How to reconcile**：多个结果如何验证、合并和解决冲突？
6. **When to stop**：如何判定完成、失败、预算耗尽或需要人工介入？

三个必须先建立的判断：

1. **Agent Orchestration 不等于 Multi-Agent**：Multi-Agent 只是编排的一种形态。
2. **编排不只是调用顺序**：它还控制状态、上下文、权限、预算、失败恢复和终止。
3. **生产级编排的核心张力是自主性与可控性**：不是让 LLM 决定得越多越好，也不是把所有路径都写死。

## 1. Agent 编排的定义

### 1.1 一个工作定义

本文将 Agent Orchestration 定义为：

> 为实现给定目标，在约束条件下协调 Agent、模型、工具、确定性程序和人类参与者，管理任务分解、执行选择、状态演化、上下文传递、结果汇聚、异常恢复与终止的控制过程。

这个定义包含四层含义：

- **目标导向**：编排不是让参与者自由交互，而是推动任务向可验证结果收敛。
- **多类执行者**：参与者不只有 Agent，也包括工具、普通函数、工作流和人。
- **动态状态**：下一步不仅由原始输入决定，也由工具结果、环境反馈、失败和人工判断决定。
- **控制约束**：执行始终受到权限、预算、并发、安全和终止条件约束。

### 1.2 编排是状态转换过程

可以把一次编排决策抽象为：

```text
当前状态 + 新观察 + 编排策略
              │
              ▼
    ┌──────────────────┐
    │   Orchestrator   │
    └──────────────────┘
       │       │      │
       ▼       ▼      ▼
   下一动作  状态更新  控制事件
                    （完成/重试/暂停/升级）
```

更形式化地表达：

```text
(next_state, commands, control_events)
    = orchestrate(current_state, observations, policies)
```

这里：

- `current_state` 表示任务、执行、上下文、预算和权限等当前状态；
- `observations` 表示模型输出、工具结果、环境变化、错误和人工反馈；
- `policies` 表示路由、权限、预算、重试、提交和终止规则；
- `commands` 表示接下来要执行的 Agent、工具或工作流动作；
- `control_events` 表示完成、失败、暂停、回退、升级或请求人工介入。

这个抽象的价值在于：它把“模型生成了什么”与“系统是否允许发生状态变化”区分开。

### 1.3 编排不是让多个 Agent 聊起来

多个 Agent 互相发送自然语言消息，只能说明系统存在多参与者通信，不能证明系统具有可靠编排。

一个完整编排至少还需要：

- 明确任务目标和完成条件；
- 明确当前任务所有者；
- 知道各参与者能够做什么、不能做什么；
- 决定消息或产物传给谁；
- 跟踪任务状态和依赖；
- 处理重复、冲突、超时和部分失败；
- 控制循环、预算和终止；
- 能够解释最终结果是如何产生的。

因此：

> **通信是编排的机制之一，不是编排本身。**

## 2. 单 Agent 也存在编排

### 2.1 Agent Loop 是最小编排单元

最小的工具型 Agent 循环已经包含微观编排：

```text
用户目标
   ↓
模型判断
   ├── 调用工具
   ├── 读取工具结果
   ├── 再次推理
   ├── 重试或更换工具
   └── 输出最终结果
```

这里已经发生：

- 动作选择；
- 工具调度；
- 状态积累；
- 观察反馈；
- 循环控制；
- 失败处理；
- 终止判断。

Multi-Agent 是在这个基础上进一步引入：

- 更多执行者；
- 更多上下文边界；
- 更多权限边界；
- 任务所有权转移；
- 结果冲突与聚合；
- 跨 Agent 的状态一致性。

### 2.2 编排知识的合理范围

`agents_orchestration` 的知识范围不应只覆盖 Multi-Agent，而应覆盖：

```text
Agent Orchestration
├── 单 Agent 执行循环
├── 确定性工作流
├── LLM 动态工作流
├── Agent 与工具协作
├── Multi-Agent 协作
├── Human-in-the-loop
└── 长运行与可恢复执行
```

如果直接从 supervisor、group chat 或角色扮演开始，会跳过编排真正困难的部分：状态、控制权、失败恢复与终止。

## 3. 编排的核心对象

编排系统至少需要显式理解五类对象。

### 3.1 Goal：目标

Goal 描述系统最终需要实现的结果，而不是下一步动作。

一个可编排目标通常需要：

- 预期结果；
- 约束条件；
- 成功判据；
- 允许的副作用；
- 时间、成本或 Token 预算；
- 需要人工确认的边界。

目标如果不可验证，编排器也无法可靠判断何时停止。

### 3.2 Task：任务

Task 是可被分配、执行和跟踪的工作单元，可能包含：

- 任务身份；
- 父任务与子任务；
- 依赖关系；
- 当前所有者；
- 输入与预期输出；
- 状态；
- 尝试次数；
- 截止时间与预算；
- 完成证据；
- 失败原因。

“一段发给 Agent 的自然语言”不自动等于完整任务模型。

### 3.3 Actor：执行者

Actor 是能够承担动作的参与者，包括：

- LLM Agent；
- 普通模型调用；
- 工具；
- 确定性函数；
- 外部工作流；
- 人类审批者；
- 远程 Agent 或服务。

不同 Actor 应具有明确的：

- 能力描述；
- 输入输出契约；
- 权限；
- 成本和延迟特征；
- 并发能力；
- 失败语义；
- 是否允许产生副作用。

### 3.4 State：状态

State 不只是对话历史。至少要区分：

- **业务状态**：任务处理对象当前处于什么业务阶段；
- **任务状态**：pending、running、blocked、completed、failed 等；
- **执行状态**：当前步骤、尝试次数、租约、超时和检查点；
- **上下文状态**：各 Actor 当前可见的信息；
- **产物状态**：文件、报告、结构化结果及其版本；
- **控制状态**：预算、权限、审批和终止信号。

如果这些状态全部混在消息历史中，系统很难恢复、审计和验证。

### 3.5 Policy：策略

Policy 决定系统允许如何演化，包括：

- 路由策略；
- 调度和并发策略；
- 权限策略；
- 上下文披露策略；
- 重试与回退策略；
- 结果聚合策略；
- 人工介入策略；
- 预算策略；
- 终止策略。

模型可以参与策略选择，但硬约束不应只存在于 Prompt 中。

## 4. 决策权：代码编排、LLM 编排与混合编排

决策权在哪里，是 Agent 编排的第一条主轴。

### 4.1 代码编排（Code-driven Orchestration）

代码通过条件、状态机、DAG、队列或工作流引擎决定执行路径。

```text
if task.type == "refund":
    run(refund_workflow)
elif task.type == "technical_support":
    run(support_workflow)
```

优势：

- 路径可预测；
- 容易测试和审计；
- 延迟与成本相对稳定；
- 权限和副作用边界明确；
- 适合强业务规则。

局限：

- 难处理开放任务；
- 未知路径需要不断增加规则；
- 复杂条件容易形成僵硬分支；
- 语义判断能力有限。

### 4.2 LLM 编排（LLM-driven Orchestration）

LLM 根据目标、上下文和观察结果动态决定下一步：

- 是否分解任务；
- 调用哪个工具；
- 委派哪个 Agent；
- 是否继续搜索；
- 是否修改计划；
- 是否认为任务完成。

优势：

- 能处理开放问题和未知路径；
- 可以根据环境反馈动态调整；
- 能用自然语言理解能力进行语义路由和任务分解。

风险：

- 同一输入可能产生不同路径；
- 可能遗漏步骤或过度展开；
- 完成判断可能缺乏证据；
- 成本和延迟难预测；
- 仅靠 Prompt 难以保证权限、预算和终止约束。

### 4.3 混合编排（Hybrid Orchestration）

混合编排由代码掌握硬约束，LLM 处理需要语义理解的局部决策：

```text
代码负责硬约束
├── 权限
├── 状态合法性
├── 并发限制
├── 预算
├── 重试上限
├── 提交边界
└── 强制终止

LLM负责语义决策
├── 任务理解
├── 动态分解
├── 专家选择
├── 工具选择
├── 结果解释
└── 局部策略调整
```

一个重要原则是：

> **LLM 可以提出下一步，但不应天然拥有所有状态转换和副作用的最终决定权。**

例如，LLM 可以建议“退款”，但代码仍需验证：

- 当前用户是否有权限；
- 订单是否存在；
- 是否满足退款条件；
- 金额是否在自动审批范围内；
- 操作是否已经执行过；
- 是否需要人工批准。

### 4.4 决策权不是二选一

同一个系统内可以存在不同粒度的决策权：

```text
业务流程：代码控制
   └── 当前阶段的研究策略：LLM 控制
          └── 工具调用参数：结构化输出 + 代码校验
                 └── 有副作用动作：策略引擎或人工批准
```

真正需要设计的不是“用代码还是用 LLM”，而是：

> **每一个决策边界由谁提出、由谁验证、由谁提交。**

### 4.5 决策权是一条权力链

“让 LLM 控制工作流”不是一个足够精确的设计描述。它可能表示：

- LLM 可以提出下一步；
- LLM 可以选择工具；
- LLM 可以生成工具参数；
- LLM 可以决定是否产生副作用；
- LLM 可以修改系统状态；
- LLM 可以认定任务完成；
- LLM 可以把控制权交给另一个 Agent；
- LLM 可以扩大预算或权限。

这些权力的风险完全不同，不能统一授予。

一次完整动作应区分七个阶段：

```text
Observe
   ↓
Propose
   ↓
Validate
   ↓
Authorize
   ↓
Execute
   ↓
Verify
   ↓
Commit
```

#### Observe：观察

系统取得当前事实：

- 用户请求；
- 当前任务状态；
- 工具和环境结果；
- 权限；
- 已发生的副作用；
- 剩余预算；
- 历史执行记录。

环境反馈是事实来源，LLM 对环境的描述不是事实本身。

#### Propose：提出

LLM 根据目标和观察结果提出候选动作：

- 意图解释；
- 任务分解；
- Agent 或工具选择；
- 参数；
- 下一步计划；
- 完成或人工介入建议。

这里产生的是 `ProposedAction`，不是已经发生的事实。

#### Validate：验证

验证回答：

> 这个提议在结构和当前状态上是否成立？

包括：

- 参数是否符合 Schema；
- 资源是否存在；
- 当前状态是否允许该动作；
- 前置步骤是否完成；
- 是否重复执行；
- 预算是否足够；
- Handoff 是否形成循环。

结构化输出只保证形状正确，不保证事实、权限和业务决定正确。

#### Authorize：授权

授权回答：

> 即使动作合法，当前 Actor 是否有权让它发生？

授权依据包括：

- 用户和 Agent 身份；
- 数据与资源作用域；
- 动作风险；
- 金额或资源阈值；
- 是否允许产生副作用；
- 是否需要人工审批。

授权不能只依赖 Prompt 中的行为要求，因为 Prompt 不能形成不可绕过的执行边界。

#### Execute：执行

执行由工具、Runtime 或外部服务完成。LLM 产生调用意图，但不直接构成环境变化。

需要区分：

- 只读查询；
- 可重复计算；
- 本地可逆修改；
- 外部可补偿动作；
- 外部不可逆动作。

#### Verify：核验

执行完成后，需要核验结果是否真实、完整和充分：

- 确定性核验：状态码、数据库记录、文件哈希、测试结果；
- 语义核验：结果是否满足用户目标；
- 人工核验：高风险、价值判断或无法自动评价的结果。

LLM 适合语义核验，但不能单独证明外部副作用已经成功。

#### Commit：提交

Commit 把已验证结果写入编排状态或业务真相源：

```text
action_proposed
      ↓
action_authorized
      ↓
action_executing
      ↓
action_succeeded
```

模型可以建议状态变化，但 Runtime、状态机或业务服务必须验证状态转换是否合法。

### 4.6 最小模型与完整模型

知识层可以同时保留两个模型。

最小三阶段模型：

```text
Propose → Validate → Commit
```

它表达最核心的权力分离：

- LLM 提议；
- 系统验证；
- 系统提交。

完整七阶段模型：

```text
Observe → Propose → Validate → Authorize
        → Execute → Verify → Commit
```

它用于分析生产系统中的完整动作生命周期，强调：

- Validate 与 Authorize 不是一回事；
- Execute 与 Commit 不是一回事；
- 工具返回与业务成功不是一回事；
- 模型建议与环境事实不是一回事。

### 4.7 四种权威来源

| 问题类型 | 主要权威 |
|---|---|
| 语义不确定性 | LLM |
| 系统硬约束 | 确定性代码与策略 |
| 规范性、价值与风险判断 | 人 |
| 外部世界事实 | 环境与工具结果 |

#### LLM：语义权威

适合：

- 用户意图理解；
- 开放任务分解；
- 候选策略生成；
- 模糊信息识别；
- 文本和证据解释；
- 结果语义评价。

但 LLM 不是权限、账户余额、正式任务状态或外部动作结果的真相源。

#### 代码与策略：规则权威

适合维护：

- 权限；
- Schema；
- 状态转换；
- 幂等；
- 预算；
- 并发；
- 截止时间；
- 重试上限；
- 工具白名单；
- 数据作用域；
- 强制终止。

#### 人：规范性权威

Human-in-the-loop 是一等决策主体，不是 Agent 失败后的兜底。人负责：

- 实质歧义裁决；
- 风险接受；
- 高风险和不可逆动作授权；
- 多个合理方案之间的价值选择；
- 专业审查；
- 人工接管。

#### 环境：事实权威

环境和工具结果说明实际发生了什么：

- 文件是否修改；
- 测试是否通过；
- API 是否成功；
- 数据库当前状态；
- 消息是否发出；
- 外部事务是否存在。

四种权威不能相互冒充：

```text
LLM 推断       ≠ 环境事实
代码校验通过   ≠ 用户授权
人工批准       ≠ 动作执行成功
工具返回成功   ≠ 整体任务完成
```

### 4.8 九类决策权

#### 4.8.1 意图解释权

LLM 可以提出对用户意图的解释。低影响歧义可以采用合理默认并说明；会实质改变结果或产生高影响动作的歧义必须由用户确认。

#### 4.8.2 规划权

LLM 可以生成和调整计划，但计划必须受到能力、范围、预算、审批和终止策略约束。计划是候选执行结构，不是命令或完成事实。

#### 4.8.3 路由权

LLM 可以在系统提供的候选 Agent、模型或流程集合中进行语义选择；Runtime 负责验证候选是否存在、可用并被允许。

#### 4.8.4 委派权

委派涉及子任务创建、任务所有权、上下文披露、权限传播、预算分配和结果回收。是否允许继续向下委派也属于显式权限。

#### 4.8.5 提议权

LLM 最适合拥有动作提议权。Tool Calling 从模型视角是“调用工具”，从系统控制视角应理解为“提交动作请求”。

#### 4.8.6 授权权

授权决定特定 Actor 是否可以在当前条件下对特定资源执行具体动作。LLM 可以解释为什么需要授权，但不能给自己授权。

#### 4.8.7 执行权

执行权属于 Tool、Runtime 或外部服务。即使一个 Agent 被命名为“退款 Agent”，也不意味着它可以绕过 Runtime 直接修改支付系统。

#### 4.8.8 状态提交权

LLM 的“任务已经完成”只是一项完成声明。只有状态机或受控提交边界才能在验证完成证据后写入正式状态。

#### 4.8.9 终止权

终止权由不同主体共同承担：

| 终止类型 | 主要决定者 |
|---|---|
| 语义完成 | LLM 提议，验证器确认 |
| 达到硬成功条件 | 代码 |
| 预算耗尽 | Runtime |
| 安全风险 | Policy |
| 用户取消 | 用户 |
| 需要补充信息 | LLM 提议暂停 |
| 高风险异常 | 人工接管或终止 |
| 循环或无进展 | Runtime 检测 |

### 4.9 任务所有权不等于权限

任务所有者负责：

- 推动任务；
- 跟踪进度；
- 协调子任务；
- 回收结果；
- 形成最终输出；
- 解释失败。

权限决定它能否：

- 读取某类数据；
- 调用某个工具；
- 修改某个资源；
- 产生外部副作用；
- 授权其他参与者；
- 提交正式状态。

一个 Agent 可以拥有任务，但没有高风险动作的批准权。审批人可以拥有批准权，但不需要拥有整个任务。

> **任务所有者负责结果收敛，不意味着拥有执行过程中所有动作的权限。**

### 4.10 Handoff 转移什么

Handoff 至少需要分别判断五种内容是否转移：

```text
Handoff
├── 对话控制权
├── 任务所有权
├── 上下文可见范围
├── 可用能力
└── 预算与期限
```

默认不应转移：

- 原 Agent 的全部权限；
- 用户未授权的数据；
- 无关会话历史；
- 无限预算；
- 再委派权；
- 高风险动作批准权。

### 4.11 权限衰减原则

委派只能缩小或保持权限，不能自动扩大权限：

```text
ChildAuthority
  ⊆ ParentAuthority
  ∩ ChildPolicy
  ∩ TaskRequiredAuthority
```

含义是：

- 父 Agent 没有的权限，不能凭委派创造；
- 子 Agent 自身策略禁止的能力，不能由父 Agent 强行赋予；
- 即使父子都有某项能力，也只授予当前子任务所需范围；
- 扩大权限必须经过独立 Policy 或 Human 授权。

权限衰减适用于 Agent as Tool、Handoff、动态 Worker 和多级委派。

### 4.12 三种权限表达方式

#### 角色权限

```text
refund_agent → 可以查询订单、创建退款建议
```

简单易懂，但角色容易获得过宽权限。

#### 工具权限

```text
当前 Agent 可以使用：
- get_order
- calculate_refund
- propose_refund
```

比角色权限更细，但仍需限制工具能够访问的资源范围。

#### 动作级 Capability

```text
Capability
├── actor: refund_agent
├── action: read_order
├── resource: order/ORD-123
├── scope: current_user
├── expires_at: ...
├── max_calls: 3
├── delegable: false
└── side_effect: none
```

动作级 Capability 可以绑定 Actor、动作、资源、范围、有效期、次数、预算和可委派性，控制最精确，但工程成本也最高。

知识上应完整理解三层；具体项目可以从角色与工具白名单起步，再按风险演进到动作级 Capability。

### 4.13 不可自授予的权力

Agent 可以请求，但不能自行完成以下权限提升：

1. 扩大数据访问范围；
2. 增加高风险工具；
3. 提高金额或资源额度；
4. 延长 Deadline；
5. 增加总体预算；
6. 提升最大委派深度；
7. 获得不可逆动作权限；
8. 把不可委派权限传给子 Agent；
9. 跳过强制审批；
10. 修改约束自身的控制策略。

合理流程是：

```text
Agent 请求额外能力
        ↓
Policy / Human 判断
        ↓
签发范围受限的新 Capability
        ↓
Agent 在新边界内继续执行
```

### 4.14 Replanning 的权力边界

Agent 修改计划时需要区分：

| 变化类型 | 默认控制主体 |
|---|---|
| 搜索方式、工具顺序等策略调整 | Agent |
| 增加新的业务目标或扩大范围 | 用户 |
| 增加工具、数据和副作用权限 | Policy / Human |
| 扩大 Token、时间或调用预算 | Runtime / Human |

Replanning 可以改变实现路径，但不能借机扩大任务范围、权限和预算。

### 4.15 受限自治（Capability-Enveloped Autonomy）

推荐的混合编排形态是由确定性控制外壳包裹 LLM 自适应核心：

```text
┌─────────────────────────────────────────────┐
│             确定性控制外壳                  │
│                                             │
│  权限  预算  状态机  幂等  超时  审批  终止 │
│                                             │
│      ┌─────────────────────────────┐        │
│      │       LLM 自适应核心        │        │
│      │ 理解、分解、选择、解释、调整 │        │
│      └─────────────────────────────┘        │
└─────────────────────────────────────────────┘
```

每次 Run 的自治包络应明确：

```text
Autonomy Envelope
├── 可用 Agent
├── 可用工具
├── 数据作用域
├── 可执行动作类型
├── 最大步骤数
├── 最大委派深度
├── 最大并发数
├── Token / 时间 / 金额预算
├── 必须审批的动作
├── 完成判据
└── 强制终止条件
```

在包络内，LLM 可以动态选择路径；越出包络则必须被拒绝、降级或升级。

### 4.16 退款场景中的权力分离

```text
用户：“把刚才重复扣款的订单退掉”
                     │
                     ▼
LLM 识别意图，发现订单不明确
                     │
                     ▼
只读查询候选订单
                     │
                     ▼
用户消除实质歧义
                     │
                     ▼
LLM 提议具体退款动作
                     │
                     ▼
代码验证订单、金额、重复执行和业务状态
                     │
                     ▼
Policy / Human 授权
                     │
                     ▼
支付工具以幂等键执行
                     │
                     ▼
环境查询核验退款结果
                     │
                     ▼
状态机提交 refund_succeeded
                     │
                     ▼
LLM 向用户解释结果
```

没有任何一个参与者拥有全部权力：

- LLM 理解和提议；
- 用户消除意图歧义；
- 代码维护规则；
- Policy 或人决定授权；
- 工具产生副作用；
- 环境提供事实；
- 状态机提交结果；
- LLM 负责最终解释。

## 5. 安全防控

### 5.1 安全是贯穿编排的控制体系

Agent 编排安全不等于在高风险工具前增加一次审批。安全贯穿：

- 输入与目标解释；
- 任务分解；
- 路由和委派；
- 上下文传递；
- 工具调用；
- 外部副作用；
- 状态提交；
- 循环和终止；
- Trace、审计与评测。

安全防控的目标是：

> **即使模型误判、工具失败、上下文被污染或参与者越界，系统仍能把影响限制在可接受范围内并留下可恢复证据。**

### 5.2 风险属于具体动作实例

风险不属于某个 Agent 或工具名称本身，而属于：

> 某个 Actor 在当前上下文中，对特定资源执行具有具体参数和预期影响的动作。

可以抽象为：

```text
RiskDecision = Policy(
    actor,
    action,
    resource,
    scope,
    parameters,
    context,
    expected_effect
)
```

同一个 `send_email`：

- 保存一封内部草稿可能是低风险；
- 向一个已确认客户发送通知可能是中风险；
- 向五千名外部联系人发送敏感内容可能是极高风险。

同一个 `read_file`：

- 读取公开 README 是低风险；
- 读取生产 Secret 或其他租户数据是高风险甚至禁止动作。

### 5.3 风险判断的八个维度

#### 影响范围

动作影响当前临时任务、当前用户、团队、租户、外部客户还是公共环境。

#### 可逆性

需要区分自然可逆、可补偿、部分可补偿和不可逆。存在补偿动作不等于真正可逆。

#### 外部性

动作是否停留在推理或隔离环境，还是影响共享系统、外部人员和现实世界。

#### 数据敏感度

公开、内部、用户私有、认证、财务、医疗、法律和 Secret 数据具有不同控制要求。只读动作也可能造成高风险披露。

#### 权限增量

新工具、更大数据范围、更高写权限、更长时间、更多预算、更深委派或跨信任边界都属于权限增量。

#### 事实与意图不确定性

事实不确定与意图不确定应通过补充观察或澄清降低，而不是由 Agent 猜测后直接执行。

#### 可验证性

动作完成后越难自动验证，越不能仅由 Agent 自主判断成功和完成。

#### 时效性

时效性决定使用预授权、自动策略还是人工审批，不是放弃控制的理由。审批和执行之间状态可能变化。

### 5.4 三种风险控制方式

#### 工具级静态分级

```text
web_search      → LOW
read_file       → LOW
write_file      → MEDIUM
send_email      → HIGH
transfer_money  → CRITICAL
```

优点是简单、可审计；缺点是粒度过粗，无法表达资源、范围和参数差异。

#### 动态风险评分

每次动作根据参数、资源和上下文重新判断。控制精细，但策略复杂；如果完全交给 LLM，又会把安全边界概率化。

#### 静态基线 + 动态修正 + 硬规则升级

推荐采用混合模型：

```text
工具 / Capability 静态风险基线
              +
参数、资源和上下文动态修正
              +
不可绕过的确定性规则升级
```

其中：

- LLM 辅助识别语义风险；
- 确定性规则维护不可绕过的升级条件；
- Human 处理规范性判断和高风险授权；
- Agent 不能自行降低硬规则确定的风险等级。

### 5.5 风险等级 R0–R5

#### R0：无外部影响

推理、分类、生成候选计划和内存中间结果。通常自动执行，但仍受步骤、Token 和时间预算限制。

#### R1：受限只读

搜索、读取当前任务允许的数据、查询状态。可以自动执行，但必须经过数据作用域和敏感信息检查。

#### R2：隔离环境中的可逆写入

修改草稿、临时文件、沙箱代码和未提交产物。可以有较高自治，但需要版本、diff、回滚和资源限制。

#### R3：共享状态或外部副作用

修改共享文档、创建正式工单、发送邮件、提交代码和更新正式数据库。需要确定性授权、幂等、结果核验和审计。

#### R4：高影响或不可逆动作

转账、大额退款、永久删除、公共发布、修改访问控制和导出敏感数据。默认人工批准，并要求完整动作预览、影响说明和提交后核验。

#### R5：禁止动作

越权访问其他租户、绕过安全策略、篡改审计、Agent 自我提权、传播不可委派权限等动作直接拒绝，不进入人工审批。

### 5.6 风险与控制结果

风险等级不应机械映射为一个“是否审批”布尔值。控制结果包括：

| 控制结果 | 含义 |
|---|---|
| `AUTO_ALLOW` | 自动执行 |
| `ALLOW_WITH_LIMITS` | 在次数、作用域和预算限制内执行 |
| `REQUIRE_CLARIFICATION` | 信息或意图不足，询问用户 |
| `REQUIRE_CONFIRMATION` | 用户确认系统理解的具体动作 |
| `REQUIRE_APPROVAL` | 具有授权资格的人批准 |
| `REQUIRE_REVIEW` | 动作或产物需要专业审查 |
| `DEFER` | 当前无法安全决定，等待新证据 |
| `DENY` | 明确禁止 |
| `TERMINATE` | 停止当前任务或 Run |

### 5.7 Human-in-the-loop 的五种语义

#### Clarification：澄清

解决用户到底想做什么，以及缺少哪些事实。

#### Confirmation：确认

用户确认系统对其意图和具体动作的理解。

#### Approval：授权

具备授权资格的人允许动作发生。用户确认不一定构成授权。

#### Review：审查

判断动作或产物质量是否可接受，例如法律、财务或品牌审查。

#### Takeover：接管

人类取得任务所有权，不再只是批准单个动作。

Human-in-the-loop 不应被简化为一个通用的“确认按钮”。

### 5.8 六类安全 Gate

```text
输入
 ↓
① Scope Gate
 ↓
任务分解
 ↓
② Delegation Gate
 ↓
动作提议
 ↓
③ Action Gate
 ↓
执行
 ↓
④ Result Gate
 ↓
状态提交
 ↓
⑤ Commit Gate
 ↓
继续或结束
 ↓
⑥ Convergence Gate
```

#### Scope Gate

检查目标、实质歧义、范围扩张，以及当前用户是否有资格提出请求。

#### Delegation Gate

检查是否允许委派、Agent 是否匹配、权限是否衰减、上下文是否最小披露，以及深度和预算是否允许。

#### Action Gate

检查参数、权限、风险、幂等、审批和操作对象的当前有效性。

#### Result Gate

检查工具是否真正成功、结果是否可信、是否需要二次核验，以及是否出现部分成功。

#### Commit Gate

检查状态转换、完成证据、版本冲突和副作用记录，然后才允许写入正式状态。

#### Convergence Gate

检查是否完成、无进展、循环、预算超限或需要暂停、降级和人工接管。

### 5.9 审批必须绑定动作快照

不应只批准抽象工具：

```text
允许 refund_order
```

而应批准具体动作实例：

```text
actor        = refund_agent
action       = refund_order
order_id     = ORD-123
amount       = 100
currency     = CNY
reason       = duplicate_charge
idempotency  = refund-ORD-123-v1
expires_at   = ...
```

审批后，如果订单、金额、收款方、资源范围或动作类型变化，原审批必须失效并重新评估。

审批对象应是具体动作提议的不可变快照，而不是 Agent 身份或工具名称。

### 5.10 审批后的重新验证

审批时合法，不代表执行时仍然合法：

```text
T1：订单尚未退款 → 审批通过
T2：另一个流程完成退款
T3：当前流程继续执行 → 可能重复退款
```

这是检查与使用之间的状态变化（TOCTOU）。高风险动作需要：

```text
提出
 ↓
验证
 ↓
审批
 ↓
执行前重新验证
 ↓
幂等执行
 ↓
执行后核验
```

审批不能代替执行前重新验证。

### 5.11 动态风险升级

出现以下情况时，应重新评估并可能升级风险：

- 用户意图出现新歧义；
- Agent 扩大任务范围；
- 请求新的权限；
- 访问新的数据域；
- Handoff 超过预期深度；
- Worker 结果冲突；
- 多次重试失败；
- 实际影响范围大于预估；
- 工具返回部分成功；
- 参数在批准后变化；
- 证据不足却准备提交完成；
- Agent 出现循环或无进展。

风险不是任务开始时计算一次的静态标签，而是在关键 Gate 持续重算的控制状态。

### 5.12 纵深防御

单一 Guardrail 无法覆盖整个 Agent 执行链。推荐使用多层防线：

```text
输入与目标约束
      ↓
能力与权限约束
      ↓
上下文隔离与最小披露
      ↓
参数、Schema 与业务验证
      ↓
审批与副作用 Gate
      ↓
沙箱、幂等与资源限制
      ↓
结果核验与受控提交
      ↓
Trace、审计与评测
```

每一层假设其他层可能失败，通过限制影响范围提高整体可靠性。

### 5.13 Guardrail 的常见误区

#### Prompt 规则不是强 Guardrail

“不要执行危险操作”属于模型行为约束，不能替代运行时阻断能力。

#### Schema 不是业务验证

Schema 可以检查字段形状，但不能证明权限、事实和业务条件成立。

#### LLM Evaluator 不是确定性授权器

评估 Agent 适合语义质量判断，不适合单独批准高风险副作用。

#### Human-in-the-loop 不是万能答案

审批界面必须说明动作、对象、范围、参数、理由、证据、可逆性和拒绝后果，否则会形成审批疲劳。

#### 审批不等于执行成功

审批只授予执行资格，执行结果仍需环境核验。

### 5.14 Prompt Injection 与跨 Agent 传播

外部文档、网页、工具结果、Memory 和其他 Agent 消息都是潜在不可信数据。安全边界需要防止：

- 把数据内容提升为系统指令；
- 在 Handoff 中传播污染上下文；
- Worker 将不可信指令写入共享状态；
- 聚合器把恶意内容当成控制命令；
- Memory 将一次攻击持久化到未来任务。

关键原则：

- 指令、事实、证据和外部数据分层；
- 上下文最小披露；
- Handoff 输入过滤；
- 工具结果不直接获得控制权；
- 写入共享状态或长期 Memory 前重新验证。

### 5.15 审计与安全评测

安全 Trace 应能够回答：

- 谁提出了动作；
- 谁验证和授权；
- 批准的是哪个动作快照；
- 执行使用了什么 Capability；
- 权限是否经过委派；
- 哪些状态发生变化；
- 结果如何核验；
- 为什么继续、暂停、拒绝或终止。

安全评测至少覆盖：

- 越权动作阻断率；
- 权限衰减正确性；
- 审批绕过率；
- 参数变化后的重新审批；
- 重复副作用率；
- 跨 Agent 污染传播；
- 敏感数据泄露；
- 高风险动作的核验覆盖；
- 错误拒绝与审批负担。

### 5.16 安全防控的阶段性结论

1. 安全是贯穿编排全流程的控制体系，不是单个工具前的审批。
2. 风险属于具体动作实例，不属于工具名称本身。
3. 使用“静态基线 + 动态修正 + 硬规则升级”的混合风险模型。
4. Agent 可以参与风险识别，但不能自行降低硬规则风险。
5. 权限默认衰减，任何扩大都需要独立授权。
6. R5 禁止动作直接拒绝，不进入人工审批。
7. 澄清、确认、授权、审查和接管具有不同编排语义。
8. 审批绑定具体动作快照，参数变化后原审批失效。
9. 审批后、执行前重新验证，执行后核验外部事实。
10. Scope、Delegation、Action、Result、Commit、Convergence 是六类关键 Gate。
11. Prompt、Schema、LLM Evaluator 和 Human Approval 都不能单独构成完整防线。
12. 纵深防御、最小权限、状态控制、审计和评测共同形成安全闭环。

## 6. 三平面模型

Agent 编排同时包含三类性质不同的工作：

```text
决定接下来做什么
保存系统现在是什么
真正让动作发生
```

分别对应：

- **控制平面（Control Plane）**；
- **状态与上下文平面（State & Context Plane）**；
- **执行平面（Execution Plane）**。

安全、可观测性和评测作为横切能力贯穿三个平面。

```text
┌─────────────────────────────────────────────┐
│ 控制平面 Control Plane                     │
│ 路由、规划、调度、权限、预算、停止、重试   │
├─────────────────────────────────────────────┤
│ 状态与上下文平面 State & Context Plane      │
│ 任务状态、上下文、消息、证据、产物、版本   │
├─────────────────────────────────────────────┤
│ 执行平面 Execution Plane                    │
│ Agent、模型、工具、工作流、人工、运行环境   │
└─────────────────────────────────────────────┘
             ↑ 可观测性、安全、评测贯穿三层
```

### 6.1 为什么需要三个平面

三个平面具有不同的核心问题和可靠性要求：

| 平面 | 核心问题 | 主要要求 |
|---|---|---|
| 控制平面 | 下一步应该做什么 | 决策、约束、收敛 |
| 状态与上下文平面 | 当前已知什么、发生过什么 | 一致性、身份、版本、可恢复 |
| 执行平面 | 如何让动作真正发生 | 隔离、资源、幂等、副作用 |

如果把三类职责全部混在一个 Agent Loop 中：

```text
LLM 读取聊天历史
 → 决定下一步
 → 调用工具
 → 用自然语言描述结果
 → 把描述当作新状态
```

就容易出现：

- 模型声明取代正式状态；
- 工具结果和事实混在消息里；
- 无法区分动作提议与动作完成；
- 重启后不知道执行到哪里；
- Handoff 时只能传递整段历史；
- Worker 越过控制边界直接修改共享状态；
- 无法精确恢复和审计。

因此，三平面首先是认知分离和责任分离。

### 6.2 三平面的反馈闭环

三平面共同构成一个持续反馈的控制循环：

```text
       ┌───────────────────────────┐
       │                           │
       ▼                           │
┌──────────────┐                  │
│ 状态与上下文 │                  │
│    平面      │                  │
└──────┬───────┘                  │
       │ State Snapshot            │
       ▼                           │
┌──────────────┐                  │
│   控制平面   │                  │
│ Decide/Route │                  │
└──────┬───────┘                  │
       │ Command                   │
       ▼                           │
┌──────────────┐                  │
│   执行平面   │                  │
│ Agent/Tool   │                  │
└──────┬───────┘                  │
       │ Observation/Artifact      │
       └───────────────────────────┘
```

执行过程是：

1. 状态与上下文平面提供当前状态快照；
2. 控制平面根据目标、状态和策略产生 Command；
3. 执行平面执行 Command；
4. 执行平面返回 Observation、Result 或 Artifact；
5. 状态与上下文平面验证并提交状态变化；
6. 控制平面基于新状态决定继续、暂停、委派或终止。

与权力链的对应关系：

| 权力阶段 | 主要平面 |
|---|---|
| Observe | 状态与上下文平面提供事实和快照 |
| Propose | 控制平面中的 LLM 或规则 |
| Validate / Authorize | 控制平面结合正式状态 |
| Execute | 执行平面 |
| Verify | 三平面共同参与 |
| Commit | 状态与上下文平面 |

核心闭环可以浓缩为：

```text
State → Decision → Command → Execution
      → Observation → Verify → Commit
```

### 6.3 控制平面（Control Plane）

控制平面决定系统接下来如何行动：

- 任务分解；
- 路由；
- 调度；
- 并行与串行；
- 所有权转移；
- 预算分配；
- 重试与回退；
- 暂停与恢复；
- 终止与人工升级。

Router、planner、scheduler、supervisor、policy engine 都可能属于控制平面，但它们不是必须由同一个组件承担。

控制平面同时包含两类控制：

```text
确定性控制
├── 权限
├── 状态合法性
├── 预算
├── 调度
├── 并发
└── 强制终止

概率性控制
├── 意图理解
├── 动态规划
├── 语义路由
├── 结果解释
└── 完成提议
```

控制平面可以产生 Command、Task、Handoff Request 和 Stop Proposal，但不能凭自身声明创造环境事实。

### 6.4 状态与上下文平面（State & Context Plane）

状态与上下文平面负责保存正式状态，并为不同 Actor 生成最小充分的上下文投影：

- 原始目标；
- 任务图；
- 消息；
- 上下文；
- 工具观察；
- 中间产物；
- 完成证据；
- 审批记录；
- 状态版本；
- 追踪关联。

这里需要区分：

#### State：正式状态

State 是系统当前正式、可恢复、可验证的工作视图，包括：

- 当前目标；
- Task 和 Attempt；
- 状态机位置；
- 任务依赖；
- 所有权；
- 权限和审批；
- 已确认副作用；
- 预算消耗；
- 产物和完成证据。

#### Context：状态投影

Context 是根据当前 Actor、任务和权限从 State 中选择出的运行视图：

```text
完整编排状态
├── 用户身份
├── 权限
├── 所有任务
├── 审批记录
├── 工具结果
├── 中间产物
├── Secret
└── 预算

Worker 上下文
├── 当前子任务
├── 必要输入
├── 可用工具
├── 完成标准
└── 局部预算
```

Worker 不应看到完整状态，也不应因为看到了某些信息就自动获得修改它们的权限。

因此：

> **让每个参与者得到完成当前职责所需的最小充分上下文。**

状态与上下文平面需要承担：

- 真相源管理；
- 状态身份和 Schema；
- 版本与并发控制；
- Checkpoint；
- 上下文选择、过滤和压缩；
- Artifact、Message、Event 和 Observation 的关联；
- 状态提交和恢复；
- 数据保留、隔离与审计。

“上下文”不等于聊天历史。本地 Runtime Context、模型可见上下文、长期 Memory 和任务正式状态需要明确区分。

### 6.5 执行平面（Execution Plane）

执行平面真正执行动作：

- 模型推理；
- Agent Loop；
- 工具调用；
- 文件或数据库操作；
- 外部 API；
- 沙箱任务；
- 人工审批；
- 远程 Agent 调用。

执行平面接收受约束的 Command，并返回：

- `Observation`：环境中观察到了什么；
- `Result`：一次动作的结构化结果；
- `Artifact`：文件、报告、代码、数据集等持久产物；
- `Error`：失败类型、范围和可重试性；
- `Usage`：时间、Token、成本与资源使用。

执行平面不能只用自然语言声称动作完成；对于外部副作用，应提供可核验结果和关联身份。

### 6.6 为什么不能只有控制平面和执行平面

简单 Demo 常被建模成：

```text
Controller → Worker
```

状态隐含在 Controller 的内存或消息历史中。随着任务变长，会出现：

#### 控制器重启导致状态丢失

系统无法判断哪些任务完成、哪些工具调用过、哪些副作用已发生、哪些 Worker 仍在运行，以及从哪里恢复。

#### 多个控制者看到不同事实

Supervisor、Router、Evaluator、Human Reviewer 和 Retry Scheduler 可能各自维护一份任务理解，形成多个不一致的真相源。

#### 状态无法独立治理

身份、Schema、版本、所有权、并发、持久化、迁移、审计和删除不应由 Planner 或 Router 顺带承担。

#### 上下文无法最小披露

如果没有独立 State，就只能把整段聊天历史转给 Worker，无法形成面向任务和权限的上下文投影。

因此，状态与上下文平面不是可选存储层，而是控制与执行之间的正式事实边界。

### 6.7 与传统控制平面 / 数据平面的相同点

传统系统中：

- 控制平面维护期望状态、策略和路由；
- 数据平面执行高频实际工作；
- 运行反馈回到控制平面。

Agent 编排也具有：

- 控制与执行分离；
- 控制平面不直接完成所有实际工作；
- 执行者依据受约束命令运行；
- 环境反馈影响下一次控制决策；
- 策略和事实不能只存在于执行者内部。

### 6.8 与传统模型的关键不同

#### Agent 控制决策具有概率性

传统控制器通常根据明确期望状态执行确定性调整。Agent 控制平面还要处理模糊目标、不完整观察、多个合理路径和语义完成条件。

#### 数据会反过来影响控制

网页、文档、工具结果和其他 Agent 消息既是数据，也可能包含不可信指令。数据进入模型后可能改变后续控制决策，因此上下文安全是独立问题。

#### 执行者也可能产生局部控制

```text
全局视角：
Supervisor 是控制者
Worker Agent 是执行者

Worker 内部视角：
Worker 的 LLM 是局部控制者
Worker 的 Tools 是执行者
```

平面描述的是当前职责，不是永久组件身份。

#### Agent 任务具有语义完成条件

完成可能需要同时判断证据充分性、用户意图、结果质量和未解决异议，因此 Verify 和 Termination 往往由环境事实、确定性条件、LLM 判断和人工判断共同完成。

### 6.9 平面不是组件分类

错误理解：

```text
Orchestrator 类 = 控制平面
Database         = 状态平面
Agent 类         = 执行平面
```

更准确的理解是：

> **平面描述职责；一个组件可以承载多个平面职责，但每一次操作应能判断属于哪个平面。**

例如 Runner 可能同时：

- 驱动循环：控制平面；
- 调度工具：执行平面调度；
- 保存 RunState：状态与上下文平面；
- 产生 Trace：横切可观测性。

人也可以承担不同平面职责：

- 审批动作：控制平面；
- 手工修改产物：执行平面；
- 提供补充事实：产生 Observation；
- 接管任务：改变任务所有权。

### 6.10 平面不是部署边界

三平面不意味着首版必须部署三个服务。

#### 单进程

```text
Python Process
├── Orchestrator
├── State Store
├── Context Builder
├── Agent Runner
└── Tool Executor
```

适合学习项目、单用户、短任务、低并发和有限副作用。

#### 模块化单体

```text
Application
├── control/
├── state_context/
├── execution/
├── policy/
└── observability/
```

职责和接口分开，但部署在同一应用中。它通常是学习项目进入实践阶段时更合理的起点。

#### 分布式运行时

```text
Control Service
      │
State / Event Store
      │
Worker Runtimes
```

适合长运行、高并发、跨进程 Worker、独立扩缩容和故障隔离。

核心顺序是：

> **先分职责，再根据规模、信任边界和可靠性需求决定是否分部署。**

### 6.11 安全、可观测性和评测为何不是第四平面

它们更适合作为横切能力：

```text
                    安全
                     │
┌────────────────────┼────────────────────┐
│ 控制平面           │ 权限、预算、策略   │
│ 状态与上下文平面   │ 隔离、脱敏、审计   │
│ 执行平面           │ 沙箱、幂等、限流   │
└────────────────────┼────────────────────┘
                     │
              可观测性与评测
```

如果把安全单独变成“安全平面”，容易让其他平面把安全责任外包。

- 安全在三个平面分别执行不同控制；
- 可观测性采集三个平面的事件；
- 评测同时评价控制路径、状态变化和执行结果。

### 6.12 跨平面交互契约

三个平面之间不应只交换自然语言：

| 方向 | 主要契约 |
|---|---|
| 状态与上下文 → 控制 | `StateSnapshot`、`ContextProjection`、`PolicyFacts` |
| 控制 → 执行 | `Command`、`TaskAssignment`、`Capability` |
| 执行 → 状态与上下文 | `Observation`、`Result`、`Artifact`、`Error` |
| 状态与上下文 → 控制 | `CommittedState`、`Conflict`、`PendingApproval` |

自然语言可以作为载荷，但身份、状态、权限和因果关联必须结构化。

### 6.13 常见跨平面职责错位

| 现象 | 职责错位 |
|---|---|
| Router 选错 Agent | 控制平面决策问题 |
| Handoff 后丢失关键事实 | 上下文投影问题 |
| Worker 同时修改同一产物 | 状态所有权与执行隔离问题 |
| 服务重启后任务消失 | 状态持久化问题 |
| 聚合遗漏 Worker 异议 | Artifact 与证据关联问题 |
| Agent 越权调用工具 | 控制授权与执行校验问题 |
| LLM 声称完成后直接写状态 | 控制提议越过 Commit Gate |
| 工具结果只存在聊天记录中 | 执行结果没有进入正式状态 |

分平面能让故障被归因到正确职责，而不是全部归因于 Prompt。

### 6.14 三平面模型的阶段性结论

1. 三平面是逻辑职责边界，不是固定组件或部署边界。
2. 控制平面决定下一步，但不能自行创造环境事实。
3. 状态与上下文平面保存正式状态，并生成面向 Actor 的最小充分上下文。
4. 执行平面让动作真正发生，并返回 Observation、Result、Artifact 和 Error。
5. 状态变化必须经过受控提交，模型声明不能直接成为正式状态。
6. 一个组件可以承载多个平面职责，一个 Agent 也可能同时是全局执行者和局部控制者。
7. 安全、可观测性和评测横切三平面，不外包给独立第四平面。
8. 首版可以采用单进程或模块化单体，无需因逻辑分层过早分布式。
9. 三平面形成 `State → Decision → Command → Execution → Observation → Commit` 反馈闭环。
10. 正式名称采用 `State & Context Plane`，避免与传统 Data Plane 混淆。

## 7. 编排模式全景

本节只建立模式谱，不展开具体实现。

### 7.1 Sequential / Prompt Chaining

```text
A → B → C
```

固定步骤串行执行，前一步输出成为后一步输入。

适合：

- 步骤可以稳定预定义；
- 每一步职责清晰；
- 中间结果可验证。

核心难点：

- 中间结果契约；
- 错误传播；
- 断点恢复；
- 跳步、回退和补偿。

### 7.2 Routing

```text
             ┌→ 专家 A
输入 → Router ├→ 专家 B
             └→ 专家 C
```

根据输入或当前状态选择不同执行路径。

核心难点：

- 模糊或跨领域任务；
- 多选路由；
- 误路由纠正；
- 路由置信度；
- 未知类别和兜底路径。

### 7.3 Parallelization

```text
          ┌→ Worker A ─┐
任务 ─────├→ Worker B ─┼→ Aggregator
          └→ Worker C ─┘
```

包括两种不同目的：

- **Sectioning**：不同 Worker 处理独立子任务；
- **Voting / Ensemble**：多个 Worker 独立处理同一任务。

核心难点：

- 子任务是否真正独立；
- 并发写冲突；
- 部分失败；
- 结果比较与合并；
- 多数意见不一定正确。

### 7.4 Orchestrator–Workers

```text
                  ┌→ Worker A
目标 → Orchestrator → Worker B → 综合
                  └→ Worker C
```

Orchestrator 根据具体目标动态分解任务、选择 Worker 并汇总结果。

与普通并行的关键区别：

- 普通并行的子任务通常预先定义；
- orchestrator-workers 的子任务由编排者运行时动态生成。

核心难点：

- 分解遗漏与重叠；
- Worker 能力匹配；
- 动态任务图膨胀；
- 共享状态冲突；
- 结果证据保留；
- 完成度判断。

### 7.5 Handoff

```text
Agent A ──控制权或任务所有权转移──▶ Agent B
```

Handoff 与“Agent as Tool”不同：

- Agent as Tool：管理者保留任务所有权和最终回答权；
- Handoff：新的 Agent 接管部分或全部控制权。

核心难点：

- 转移的究竟是执行权、对话权还是任务所有权；
- 传递完整历史还是上下文投影；
- 原 Agent 能否收回控制；
- 新 Agent 失败后返回谁；
- 用户感知到的是谁。

### 7.6 Evaluator–Optimizer

```text
生成者 → 结果 → 评估者
   ↑                │
   └──── 修改意见 ──┘
```

适合有明确质量标准，且反馈能够实质改善结果的任务。

必须同时设计：

- 评估标准；
- 通过阈值；
- 最大迭代次数；
- 成本预算；
- 无改进检测；
- 人工接管。

### 7.7 Group Chat

多个 Agent 在共享会话中交流，由主持者或规则决定发言者和终止。

适合需要显式多方讨论、角色观点碰撞或协商的任务，但不应作为默认模式。

常见风险：

- 重复发言；
- 角色漂移；
- 互相附和；
- 上下文快速膨胀；
- 缺少明确任务所有者；
- 讨论难以终止。

### 7.8 模式可以组合

现实系统通常不是单一模式：

```text
输入
 ↓
路由
 ├── 简单任务 → 单 Agent
 └── 复杂任务 → Orchestrator
                    ├── 并行 Worker
                    ├── 专家 Handoff
                    └── Evaluator 检查
                              ↓
                          人工审批
```

模式选择不应基于框架提供了哪些类，而应基于任务结构、决策不确定性、状态边界和失败语义。

## 8. 与邻近概念的边界

### 8.1 Orchestration 与 Planning

- **Planning** 回答“准备怎么做”；
- **Orchestration** 负责让计划在真实环境中执行、校验、调整和终止。

计划只是编排状态中的一种产物，不是编排本身。

### 8.2 Orchestration 与 Workflow

- Workflow 通常强调预定义路径；
- Orchestration 还包括运行时动态选择、控制权转移和状态治理。

一个 workflow engine 可以承载 Agent 编排，但它不会自动解决语义路由、上下文投影和完成判断。

### 8.3 Orchestration 与 Agent Loop

Agent Loop 是单 Agent 内部“思考—行动—观察”的循环，是编排的最小单元。

系统级编排还需要管理多个循环之间的：

- 任务关系；
- 状态传递；
- 权限；
- 资源竞争；
- 所有权；
- 生命周期。

### 8.4 Orchestration 与 Tool Calling

Tool Calling 是 Agent 发起外部动作的一种机制。

它不负责：

- 任务分解；
- 多工具之间的依赖；
- 副作用提交；
- 失败补偿；
- 整体完成判断。

### 8.5 Orchestration 与 Multi-Agent

Multi-Agent 表示多个 Agent 参与同一系统；Orchestration 表示这些参与者和其他执行单元如何被协调和控制。

没有清晰控制与状态模型的 Multi-Agent 系统，可能只是一组互相发送消息的模型调用。

### 8.6 Orchestration 与 Runtime

Runtime 负责：

- 进程或任务调度；
- 事件传递；
- 状态持久化；
- 检查点；
- 超时；
- 恢复；
- 资源隔离。

Runtime 承载编排，但不自动定义任务语义、控制权和结果聚合策略。

### 8.7 Orchestration 与 Protocol

Protocol 定义参与者如何发现彼此、发送消息和表达能力。

协议解决“如何通信”，但不能独自解决：

- 为什么委派；
- 委派什么；
- 谁拥有任务；
- 如何验证结果；
- 什么时候终止。

### 8.8 Orchestration 与 Memory

Memory 保存跨步骤或跨会话可复用的信息；Orchestration 决定：

- 何时召回；
- 何时写入；
- 传给哪个 Actor；
- 允许看到哪些范围；
- 如何避免旧状态污染当前决策。

## 9. 什么时候需要 Multi-Agent

### 9.1 “任务复杂”不是充分条件

一个能力足够的单 Agent 配合清晰工具、动态 Prompt 和受控工作流，往往比 Multi-Agent 更简单可靠。

Multi-Agent 更合理的触发条件包括：

1. **上下文隔离**：不同职责需要不同知识和指令，放进一个上下文会互相干扰。
2. **能力隔离**：不同角色需要不同模型、工具或运行环境。
3. **权限隔离**：不同参与者必须拥有不同数据或副作用权限。
4. **真实并行性**：存在相互独立、值得并行的子任务。
5. **所有权转移**：业务本身要求专家接管或跨域升级。
6. **独立评估**：生成与评估需要角色分离，以减少自证正确。
7. **工具面过大**：单 Agent 面对的工具和策略太多，导致选择可靠性下降。

### 9.2 Multi-Agent 引入的新成本

Multi-Agent 会新增：

- 协调错误；
- 上下文丢失；
- 重复劳动；
- 状态冲突；
- 结果不一致；
- 延迟与 Token 成本；
- 权限扩散；
- 追踪复杂度；
- 评测空间组合爆炸。

因此应遵循：

> **只有当角色拆分带来的上下文隔离、能力边界、并行收益或质量收益能够被验证时，才增加 Agent 数量。**

## 10. 编排的核心设计张力

### 10.1 自主性与可控性

- 自主性高：能够适应未知路径，但行为和成本难预测；
- 可控性高：容易验证和审计，但难处理开放任务。

问题不是选一边，而是确定每个决策边界的控制方式。

### 10.2 灵活路径与可恢复执行

动态路径可以提高适应性，但恢复要求系统显式记录：

- 已经做了什么；
- 为什么这样做；
- 产生了哪些副作用；
- 哪些结果可以复用；
- 从哪里继续才不会重复执行。

### 10.3 共享上下文与最小披露

共享越多，参与者越容易理解全局；但也会带来：

- 上下文膨胀；
- 注意力稀释；
- 敏感信息扩散；
- 指令污染；
- Agent 间不必要耦合。

### 10.4 并行速度与状态冲突

并行可以降低墙钟时间，但只有在子任务真正独立时才安全。

对共享产物的并行写入，需要所有权、版本、合并或提交协议。

### 10.5 专业化与协调成本

角色越专业，单个 Agent 的 Prompt 和工具面越聚焦；但角色越多，路由、上下文传递和结果聚合越复杂。

### 10.6 开放式探索与明确终止

研究、搜索和反思任务天然可以继续扩展。编排必须区分：

- 找到足够证据；
- 达到质量阈值；
- 边际收益不足；
- 预算耗尽；
- 真正完成。

---

## 11. 基础评测视角

Agent 编排不能只评测最终答案，还要评测执行过程。

### 11.1 结果质量

- 是否完成用户目标；
- 输出是否正确、完整、可验证；
- 是否保留关键证据和异议；
- 是否产生不允许的副作用。

### 11.2 路径质量

- 是否选择了正确的 Agent 或工具；
- 是否存在无效步骤；
- 是否发生循环；
- 是否遗漏必要步骤；
- 是否进行了不必要的 handoff；
- 是否正确触发人工介入。

### 11.3 系统质量

- 延迟；
- Token 与调用成本；
- 并行收益；
- 恢复成功率；
- 重复执行率；
- 状态冲突率；
- 超时与重试分布。

### 11.4 可解释性

应能够回答：

- 谁在什么时候做了什么；
- 它基于哪些输入和观察；
- 为什么发生路由或 handoff；
- 哪些规则批准了副作用；
- 最终结果使用了哪些中间产物；
- 任务为什么结束。

## 12. 常见认知陷阱

### 12.1 把 Multi-Agent 当成复杂任务的默认答案

复杂任务首先应该考虑任务分解、工具设计和状态建模，而不是直接增加 Agent 数量。

### 12.2 把角色 Prompt 当成编排架构

“你是规划者”“你是评审者”只定义角色，不定义任务状态、控制权、失败语义和终止条件。

### 12.3 把自然语言聊天记录当成共享状态

消息历史不等于结构化任务状态。仅依赖聊天记录会让恢复、并发、验证和审计变得困难。

### 12.4 把所有动态决策都交给 LLM

权限、预算、状态合法性、幂等和高风险副作用需要确定性校验。

### 12.5 把所有流程都写成固定 DAG

固定 DAG 适合稳定流程，但不能自然处理运行时才出现的新子任务和未知环境反馈。

### 12.6 只设计正常路径

可靠编排必须设计：

- 工具失败；
- Worker 超时；
- 结果不完整；
- 多方冲突；
- Agent 无法继续；
- 部分副作用已发生；
- 人工长时间未响应；
- 服务重启。

### 12.7 只评测最终回答

相同最终答案可能由完全不同的路径产生。路径中的越权、重复调用和不可恢复副作用不能被最终文本质量掩盖。

### 12.8 没有明确终止条件

“继续思考直到完成”不是可执行的终止策略。开放式任务必须受到质量、次数、时间、成本或人工判断约束。

## 13. 后续知识深入顺序

建议按以下顺序逐一深入：

1. **决策权与控制边界（已深入）**
   - `Observe → Propose → Validate → Authorize → Execute → Verify → Commit`；
   - 语义、规则、规范与环境四类权威；
   - 九类决策权；
   - 任务所有权与权限分离；
   - Human-in-the-loop 一等主体；
   - 权限衰减、Capability 与受限自治。

2. **安全防控（已深入）**
   - 风险对象与八个风险维度；
   - 静态基线、动态修正、硬规则升级；
   - R0–R5；
   - 六类安全 Gate；
   - 审批快照与执行前重新验证；
   - Prompt Injection、纵深防御、审计与安全评测。

3. **三平面模型（已深入）**
   - Control、State & Context、Execution 三类逻辑职责；
   - `State → Decision → Command → Execution → Observation → Commit`；
   - State 与 Context Projection；
   - 与传统 Control Plane / Data Plane 的异同；
   - 职责边界与部署边界；
   - 跨平面结构化契约；
   - 安全、可观测性与评测横切三个平面。

4. **编排模式**
   - Sequential；
   - Routing；
   - Parallelization；
   - Orchestrator–Workers；
   - Handoff；
   - Evaluator–Optimizer；
   - Group Chat；
   - 模式组合和选择方法。

5. **任务、状态与所有权**
   - Goal、Task、Attempt、Artifact；
   - 状态机；
   - 动态任务图；
   - 单写者与所有权转移。

6. **上下文工程与通信**
   - 共享上下文与私有上下文；
   - 上下文投影；
   - 消息、事件与产物；
   - Handoff 输入过滤；
   - 跨 Agent 证据保真。

7. **结果聚合与冲突解决**
   - 拼接、归约、投票、排名、裁决；
   - 少数意见；
   - 证据独立性；
   - 聚合失败。

8. **运行时可靠性**
   - 幂等；
   - 重试与回退；
   - 超时；
   - 检查点；
   - 暂停恢复；
   - 补偿；
   - 长运行任务。

9. **Human-in-the-loop 与治理**
   - 审批；
   - 澄清；
   - 接管；
   - 权限；
   - 安全边界；
   - 审计。

10. **可观测性与评测**
   - Trace；
   - 路径评测；
   - 状态转换评测；
   - 故障归因；
   - 成本与质量联合评测。

## 14. 当前阶段结论

1. Agent Orchestration 是对 Agentic System 执行过程的控制，不是 Multi-Agent 的同义词。
2. 单 Agent Loop、确定性工作流、动态 Agent 和 Multi-Agent 都属于编排知识范围。
3. 编排的关键对象是 Goal、Task、Actor、State 和 Policy。
4. 决策权是一条从观察到提交的权力链，应按动作和阶段分配，而不是全局选择“代码”或“LLM”。
5. LLM 负责语义提议，代码与策略维护硬约束，人负责规范性判断，环境提供外部事实。
6. Human-in-the-loop 是一等决策主体，不是 Agent 失败后的异常兜底。
7. 任务所有权不等于权限；拥有任务不意味着拥有所有动作的授权、执行和提交权。
8. 委派与 Handoff 默认权限衰减，子 Agent 只获得当前子任务所需的权限子集。
9. 混合编排适合作为生产系统基础：确定性控制外壳包裹 LLM 自适应核心。
10. 安全是贯穿目标、委派、上下文、执行、提交和终止的控制体系。
11. 风险属于具体动作实例，应使用“静态基线 + 动态修正 + 硬规则升级”。
12. 审批必须绑定具体动作快照，审批后执行前重新验证，执行后核验外部事实。
13. Scope、Delegation、Action、Result、Commit、Convergence 是六类关键安全 Gate。
14. 控制平面、状态与上下文平面、执行平面是职责边界，不是固定组件或部署边界。
15. 编排模式只是表层拓扑；状态、所有权、失败恢复和终止才是可靠性的核心。
16. Multi-Agent 只有在上下文隔离、能力与权限边界、真实并行或独立评估能够带来可验证收益时才值得引入。
17. 编排评测必须同时覆盖最终结果、执行路径、系统质量、安全和可解释性。
18. 下一阶段进入具体编排模式，先讨论 Sequential 与 Routing。
