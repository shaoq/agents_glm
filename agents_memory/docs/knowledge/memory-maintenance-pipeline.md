## 0. 核心定位

### 0.1 Maintenance 是记忆系统的生命周期控制面

Maintenance 不是一个“定时降低 importance 的清理任务”，也不只是遗忘与 Reflection 的简单组合。

它负责持续回答：

1. 记忆库当前存在哪些健康问题？
2. 哪些记忆仍值得保留、需要降级、应被重新验证或可以清除？
3. 哪些重复、碎片和历史版本需要重新组织？
4. 原始证据变化后，依赖它们的派生记忆是否仍然成立？
5. 生命周期变化如何安全传播到关系、派生知识和语义索引？
6. 维护失败、并发修改或部分执行后，系统如何恢复一致状态？

整体关系可以概括为：

```text
Write
  └─ 产生、修正和持久化记忆

Recall
  └─ 面向当前任务选择和组织证据

Reflection
  └─ 从多条证据形成新的派生认知

Maintenance
  └─ 持续诊断记忆库
       → 制定维护动作
       → 执行生命周期转换
       → 传播依赖变化
       → 维护真相源与派生索引一致性
```

Maintenance 因此更像记忆系统的**控制面**：

- Write、Recall 是主要在线数据路径；
- Reflection 是受控的认知生成子管线；
- Maintenance 在后台观察并调整长期状态。

### 0.2 为什么需要 Maintenance

如果长期记忆只写不维护，会逐渐出现：

- 记忆数量持续增长，低价值候选淹没有效信号；
- 旧版本、重复内容和碎片信息占用检索预算；
- 已经过时、被纠正或失去证据支持的内容继续参与 Recall；
- Reflection 等派生认知在来源变化后仍被当作有效结论；
- SQLite 与 Chroma 发生索引遗漏、索引滞留或状态漂移；
- 删除只作用于某一份数据，关系、索引或派生内容仍保留；
- 维护策略把“经常出现”误当成“真实”或“重要”，形成错误强化。

Maintenance 的价值不是单纯减少记录数量，而是维持长期记忆的：

- **有效性**：当前可用状态与时间语义准确；
- **价值密度**：有限召回预算中高价值信息占比更高；
- **结构质量**：重复、碎片、版本和依赖关系清晰；
- **可追溯性**：压缩、派生和失效过程可解释；
- **一致性**：真相源、关系和派生索引能够收敛；
- **可治理性**：明确保留、归档、过期和清除边界。

### 0.3 Maintenance 的基本闭环

维护不是“扫描后立即修改”，而是诊断、决策和执行分离的闭环：

```text
[触发]
   ↓
[构建维护工作集]
   ↓
[健康诊断]
   ↓
[维护策略判断]
   ↓
[形成动作计划]
   ↓
[约束与依赖验证]
   ↓
[执行生命周期转换]
   ↓
[传播关系与派生影响]
   ↓
[同步索引 / 审计 / 重试]
```

其中：

- 诊断回答“可能存在什么问题”；
- 策略回答“在当前目标下应该如何处理”；
- 动作计划回答“需要改变哪些对象及依赖”；
- 执行负责幂等地完成状态变化；
- 传播负责避免源记忆变化后留下失真的派生结果。

## 1. 必须修正的几个基础认知

### 1.1 遗忘不等于单纯降权

“遗忘不是删除，是降权”只能描述一种较温和的遗忘方式，不能作为普遍定义。

更准确地说，遗忘是**受控地降低记忆可访问性或保留等级**，可能经过多级状态：

```text
正常可用
  → 降低召回优先级
  → 冷却
  → 归档
  → 过期
  → 满足条件后清除
```

不同动作的语义并不相同：

| 动作 | 核心含义 | 是否仍可恢复或审计 |
|---|---|---|
| 降权 | 仍然有效，但默认召回优先级降低 | 是 |
| 冷却 | 暂时退出普通热路径 | 是 |
| 归档 | 保留历史或审计价值，不参与普通当前召回 | 是 |
| 过期 | 生命周期条件已结束 | 取决于策略 |
| 清除 | 从受管存储和派生表示中移除 | 通常否或仅保留最小审计信息 |

显式删除、隐私删除、非法数据清除和错误数据清除不能只通过降权实现。

### 1.2 失效、遗忘、删除不是同一件事

- **失效**回答“这条知识现在是否仍然成立或可用于当前任务”；
- **遗忘**回答“系统还应以多高可访问性保留它”；
- **删除**回答“系统是否还允许保存它”。

一条记忆可以：

- 已失效但仍需保留历史；
- 当前有效但因低任务价值进入冷存储；
- 很重要但因用户明确删除而必须清除；
- 已归档但在历史查询或内部维护中仍可使用。

因此不能用一个 `importance` 或一个 `active` 布尔值同时表达所有生命周期语义。

### 1.3 不应直接让原始 importance 随时间衰减

需要区分至少四类信号：

| 信号 | 回答的问题 | 稳定性 |
|---|---|---|
| `intrinsic_importance` | 这条内容本身有多重要？ | 相对稳定 |
| `recall_utility` | 它对当前查询有多大帮助？ | 每次查询动态变化 |
| `retention_score` | 它现在还值得以什么等级保留？ | 由 Maintenance 周期计算 |
| `access_signal` | 最近是否被有效使用？ | 随时间变化 |

如果直接修改原始 importance：

- 一条重要但长期没有被问到的事实可能被错误贬值；
- 高频召回的错误或噪声记忆可能得到错误强化；
- 无法区分“内容不重要”和“近期没有使用”；
- Recall 与 Maintenance 会争夺同一个字段的语义。

更合理的知识模型是保留相对稳定的内容属性，再根据时间、使用、有效性和依赖状态计算维护决策。

### 1.4 使用频率不是真实性证据

访问次数、最近访问时间和 Recall 命中可以说明“这条记忆经常有用”，但不能说明：

- 内容一定正确；
- 当前仍然有效；
- 用户希望继续保存；
- 它比反证更可信；
- 它应覆盖新的事实版本。

错误记忆越常被召回，越可能形成正反馈。因此使用信号只能参与保留价值和缓存层级判断，不能替代真实性验证。

### 1.5 Reflection 不是 Maintenance 的全部认知处理

Reflection 是 Maintenance 的一个独立子领域，负责从证据形成新的高阶认知；Maintenance 还负责：

- 是否触发 Reflection；
- 哪些范围值得反思；
- 反思结果如何进入生命周期；
- 来源变化后是否需要重新验证；
- 反思结果应降级、归档还是失效；
- 删除传播是否影响派生认知。

Reflection 的综合与验证过程在独立文档中讨论，Maintenance 文档不重复展开。

## 2. 生命周期的多维状态模型

### 2.1 为什么不能只有一个生命周期枚举

记忆生命周期不能简化为：

```text
ACTIVE → ARCHIVED → DELETED
```

原因是“是否仍然成立”“如何参与 Recall”“是否继续存储”是三个不同问题。

如果压入一个状态字段，就无法准确回答：

- `ARCHIVED` 是不再成立，还是只退出普通召回？
- `EXPIRED` 是事实为假，还是 Session 生命周期结束？
- `DELETED` 是收到删除指令、等待传播，还是已经完成物理清除？
- `SUPERSEDED` 的历史事实是否仍可用于时点查询？

一条记忆至少同时具有三个正交维度：

```text
                 一条记忆
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   知识有效性     服务可访问性     保留状态
   是否仍成立     如何参与 Recall   是否继续存储
```

### 2.2 知识有效性

知识有效性描述记忆在其时间和作用域内能否作为知识使用。

| 状态 | 含义 |
|---|---|
| `ACTIVE` | 在适用时间和作用域内仍可作为有效知识 |
| `SUPERSEDED` | 曾经有效，但已经被后续状态取代 |
| `RETRACTED` | 内容被确认错误或被明确纠正 |
| `DISPUTED` | 存在重要反证，当前无法可靠裁决 |
| `UNVERIFIED` | 来源或依赖不足，尚未达到稳定知识状态 |

其中：

- `SUPERSEDED` 仍可能是真实历史；
- `RETRACTED` 不应继续作为事实使用；
- `DISPUTED` 需要保留相互冲突的证据边界；
- `UNVERIFIED` 表示支持不足，不等于已经证伪。

当前存储模型已经具有 `ACTIVE / SUPERSEDED / RETRACTED`。`DISPUTED` 和 `UNVERIFIED` 首先是知识模型；是否成为新的持久化枚举，应在后续实施设计中结合现有关系和 Pending 语义决定。

以下信号不能单独改变知识有效性：

- 长时间没有被访问；
- importance 较低；
- 内容较旧；
- 向量相似度较低；
- Session 已结束；
- 存储空间不足。

有效性只能由新证据、明确关系、来源变化或受控纠错改变。

### 2.3 服务可访问性

服务可访问性描述记忆如何参与在线 Recall：

```text
HOT ⇄ WARM ⇄ COLD ⇄ ARCHIVED
```

| 层级 | 普通 Recall 行为 |
|---|---|
| `HOT` | 进入高频候选路径，适合近期任务连续性 |
| `WARM` | 作为普通长期记忆参与召回 |
| `COLD` | 只在高相关性、扩展检索或普通结果不足时参与 |
| `ARCHIVED` | 默认退出当前态 Recall，只用于历史、审计、维护或显式完整历史 |

可访问性不表达真实性：

- Hot 记忆不一定比 Cold 记忆更正确；
- Archived 记忆不一定为假；
- 新的有效使用可以使 Cold 记忆重新升温；
- 历史查询可以临时访问 Archived 记忆，但不必永久改变其层级。

例如用户已经从北京搬到上海：

```text
“用户 2024 年居住在北京”

validity    = SUPERSEDED
access_tier = ARCHIVED
```

它不再代表当前状态，但仍是合法历史证据。

### 2.4 保留状态

保留状态回答系统是否继续保存这条记忆：

| 状态 | 含义 |
|---|---|
| `RETAIN` | 按当前策略继续保留 |
| `REVIEW_DUE` | 达到维护条件，需要重新评估 |
| `EXPIRY_ELIGIBLE` | 满足过期候选条件，但尚未清除 |
| `PURGE_PENDING` | 已确认需要清除，等待依赖传播和存储执行 |
| `PURGED` | 已从受管存储和派生表示中清除 |
| `HOLD` | 因依赖、审计或其他明确约束暂时禁止清除 |

`EXPIRY_ELIGIBLE` 与 `PURGE_PENDING` 必须分开。

满足 TTL 只能使记忆成为过期候选。进入清除前还应检查：

- 是否是其他记忆的来源；
- 是否位于版本链或事件链中；
- 是否参与 Summary、Consolidation 或 Reflection；
- 是否需要保留历史或最小审计信息；
- 是否存在并发 Write、Recall 或删除；
- 是否受到显式保留约束。

### 2.5 三个维度的合理组合

| 有效性 | 可访问性 | 保留状态 | 语义 |
|---|---|---|---|
| `ACTIVE` | `HOT` | `RETAIN` | 当前高频有效记忆 |
| `ACTIVE` | `COLD` | `RETAIN` | 真实但长期少用 |
| `SUPERSEDED` | `ARCHIVED` | `RETAIN` | 合法历史版本 |
| `RETRACTED` | `ARCHIVED` | `RETAIN` | 保留纠错审计，不可作为事实 |
| `DISPUTED` | `WARM` | `REVIEW_DUE` | 存在冲突，等待新证据 |
| `ACTIVE` | `ARCHIVED` | `EXPIRY_ELIGIBLE` | 未被证伪，但生命周期已结束 |
| 任意非清除状态 | 任意层级 | `PURGE_PENDING` | 已进入明确清除流程 |

这说明：

- 归档不等于失效；
- 失效不等于清除；
- 低访问性不等于低真实性；
- 当前不可召回不等于没有历史价值。

### 2.6 三条状态路径

#### 有效性路径

```text
                     ┌───────────────┐
                     ▼               │ 新证据解决争议
ACTIVE ───────────→ DISPUTED ────────┘
  │                    │
  │ 状态自然变化       │ 被证伪
  ▼                    ▼
SUPERSEDED         RETRACTED
```

时间流逝本身不能推动 `ACTIVE → RETRACTED`。

#### 可访问性路径

```text
HOT ⇄ WARM ⇄ COLD ⇄ ARCHIVED
```

这条路径通常可逆。新的任务价值、有效使用或主题重新激活都可能使记忆升温。

#### 保留路径

```text
RETAIN
  → REVIEW_DUE
  → EXPIRY_ELIGIBLE
  → PURGE_PENDING
  → PURGED
```

在 `PURGED` 前通常允许因为依赖、审计、用户行为或策略变化取消清除。进入 `PURGED` 后不能假设仍可恢复。

### 2.7 生命周期动作的优先级

多个信号同时出现时，应按语义优先级处理：

```text
1. 明确删除或强制保留约束
2. 用户和作用域边界
3. 知识有效性及证据变化
4. 派生依赖完整性
5. 生命周期过期条件
6. 保留价值和访问层级优化
7. 存储成本优化
```

例如：

- 用户明确删除时，importance 再高也不能阻止清除；
- 来源被纠正时，访问频率再高也不能维持其当前事实身份；
- 低使用记忆如果是 Reflection 的唯一来源，不能直接清除；
- 存储压力不能成为破坏证据链的理由。

### 2.8 自动动作的证据门槛

动作越不可逆，所需证据门槛越高：

```text
低门槛、可逆
DEMOTE / COOL
        ↓
中等门槛
ARCHIVE / EXPIRE
        ↓
需要语义和依赖验证
CONSOLIDATE / INVALIDATE
        ↓
最高门槛、通常不可逆
PURGE
```

Maintenance 可以积极执行可逆优化，但应保守执行知识改变和物理清除。

### 2.9 生命周期转换必须可解释

每个非平凡转换都应能回答：

- 处理了哪条记忆或哪个集合？
- 原来处于什么状态？
- 转换成什么状态？
- 由什么信号触发？
- 使用了哪些证据？
- 哪类策略或明确指令作出决定？
- 决策发生在什么时间？
- 是否可逆？
- 影响了哪些关系和派生记忆？

缺少原因和证据的生命周期转换，会让错误归档、失效或清除无法审计和恢复。

## 3. Maintenance 维护的对象

Maintenance 的最小读取单位可以是一条 `MemoryRecord`，但正确的决策单位通常是一个具有必要关系闭包的维护工作集。

如果逐条扫描、逐条算分、逐条修改，容易出现：

- 删除 Reflection 的唯一证据，却保留 Reflection；
- 归档当前事实，却没有处理版本链的链头；
- 合并内容相似但实际独立的事件；
- 清除原始记忆，但 Summary 仍保留相同内容；
- 只删除 SQLite 记录，却留下 Chroma 索引和关系边。

### 3.1 四类身份必须分开

#### 记录身份

`memory_id` 表示一条具体持久化记录。两条记录即使内容完全相同，也仍有不同记录身份。

#### 事实身份

事实身份表示多条记录是否描述同一事实槽位，概念上由以下信息构成：

```text
主体 + 属性/关系 + 适用作用域 + 时间范围
```

同一事实身份下可以存在多个历史版本。

#### 事件身份

事件身份表示多条记录是否描述同一次现实事件，通常依赖：

- 事件类型；
- 参与者；
- 时间锚点；
- 地点；
- 关键对象；
- 发生次数或序号。

内容相似不表示事件身份相同。

#### 派生产物身份

Summary、Consolidation 和 Reflection 都是新的知识对象。它们依赖原始记忆，但不等于任何一条来源。

记录身份、事实身份、事件身份和派生产物身份不能用向量相似度统一替代。

### 3.2 单条记忆

单条记忆适合处理局部且确定的维护问题：

- Session TTL；
- 单条状态复核；
- 单条索引遗漏；
- 明确删除指令；
- 字段完整性；
- 访问层级调整。

单条记忆不适合独立完成：

- 去重和 Consolidation；
- 事实版本纠错；
- 事件合并；
- Reflection 重评估；
- 冲突消解。

### 3.3 事实版本链

例如用户住址、偏好和项目决策的前后版本。

```text
旧状态 ──SUPERSEDES──> 新状态
旧错误 ──CORRECTS────> 修正事实
```

Maintenance 需要将整条链视为结构对象，判断：

- 是否只有一个当前有效节点；
- 当前链头是否明确；
- 是否存在多个 ACTIVE 节点；
- 修正与自然演化是否被正确区分；
- 是否存在断链、循环或反向关系；
- 旧版本应保留、归档还是清除；
- 下游派生知识依赖整条演化还是某一版本。

旧节点即使不参与当前 Recall，也可能仍然具有：

- 历史状态价值；
- 修正审计价值；
- 演化解释价值；
- Reflection 的时间证据价值。

### 3.4 事件及事件簇

事件簇是一组可能有关联的事件，不表示已经确认是同一事件：

```text
Event Cluster
  ├─ 可能为同一事件的不同描述
  ├─ 同一主题下的多次独立事件
  ├─ 前因后果事件
  ├─ 内容相似但时间不同的事件
  └─ 身份暂时未知的事件
```

合并或压缩前必须先判断：

```text
是否同一事件？
  ├─ 是：考虑重复、补充或纠正
  ├─ 否：保持独立，必要时建立关联
  └─ 未知：DEFER，不执行破坏性合并
```

事件簇用于限定比较范围，不能作为自动合并依据。

### 3.5 重复与 Consolidation 集合

重复诊断需要区分：

- 完全重复；
- 同义重复；
- 正交补充；
- 不同时间版本；
- 相似但独立的事件；
- 互相冲突的事实。

不同关系对应不同处理倾向：

| 关系 | Maintenance 行为倾向 |
|---|---|
| 完全重复 | 保留规范记录，其他记录归档或建立重复关系 |
| 同义重复 | 合并前验证时间、来源和作用域 |
| 正交补充 | 保持原始内容，可能形成组合表示 |
| 历史版本 | 建立版本链，不压缩为单一当前事实 |
| 相似独立事件 | 保持独立 |
| 冲突事实 | 保留双方并进入重评估 |
| 多条碎片 | 可以形成带来源的 Consolidation 产物 |

相似度只负责发现候选集合，不能直接决定 Consolidation。

### 3.6 主题、任务和会话工作集

很多维护问题只能在集合层发现：

- 某一主题积累大量碎片；
- 一个完成任务留下过多过程细节；
- 某一会话记忆达到 TTL；
- 某类信息长期没有进入任何有效 Recall。

主题、任务或会话工作集提供维护范围，不表示其中所有记忆应执行相同动作。

### 3.7 派生知识及来源图

Reflection、Summary、Consolidation 产物都依赖原始证据。

```text
Source A ─┐
Source B ─┼──> Derived Memory
Source C ─┘
```

显式来源关系用于：

- 判断来源变化的影响；
- 判断剩余证据是否充分；
- 区分用户原话和系统推断；
- 重新验证派生结论；
- 解释结论产生时的上下文。

派生关系通常形成有向依赖图：

```text
原始记忆
   ↓
Summary / Consolidation
   ↓
Reflection
   ↓
更高阶策略或画像
```

必须限制派生深度，避免 Reflection 反复基于 Reflection 形成自我强化。

### 3.8 Deferred/Pending 生命周期

维护只处理生命周期和可执行性：

- TTL 是否到期；
- 目标记忆是否仍存在；
- 是否已经被其他流程解决；
- 是否需要归档或清理；
- 重复 Pending 是否可以合并。

没有新证据时，Maintenance 不应反复调用关系模型重新采样。时间流逝本身不是新的事实证据。

### 3.9 存储与索引状态

维护还需要处理运行状态：

- SQLite 有记录、Chroma 缺索引；
- SQLite 已失效、Chroma 仍滞留；
- 删除只完成一侧；
- 索引操作持续失败；
- 关系指向不存在或越权对象；
- 派生记录缺失来源。

这类工作属于运行维护，不等同于知识遗忘，但属于完整 Maintenance 控制面的职责。

### 3.10 三种关系图必须分开

#### 语义关系图

描述知识之间的语义：

```text
SUPERSEDES
CORRECTS
CONFLICTS_WITH
SUPPORTS
RELATED_TO
SAME_EVENT
```

它回答“这些记忆在知识上是什么关系”。

#### 来源依赖图

描述派生产物与证据：

```text
DERIVED_FROM
SUMMARIZES
CONSOLIDATES
REFLECTS_ON
SUPPORTED_BY
COUNTEREVIDENCED_BY
```

它回答“这个结论依赖哪些证据”。

#### 存储投影图

描述同一知识对象在不同存储中的表示：

```text
SQLite MemoryRecord
    ├─ Chroma vector document
    ├─ relation rows
    ├─ source rows
    └─ pending/index operations
```

它回答“一个状态变化需要同步哪些物理表示”。

三种图不能混用：

- Chroma 缺失不表示知识失效；
- `RELATED_TO` 不表示来源依赖；
- `DERIVED_FROM` 不表示两个对象是同一事实；
- 删除向量索引不表示已经删除真相记录。

### 3.11 有界维护工作集

一次 Maintenance 不应处理整个关系图，也不能只处理孤立 seed。

```text
触发种子
   ↓
加载直接结构关系
   ↓
加载必要来源与下游依赖
   ↓
加载有限语义邻居
   ↓
重新验证 user / scope
   ↓
形成不可变维护工作集
```

概念上的工作集包含：

```text
MaintenanceWorkset
  ├─ seeds
  ├─ version_chain
  ├─ event_neighbors
  ├─ duplicate_candidates
  ├─ upstream_sources
  ├─ downstream_derivations
  ├─ storage_projections
  └─ pending_references
```

工作集追求必要闭包，不追求完整图闭包。每种关系需要独立的扩展深度和数量上限。

### 3.12 每次扩展都必须重新验证 Scope

起始记忆合法，不表示所有关系邻居都合法。

```text
合法 seed
  → 关系扩展
  → 逐个验证 user / agent / scope
```

跨用户指向可能来自历史 bug、错误关系或数据损坏。Maintenance 不能处理越权邻居，还应把该关系标记为结构异常。

### 3.13 依赖健康状态

派生知识需要表达来源依赖的健康程度：

| 状态 | 含义 |
|---|---|
| `HEALTHY` | 必要来源存在且仍支持结论 |
| `DEGRADED` | 部分来源失效，但剩余证据可能仍充分 |
| `REVIEW_REQUIRED` | 来源发生关键变化，需要重新验证 |
| `ORPHANED` | 必要来源全部丢失或无法追溯 |
| `CONTRADICTED` | 新反证直接挑战派生结论 |
| `INVALID` | 已确认不能继续使用 |

依赖健康与派生记忆自身有效性相关，但不是同一个概念。

例如五条来源中一条被删除：

- 不能默认 Reflection 继续有效；
- 也不能立即删除 Reflection；
- 应判断其余来源是否仍然充分；
- 如果删除来源包含不可继续保留的信息，还要判断派生结果是否重现该信息。

### 3.14 来源变化传播

| 源记忆变化 | 下游派生知识的默认处理 |
|---|---|
| `DEMOTE` | 通常不改变下游有效性 |
| `COOL` | 不改变下游有效性 |
| `ARCHIVE` | 保留依赖，必要时调整下游访问层级 |
| `SUPERSEDED` | 判断下游依赖的是旧时点还是当前状态 |
| `RETRACTED` | 下游进入 `REVIEW_REQUIRED`，必要时失效 |
| `DISPUTED` | 降低依赖健康并检查是否遗漏反证 |
| `CONSOLIDATE` | 重连到新表示，同时保留原始溯源 |
| `PURGE_PENDING` | 清除前计算受影响下游闭包 |
| `PURGED` | 移除来源引用，重评估或清除无法合法保留的派生物 |
| `REPAIR_INDEX` | 不传播知识有效性变化 |

来源变化不能简单级联删除，需要同时考虑：

- 剩余证据充分性；
- 内容依赖程度；
- 时间视角；
- 删除原因；
- 派生内容是否重现被删除信息；
- 是否还有合法独立来源。

### 3.15 Consolidation 后的来源重连

假设：

```text
A、B、C → Consolidated D
```

不能直接删除 A、B、C，只留下 D。更合理的知识过程是：

1. 创建 D，并标明派生身份；
2. 建立 D 到 A/B/C 的来源关系；
3. 验证 D 是否保留时间、否定、来源和冲突；
4. 将 A/B/C 调整为 Cold 或 Archived；
5. 观察 D 是否真正改善 Recall；
6. 满足独立清除条件后，再评估原始记录。

这样在 D 压缩错误时仍能回到原始证据。

### 3.16 循环依赖

派生图应尽量保持有向无环。危险结构包括：

```text
Reflection A → 支持 Reflection B
Reflection B → 支持 Reflection A
```

它会造成：

- 结论自我证明；
- 删除和失效传播无法终止；
- 依赖数量虚高；
- 没有原始证据仍显示多个来源支持。

Maintenance 需要识别自环、派生环、无原始证据支持闭环和超过允许深度的 Reflection 链。循环中的节点不能互相恢复有效性，应进入 `REVIEW_REQUIRED`。

### 3.17 动作与目标粒度

| 动作 | 合适的目标粒度 |
|---|---|
| `DEMOTE / COOL` | 单条记忆或主题工作集 |
| `ARCHIVE` | 单条记忆、Session 或版本链历史节点 |
| `EXPIRE` | 具有明确生命周期的记录或工作集 |
| `REVALIDATE` | 事实槽位、事件簇或派生依赖子图 |
| `CONSOLIDATE` | 重复集合、碎片集合或版本结构 |
| `INVALIDATE` | 具体事实版本或派生结论 |
| `PURGE` | 记忆、存储投影和受影响依赖闭包 |
| `REPAIR_INDEX` | 单条投影或有界索引批次 |

粒度选择错误会导致：

- 对单条记录执行 Consolidation；
- 对整个主题执行高风险 Purge；
- 对整个版本链统一 Retract，抹掉真实历史；
- 对 Chroma 投影执行 Invalidate，混淆知识与索引状态。

## 4. Maintenance 的主要子领域

现阶段不再使用简单的“遗忘 + Reflection”两分法，而采用以下知识地图：

### 4.1 调度与工作集管理

#### 4.1.1 Trigger、Scheduler 与 Workset Builder

三个概念必须严格分开：

```text
Trigger
发现“可能值得检查”

Scheduler
决定“何时、以什么优先级检查”

Workset Builder
决定“本次必须一起查看哪些对象”
```

Trigger 只产生检查理由，不是维护结论，更不能直接执行状态变化。

例如“90 天未访问”只能触发 retention 检查，不能直接得出“应该删除”。

#### 4.1.2 增量维护与周期 Reconciliation

单纯定时全库扫描会导致：

- 成本随记忆规模线性增长；
- 未变化记录被重复检查；
- 删除、纠正和来源失效处理不及时；
- 缺少版本链和依赖上下文；
- 高频用户占用大量资源；
- 语义判断成本和输出漂移持续扩大。

推荐的知识模型是：

```text
事件驱动的增量维护
        +
周期性的有界 Reconciliation
```

- 增量维护负责及时响应实际变化；
- Reconciliation 负责发现丢失事件、历史异常、孤儿依赖和长期累积问题。

Reconciliation 是完整性兜底，不应成为所有语义维护的主路径。

#### 4.1.3 Trigger 的表达

Trigger 应表达：

- 哪个对象可能存在问题；
- 为什么值得检查；
- 初始诊断目的；
- 触发时间；
- 初始优先级；
- 已知变化证据；
- 事件来源。

正确表达：

```text
reason = SOURCE_RETRACTED
target = reflection_123
suggested_check = DEPENDENCY_REVALIDATION
```

错误表达：

```text
source 被撤回
→ 立即删除 reflection_123
```

派生结论可能仍有其他独立来源，必须先重评估。

#### 4.1.4 数据变化 Trigger

来自 Write 或受控状态变化：

- 新记忆写入；
- 事实被取代；
- 旧内容被纠正；
- 来源被撤回；
- 关系链发生变化；
- 新反证进入系统；
- Consolidation 或 Reflection 产物创建。

例如：

```text
源事实 RETRACTED
→ 触发下游派生知识重评估

新事实 SUPERSEDES 旧事实
→ 触发版本链健康检查
```

#### 4.1.5 生命周期 Trigger

来自时间或作用域结束：

- Session 结束；
- 临时任务结束；
- TTL 到期；
- 项目阶段关闭；
- 记忆达到复核周期；
- Pending/Deferred 到达生命周期节点。

时间只触发检查：

```text
TTL 到期
→ EXPIRY_REVIEW
```

而不是直接：

```text
TTL 到期
→ RETRACTED
```

#### 4.1.6 Recall 反馈 Trigger

Recall 可能发现：

- 同一事实槽位反复冲突；
- 当前查询经常依赖历史版本；
- 某些候选多次被判定为高冗余；
- 版本链无法解释；
- Chroma 候选在 SQLite 中大量失效；
- 高价值记忆长期缺少索引；
- 派生结论反复被反证覆盖。

这些可以成为 Maintenance 信号，但 Recall 不直接改变持久状态。

当前 Recall 设计保持主路径只读，不自动更新访问次数。因此 Maintenance 不能把“没有 access_count”理解成“从未使用”。

未来如果记录使用反馈，需要区分：

- 被候选生成命中；
- 进入最终证据集；
- 被模型实际引用；
- 对回答产生正向贡献；
- 仅因冲突完整性而被保留。

这些信号的维护价值并不相同。

#### 4.1.7 运行一致性 Trigger

来自存储与索引：

- SQLite ACTIVE、Chroma 缺失；
- SQLite 已失效、Chroma 滞留；
- 索引操作持续失败；
- 删除只完成一侧；
- 关系目标不存在；
- 派生记录缺少来源；
- 检测到跨用户关系；
- Schema 或 metadata 不一致。

这些 Trigger 通常进入 `REPAIR_INDEX` 或结构完整性诊断，不进入知识真实性判断。

#### 4.1.8 显式与管理 Trigger

包括：

- 用户明确删除或保留；
- Agent 或应用明确请求归档；
- 系统迁移；
- 人工审计；
- 主动启动 Reflection；
- 运维请求重建索引。

显式删除属于高优先级约束，但仍需构建必要依赖工作集，保证删除传播完整。

#### 4.1.9 阈值 Trigger

累计信号也可以触发诊断：

- 某主题的记忆数量超过阈值；
- 一段时间内新增 importance 累计达到阈值；
- 同一事实槽位版本过多；
- 重复候选密度过高；
- Pending 数量持续增加；
- 索引失败率超过阈值；
- 派生结论反证增加；
- Session 或任务达到压缩条件。

阈值只决定何时值得检查，不能证明最终动作。

```text
主题内有 20 条相似记忆
→ 触发 Consolidation 诊断

不等于

保留第一条并删除其余 19 条
```

#### 4.1.10 四种运行模式

| 模式 | 适用问题 | 核心特点 |
|---|---|---|
| 紧急模式 | 明确删除、跨用户引用、严重损坏、关键来源撤回 | 高优先级、快速构建必要闭包 |
| 增量模式 | Write、Recall、Reflection 和索引事件 | 日常主路径，只处理变化 seed 及必要邻居 |
| 批处理模式 | TTL、主题整理、长期 retention、低优先级归档 | 分片、分批、预算与公平性 |
| Reconciliation | 丢失事件、孤儿关系、索引漂移、卡住任务 | 周期兜底和不变量检查 |

紧急模式仍然不能绕过用户边界、证据验证和依赖检查。

#### 4.1.11 维护优先级

维护优先级表示问题的紧急程度和影响范围，不等于 memory importance：

| 优先级 | 典型 Trigger |
|---|---|
| `P0` | 明确删除、跨用户引用、严重一致性破坏 |
| `P1` | 来源撤回、当前事实冲突、关键派生知识失去支持 |
| `P2` | TTL、版本链异常、重复密度、索引遗漏 |
| `P3` | 降权、冷却、长期归档、低价值整理 |

低 importance 的跨用户异常仍然是 P0；高 importance 记忆长期未访问通常仍只是低优先级 retention 检查。

#### 4.1.12 Trigger 合并、防抖与冷却

同一问题可能由多个来源重复触发：

```text
Write 发现关系变化
Recall 发现冲突
周期检查发现版本异常
```

合并时应考虑：

- 相同用户和 Scope；
- 相同目标身份；
- 相同或兼容的诊断目的；
- 相近时间窗口；
- 相同策略版本。

合并后：

- 保留全部 reason；
- 使用最高优先级；
- 合并新增证据；
- 更新最后触发时间；
- 不丢失最早等待时间。

防抖适合短时间连续写入的热门主题；冷却适合刚完成维护后反复出现的相同弱信号。

明确删除、新反证和来源撤回不能被普通冷却压制。

#### 4.1.13 避免 Maintenance 自触发循环

Maintenance 动作也会产生状态变化：

```text
Maintenance 归档记忆
→ 产生状态事件
→ 再次触发 Maintenance
→ 再次判断归档
```

触发事件概念上需要携带：

- `origin`；
- 原始 `cause`；
- `operation_id`；
- `policy_version`；
- 是否属于某维护计划的预期结果。

预期状态变化用于确认动作完成，不重新创建相同诊断。如果只完成 SQLite、Chroma 未同步，则应转为一致性修复 Trigger。

#### 4.1.14 从 Seed 到 Workset

Seed 只是触发起点：

```text
seed = memory_123
reason = SOURCE_RETRACTED
```

Workset Builder 应按诊断目的扩展。

版本链诊断：

```text
seed
→ SUPERSEDES / CORRECTS 前后节点
→ 当前链头
→ 引用该链的派生知识
```

Consolidation 诊断：

```text
seed
→ 同 user/scope/type 的有限语义邻居
→ 时间与事件身份过滤
→ 来源和版本关系
```

派生重评估：

```text
derived seed
→ 直接来源
→ 来源当前状态
→ 必要反证
→ 有限下游派生物
```

Purge 传播：

```text
delete target
→ 存储投影
→ 关系边
→ Pending 引用
→ 直接派生物
→ 可能重现被删内容的下游
```

不同诊断目的使用不同扩展规则，不能采用一个通用的“加载所有邻居”。

#### 4.1.15 结构关系优先于语义邻居

工作集扩展优先级：

```text
1. 存储投影
2. 显式版本和纠错关系
3. 直接来源及下游依赖
4. Pending/Deferred 引用
5. 任务需要时的有限语义邻居
```

前四类是结构上必要的关系，语义邻居只是候选。首先执行向量相似检索，可能扩大到整个热门主题，同时漏掉内容不相似但结构上必须处理的依赖。

#### 4.1.16 Workset 必须有界

需要限制：

- 最大节点数；
- 各关系类型的扩展数量；
- 最大依赖深度；
- 最大语义候选数；
- 最大时间窗口；
- 最大执行时间；
- LLM 诊断预算。

达到上限时必须标记闭包不完整，而不是假装工作集完整：

```text
closure_status = PARTIAL
```

- 可逆动作可以在明确局部范围内执行；
- Consolidation 和 Invalidate 通常等待补充分片；
- Purge 必须先完成必要依赖闭包；
- 超大工作集应拆成有顺序的子工作项。

#### 4.1.17 增量游标与策略版本

周期维护可以使用：

- `updated_at` Watermark；
- 状态变化序号；
- 尚未维护标记；
- 按 user/Scope 分片的游标；
- 上次完整 Reconciliation 时间；
- 失败任务续跑位置。

需要区分：

```text
created_at
updated_at
last_maintained_at
evaluated_policy_version
```

即使记忆内容未变化，维护策略版本变化也可能要求重新诊断。

#### 4.1.18 逻辑快照与最终复核

```text
T1 构建工作集快照
→ 诊断与规划
→ T2 执行前复核关键节点
```

复核：

- seed 是否仍存在；
- validity 是否变化；
- 关系是否新增或移除；
- 是否出现更高优先级删除；
- 依赖闭包是否发生关键变化；
- 是否已被其他维护任务处理。

状态变化时可以有界重建一次，或将任务标记为 stale 后重新排队；不能基于陈旧快照执行不可逆动作。

#### 4.1.19 调度公平性

调度应同时考虑：

- 优先级；
- 等待时间；
- 用户级配额；
- 单主题最大并发；
- 批处理公平性；
- 长期未维护对象的最低保障；
- 轻任务和重任务分离。

否则高活跃用户会持续占用资源，而不活跃用户永远没有事件触发。

#### 4.1.20 Trigger 的重复与丢失

系统不能假设事件恰好到达一次：

- 重复事件通过目标身份、原因、策略版本和 operation ID 合并；
- 丢失事件通过周期 Reconciliation 重新发现状态不变量、孤儿依赖、索引漂移和过期候选。

```text
事件驱动负责及时性
Reconciliation 负责最终完整性
```

#### 4.1.21 从触发到执行的完整边界

```text
Trigger:
“可能存在问题”

Workset:
“理解问题必须一起查看这些对象”

Diagnosis:
“确认问题是什么”

Plan:
“当前证据支持哪些维护动作”

Execution:
“幂等改变状态并传播影响”
```

任何一步都不能跳过：

- Trigger 不能直接 Purge；
- 相似候选工作集不能直接 Consolidate；
- Diagnosis 不能绕过依赖检查执行；
- 执行失败不能伪装成维护成功。

### 4.2 记忆健康诊断

讨论：

- 过期、低价值、重复、碎片、冲突、陈旧和孤儿如何识别；
- 单条信号与集合信号如何结合；
- 确定性诊断与语义诊断如何分工；
- 诊断结论如何表达置信度和证据。

### 4.3 保留与遗忘策略

讨论：

- 保留、降权、冷却、归档、过期和清除的区别；
- fact、event、session、用户长期记忆是否采用不同策略；
- importance、使用、时效和依赖如何共同影响 retention；
- 用户明确删除和系统自动遗忘如何分开。

### 4.4 Consolidation 与结构重组

讨论：

- 何时去重，何时合并，何时只建立关系；
- 摘要替代与原始证据如何共存；
- 版本链、事件簇和主题碎片如何压缩；
- 如何避免压缩丢失否定、时间、来源和冲突。

### 4.5 重新验证与纠错协作

讨论：

- 哪些信号表明记忆可能陈旧或错误；
- Maintenance 能否自行判定，何时必须等待新证据；
- 如何与 Write 的关系判断、Recall 的冲突信号和 Deferred 消解协作；
- 为什么“时间过去了”不能自动成为纠错证据。

### 4.6 Reflection 调度与派生知识维护

讨论：

- 何时值得启动 Reflection；
- 如何避免同一证据反复形成相同洞察；
- 派生结论如何随来源变化重评估；
- 如何限制 Reflection 基于 Reflection 的自我强化。

Reflection 内部的提问、证据召回、洞察综合和验证在独立知识文档中深入。

### 4.7 生命周期执行与依赖传播

讨论：

- 维护动作如何从计划变为受控状态转换；
- 一个源记忆变化后应传播到哪些关系、摘要和 Reflection；
- 如何避免部分传播形成不一致；
- 哪些动作可恢复，哪些动作不可逆。

### 4.8 存储一致性与运行修复

讨论：

- SQLite 与 Chroma 如何检查和修复漂移；
- 如何处理孤儿关系、失败索引操作和删除残留；
- 如何保证维护任务幂等、可重试和可续跑；
- 如何处理 Maintenance 与 Write、Recall 并发。

## 5. Maintenance 动作语义

下面只建立讨论词汇，具体判断条件将在后续主题中深入。

| 动作 | 含义 | 是否改变知识真实性 |
|---|---|---|
| `KEEP` | 保持当前状态 | 否 |
| `RETAIN_HIGH` | 提高保留等级或避免自动遗忘 | 否 |
| `DEMOTE` | 降低普通召回优先级 | 否 |
| `COOL` | 移出高频热路径 | 否 |
| `ARCHIVE` | 保留历史或审计价值，退出普通当前召回 | 通常否 |
| `EXPIRE` | 生命周期条件已结束 | 影响当前可用性 |
| `REVALIDATE` | 因来源、反证或时间变化重新评估 | 尚未决定 |
| `CONSOLIDATE` | 重组重复或碎片记忆并保留来源 | 可能生成派生表示 |
| `INVALIDATE` | 明确标记不再成立或证据不足 | 是 |
| `PURGE` | 按删除语义从受管存储和派生表示清除 | 是且通常不可逆 |
| `REPAIR_INDEX` | 修复真相源与派生索引差异 | 否 |
| `DEFER` | 证据不足，保留待后续处理 | 否 |

需要特别注意：

- `DEMOTE` 不能代替 `INVALIDATE`；
- `ARCHIVE` 不能代替隐私删除；
- `PURGE` 不能由一个低 retention 分数自动触发；
- `CONSOLIDATE` 是知识变换，必须保留来源和可回溯性；
- `REPAIR_INDEX` 修复表示一致性，不改变知识结论。

### 5.1 可访问性动作

- `DEMOTE`：降低普通召回优先级，但保持知识有效性和存储状态；
- `COOL`：移出高频候选路径，主要改变运行层访问成本；
- `ARCHIVE`：退出普通当前态召回，但保留历史、审计、维护或派生价值。

这些动作原则上可逆。它们不能代替 `INVALIDATE`，也不能被解释为内容错误。

### 5.2 有效性动作

- `REVALIDATE`：因新证据、反证、来源变化或异常结构进入重新评估；
- `INVALIDATE`：有足够依据表明原知识不能继续按原结论使用。

`INVALIDATE` 不是单一终态，可能进一步表现为：

- 自然状态变化后的 `SUPERSEDED`；
- 明确错误后的 `RETRACTED`；
- 尚不能裁决的 `DISPUTED`；
- 派生结论失去充分支持后的 `UNVERIFIED`。

低 retention、低访问量和普通时间流逝不能单独触发有效性变化。

### 5.3 知识变换动作

`CONSOLIDATE` 将重复、碎片或版本结构重组为更紧凑的表示：

```text
原始证据集合
   → 形成合并或摘要表示
   → 建立来源关系
   → 验证覆盖、时间和冲突
   → 再决定原始记录的访问层级
```

原始记录通常先归档，而不是立即清除。Consolidation 必须保留来源、时间、否定和不确定性。

### 5.4 清除与运行修复

- `PURGE`：从受管存储、派生索引、关系和下游表示中完成清除；
- `REPAIR_INDEX`：修复 SQLite 与 Chroma 的表示差异，不改变知识结论。

`PURGE` 可能影响：

- SQLite 记录；
- Chroma 索引；
- 关系边；
- Summary、Consolidation 和 Reflection；
- Pending/Deferred 引用；
- 缓存和导出副本。

它是高门槛且通常不可逆的动作，不能由普通低分自动触发。

### 5.5 `DEFER` 的位置

`DEFER` 表示当前证据不足，不执行不可逆维护动作。它是维护决策状态，不是 MemoryRecord 的生命周期状态。

后续重新判断需要新证据、依赖变化或明确事件。对相同输入重复调用关系模型不会产生新的事实依据。

## 6. 与其他管线的职责边界

### 6.1 与 Write

Write 负责当前输入带来的新增、补充、纠正和状态变化。

Maintenance 负责：

- 长期生命周期；
- 跨时间窗口的重复和碎片；
- 来源变化后的下游重评估；
- Pending 生命周期；
- 存储和索引健康。

如果新输入已经明确纠正旧事实，应由 Write 当场处理，不能等待 importance 自然衰减。

### 6.2 与 Recall

Recall 面向当前 Query 组织证据，可以产生：

- 疑似过期信号；
- 冲突信号；
- 无法解释的版本链信号；
- 低价值或高冗余信号；
- 索引异常信号。

这些可以成为 Maintenance 输入，但 Recall 不应偷偷修改持久化状态。

Recall 使用频率可以辅助 retention 判断，但不能证明真实性。

### 6.3 与 Reflection

Reflection 形成新的派生认知；Maintenance：

- 决定何时调度它；
- 控制证据范围和重复触发；
- 管理其产物生命周期；
- 在来源变化后触发重评估或失效传播。

### 6.4 与显式删除

用户删除是明确指令，不是普通的自动遗忘策略。

删除需要考虑：

- SQLite 真相记录；
- Chroma 派生索引；
- 关系边；
- Summary、Consolidation 和 Reflection 等派生内容；
- Pending/Deferred 引用；
- 最小必要审计信息。

维护策略不能因为某条记忆“很重要”而阻止明确删除。

## 7. 关键设计张力

这些问题构成后续深入讨论的主线。

### 7.1 精炼与证据保留

压缩越激进，召回越轻量，但越容易丢失：

- 否定；
- 时间；
- 来源；
- 不确定性；
- 冲突；
- 历史变化。

### 7.2 自动化与误伤

自动维护可以控制规模，但错误的自动归档、合并或清除比暂时保留噪声更难恢复。

因此不同动作需要不同证据门槛和可逆性要求。

### 7.3 使用价值与事实有效性

一条记忆可能：

- 很少使用但仍然真实且重要；
- 经常使用但已经过时；
- 当前不适合 Recall，但具有历史或审计价值；
- 内容真实，但用户已明确要求删除。

不能用一个统一分数替代这些判断。

### 7.4 局部判断与集合结构

单条记忆可能看似低价值，但它可能是：

- Reflection 的关键来源；
- 事件链的必要节点；
- 冲突的反证；
- 修正关系的历史对象；
- 删除传播的依赖节点。

Maintenance 动作前必须检查集合和依赖影响。

### 7.5 在线状态与离线维护并发

Maintenance 运行期间可能同时发生：

- 新记忆写入；
- 旧记忆纠正；
- Recall 正在读取；
- 用户明确删除；
- 索引修复重试。

因此维护不能建立在“扫描后数据不会变化”的假设上。

## 8. 后续深入讨论顺序

建议按以下顺序推进：

1. **Maintenance 定位与生命周期语义**
   深入区分保留、降权、冷却、归档、过期、失效、删除和清除。

2. **维护对象与依赖模型**
   明确单条记忆、版本链、事件簇、主题工作集、派生记忆和索引状态之间的关系。

3. **触发机制与工作集构建**
   讨论定时、事件、阈值、异常触发以及如何避免全库扫描。

4. **健康诊断与维护信号**
   讨论时间、使用、价值、重复、冲突、来源和依赖信号的语义。

5. **保留与遗忘策略**
   针对 fact、event、session 和长期用户记忆建立分层策略。

6. **Consolidation 与摘要替代**
   讨论去重、压缩、来源保留、版本历史和冲突保护。

7. **陈旧、冲突与重新验证**
   明确 Maintenance 可以自动做什么，什么必须依赖新证据或受控写回。

8. **Reflection 调度与派生记忆维护**
   重点讨论来源变化后的重评估和失效传播。

9. **维护动作规划与执行约束**
   讨论证据门槛、动作可逆性、批处理和审计。

10. **幂等、并发及双存储一致性**
    讨论任务续跑、状态漂移、索引修复和删除传播。

安全治理与完整评测可在核心知识链完成后单独启动专项讨论。

## 9. 当前阶段结论

1. Maintenance 是记忆系统的生命周期控制面，不是简单的定时清理。
2. 遗忘是降低可访问性或保留等级的过程，可能包括降权、冷却、归档、过期和清除。
3. 失效、遗忘和删除分别回答知识有效性、保留策略和存储许可，不能混为一谈。
4. 原始 importance、查询期 utility、维护期 retention 和 access signal 必须保持语义分离。
5. 使用频率可以说明使用价值，不能证明真实性。
6. Maintenance 的对象包括单条记忆、版本链、事件簇、重复集合、派生依赖、Pending 生命周期及存储索引状态。
7. Reflection 是独立的派生认知子管线，Maintenance 负责调度和生命周期，不重复承担其内部综合过程。
8. Maintenance 必须先诊断、再规划、后执行，并在动作前验证依赖影响。
9. Recall 可以产生维护信号，但持久状态变化必须经过受控的 Write 或 Maintenance 边界。
10. 记忆生命周期至少需要知识有效性、服务可访问性和保留状态三个正交维度。
11. `ARCHIVED`、`EXPIRED`、`SUPERSEDED`、`RETRACTED` 和 `PURGED` 不能压缩成一个状态。
12. `memory_id`、事实身份、事件身份和派生产物身份必须分开。
13. 语义关系、来源依赖和存储投影是三种不同的关系图。
14. Maintenance 的正确决策单位通常是有界工作集，而不是孤立记录。
15. 来源变化需要按变化类型传播，不能简单级联删除所有派生知识。
16. Trigger 只是检查理由，不能直接决定 Consolidate、Invalidate 或 Purge。
17. 事件驱动增量维护负责及时性，周期 Reconciliation 负责最终完整性。
18. 工作集应优先扩展结构依赖，再按诊断目的补充有限语义邻居。
19. 工作集闭包不完整时，不能执行需要完整依赖影响分析的高风险动作。
20. Maintenance 需要合并重复 Trigger、避免自触发循环，并兼顾调度优先级和跨用户公平性。
