# Agent Memory 知识点：记忆召回管线（Memory Recall Pipeline）

> **文档定位**：本文聚焦 Agent Memory 的**召回管线**——如何根据当前 Agent 状态，从长期记忆中激活一组有效、互补、可信且值得进入工作上下文的历史信息。
>
> **与实现方案的区别**：
> - 本文讨论召回阶段的核心概念、判断依据、难点和知识边界。
> - 不在本文决定具体类、接口、存储引擎、检索组件或 Prompt 实现。
>
> **与 RAG 查询的关系**：
> - RAG 主要从外部文档知识中寻找支持当前问题的内容。
> - Memory Recall 主要从特定主体的历史事实、事件、经验和派生认知中恢复上下文。
> - 两者可共享部分检索思想，但 `agents_memory` 保持独立，不与同级子项目形成代码依赖。

## 0. 核心认知

记忆召回的本质不是“找到与 query 最相似的文本”，而是回答：

> **在当前任务、主体、时间和上下文约束下，哪些过往记忆真正有助于 Agent 正确理解和行动？**

需要把握以下六个核心判断。

### 0.1 Recall 不等于 Vector Retrieval

| 概念 | 核心问题 | 典型产物 |
|---|---|---|
| Retrieval | 哪些记录与查询相似或匹配？ | 候选记录 |
| Recall | 哪些历史信息对当前任务真正有用？ | 记忆证据集合 |
| Reading / Usage | Agent 应如何理解和使用这些记忆？ | 受记忆支持的回答或行动 |

向量检索只是候选生成的一种手段。完整 Recall 还包括召回意图构造、有效性过滤、时间与冲突判断、集合选择、上下文编排和使用反馈。

### 0.2 Recall 的输入不是裸 Query，而是当前 Agent 状态

同一句话在不同任务、项目、主体和时间下需要不同的记忆。召回输入通常同时包含：

- 用户当前表达；
- 当前会话上下文；
- 当前任务或目标；
- 涉及的实体与指代；
- 时间锚点；
- 用户、Agent、项目等作用域；
- 期望召回的记忆类型。

### 0.3 相关性不是可用性的充分条件

一条记忆即使语义高度相关，也可能：

- 已经过时；
- 属于另一个用户或项目；
- 仍处于待决状态；
- 与当前问题的时间范围不匹配；
- 只是低置信度推断；
- 已被后续事实修正；
- 与其他高相关记忆重复。

因此，召回目标应从“相关性”提升为“当前效用”。

### 0.4 三信号是经典基线，不是通用标准

Generative Agents 使用 Recency、Importance、Relevance 三类信号检索记忆，这是重要的研究基线，但不能直接视为所有 Memory 系统的通用标准。

- Relevance：语义上是否相关；
- Recency：距离当前时间是否接近；
- Importance：写入时判断的总体重要程度。

它们没有直接覆盖有效性、作用域、来源可信度、时间适配、冲突状态、集合冗余和下游任务适配等问题，而且不同记忆类型不应机械使用相同权重。

### 0.5 Top-K 不是最终的 Recall 目标

逐条取最高分容易得到大量近义记忆，却遗漏反证、时间线或互补信息。最终目标是形成一个受上下文预算约束的**记忆证据集合**，而不是简单返回若干高分记录。

### 0.6 Memory 是认知证据，不是高优先级指令

召回记忆可能来自用户明确陈述、系统观察、历史事件或模型派生结论，它们的可信度并不相同。

记忆进入上下文时应保留类型、时间、来源和置信度边界，不能因为被召回就自动成为 system 级指令，也不能覆盖用户当前表达或系统安全约束。

## 1. 全景：召回管线的 8 个核心环节

```text
当前 Agent 状态
    ↓
① 召回触发与任务识别
    ↓
② 召回意图构造
    ↓
③ 多路径候选生成
    ↓
④ 资格与有效性过滤
    ↓
⑤ 单条记忆效用评分
    ↓
⑥ 时间、冲突与关系解析
    ↓
⑦ 集合选择与上下文编排
    ↓
⑧ 使用、反馈与评测
```

这八个环节是知识分解，用于明确召回过程中需要解决的不同问题，不代表未来必须拆成八个代码模块。

## 2. 召回触发与任务识别（Recall Trigger & Task Recognition）

> ✅ 已完成首轮深入

召回触发不是简单的“是否调用检索”，而是一次**认知路由判断**：

> 当前任务是否依赖长期记忆？如果依赖，需要恢复哪一种历史知识，服务什么目的？

这个入口决定后续召回方向。触发和任务识别错误时，后续候选生成与排序即使准确，也无法得到正确的记忆集合。

### 2.1 核心问题

这一环节包含三层递进判断：

```text
当前 Agent 状态
    ↓
① 是否需要长期记忆？
    ↓
② 需要完成哪类记忆任务？
    ↓
③ 需要在什么范围和深度内回忆？
    ↓
进入“召回意图构造”
```

#### 第一层：召回必要性

| 判断 | 含义 |
|---|---|
| 不需要 | 当前上下文和通用知识已经足够 |
| 可能需要 | 历史信息可能改善回答，但不是完成任务的前提 |
| 明确需要 | 没有历史记忆就无法正确理解或完成任务 |

例如：

- “Python 怎么读取 JSON？”通常不需要个人记忆。
- “按我习惯的风格写一个示例。”可能需要偏好记忆。
- “继续昨天的 Memory 方案。”明确需要历史任务记忆。
- “我五月份决定用哪个模型？”明确需要历史事件和时间记忆。

“历史信息可能有帮助”和“当前任务依赖历史信息”不是一回事。如果只要可能有帮助就召回，系统会逐渐在每次回答中携带大量无关历史。

#### 第二层：记忆任务识别

知道“需要记忆”还不够，还需要判断要恢复的是稳定事实、偏好、历史事件、当前状态、变化过程、任务进度、历史经验还是多条证据。

不同任务需要的时间范围、记忆类型和证据组织方式不同。

#### 第三层：召回范围判断

任务识别后，还要初步确定：

- 回忆谁或什么实体；
- 属于哪个用户、Agent、项目或任务；
- 回忆当前状态还是历史状态；
- 回忆单一事实还是完整事件链；
- 需要原始记忆还是 Reflection；
- 需要一个答案还是多条证据。

这一步只明确记忆需求及其范围，不生成最终检索 Query。具体的上下文补全和 Query 构造属于 §3“召回意图构造”。

### 2.2 每轮做判断，不等于每轮做检索

每轮交互都隐含着一次“当前是否需要长期记忆”的判断，但判断结果可以是不召回：

```text
每轮都做召回判断
        ≠
每轮都执行记忆检索
```

如果完全没有召回判断，Agent 容易错过隐式历史依赖；如果每轮都直接检索，又会造成过度召回。

Recall Trigger 是当前工作上下文与长期记忆之间的认知门控：

```text
当前工作上下文
      │
      ├── 信息足够 ──────────→ 继续任务
      │
      └── 存在历史信息缺口
                    ↓
              打开长期记忆
```

### 2.3 触发信号

#### 2.3.1 用户显式触发

用户直接要求使用或限制历史记忆：

- “你还记得……吗？”
- “上次我们讨论了什么？”
- “按照我之前的偏好……”
- “回顾一下过去几次失败的原因。”
- “不要使用之前的记忆。”

“不要使用记忆”是一种负向触发：它要求关闭或限制召回，而不是寻找相关记忆。

#### 2.3.2 语言与指代触发

用户没有提到“记忆”，但表达依赖历史上下文：

- “还是按上次的方式。”
- “继续之前那个方案。”
- “他后来改了吗？”
- “之前选的是 A 还是 B？”
- “这次不要再犯同样的问题。”

“上次、之前、后来、最近、一直、还是、继续、同样”等表达经常暗示历史依赖，但它们也可能只指当前会话。这里首先要判断当前工作上下文是否已经足以消解指代。

#### 2.3.3 个性化需求触发

当前任务可能需要用户的：

- 回答风格偏好；
- 技术栈；
- 工作习惯；
- 已知约束；
- 长期目标；
- 明确禁忌或既有选择。

但个性化不能成为无边界的默认目标。可使用一个反事实问题判断其必要性：

> 如果移除这些个性化信息，回答的正确性、适配度或连续性是否会明显下降？

如果不会，召回的实际价值可能很低。

#### 2.3.4 认知缺口与一致性风险触发

Agent 在理解或推理过程中可能发现：

- 当前信息不足；
- 用户表达与已知状态可能冲突；
- 即将陈述用户事实，但缺少历史依据；
- 当前任务可能是历史任务的延续；
- 需要确认某个决策是否发生变化；
- 需要比较当前情况与历史经验。

这种触发可以发生在任务处理过程中，而不一定发生在入口。

#### 2.3.5 内部认知任务触发

召回也可以服务于非回答任务：

- Reflection 召回支持证据和反证；
- Maintenance 重新验证派生记忆；
- DEFER 消解寻找后续上下文；
- 任务规划寻找历史经验；
- 行动前检查用户约束或过去失败记录。

内部召回的目的和信任边界与面向回答的召回不同，其结果不应自动暴露给用户。

### 2.4 召回的触发时机

Recall 不一定是收到 Query 后执行的一次固定预处理。一个任务中可能出现多种触发时机。

| 时机 | 说明 |
|---|---|
| 初始召回 | 理解用户请求后发现任务明显依赖历史信息 |
| 推理中召回 | 处理过程中发现实体、决策或事实缺口 |
| 验证性召回 | 在陈述用户事实前，召回历史证据进行确认 |
| 行动前召回 | 执行持续性动作前，检查历史约束或失败经验 |
| 离线召回 | Reflection、Maintenance、DEFER 消解等内部过程寻找证据 |

因此，更准确的认识是：

> Recall 是可在认知过程中按需发生的能力，而不只是请求入口的一次检索。

### 2.5 常见召回任务

#### 2.5.1 稳定事实恢复

恢复用户或项目跨时间相对稳定的属性。主要依赖 fact，但仍需确认其作用域和有效状态。

#### 2.5.2 偏好适配

恢复表达、工具和工作方式偏好。历史偏好不能覆盖用户当前明确要求，单次选择也不应被直接视为长期偏好。

#### 2.5.3 历史事件回顾

回答某件事何时发生、发生了什么。主要关注 event、时间锚点和来源，而不是只返回最新记忆。

#### 2.5.4 任务延续

恢复未完成任务、已确认决策、进度和下一步：

```text
目标 + 已完成事项 + 已确认决策 + 未完成事项
```

单条事实通常不足以恢复完整任务状态。

#### 2.5.5 当前状态恢复

回答“现在是什么状态”。这里需要当前有效事实，但最新写入的记忆不一定对应最新发生或最新生效的事实。

#### 2.5.6 时间变化与知识更新

判断事实如何从 A 变化成 B。它通常需要多个时间点，不能只取最新一条或最高分记录。

#### 2.5.7 历史经验迁移

根据过往成功或失败经验辅助当前行动。需要判断当前情境与历史情境是否相似，不能把“曾经发生过”直接推导为“现在应该这样做”。

#### 2.5.8 多记忆综合

答案分散在多个会话或事件中，需要跨记忆推理。这类任务往往需要互补证据，而不是单个高相关结果。

#### 2.5.9 Reflection 证据召回

目标不是直接回答用户，而是为派生认知寻找支持证据、反证、不同时间的样本和足够的事件多样性。

#### 2.5.10 证据不足与拒绝推断

召回也可以得到“不足以形成结论”的有效结果。触发 Recall 不代表记忆库一定具有充分证据。

例如，只有一次使用函数式写法，通常不足以支持“用户一直偏好函数式编程”。

### 2.6 召回范围的六个维度

这里描述的是知识边界，不是具体数据结构。

| 维度 | 核心问题 |
|---|---|
| Purpose | 为什么需要回忆？ |
| Subject | 回忆谁或什么实体？ |
| Scope | 属于哪个用户、项目、任务或会话？ |
| Time | 当前、历史某时、最近一次还是变化过程？ |
| Memory Type | fact、event、reflection，还是多类组合？ |
| Depth | 单点事实、多个证据还是完整时间线？ |

例如，“我们之前为什么不用方案 B？”包含的记忆需求是：

```text
目的：解释历史决策
主体：当前项目
时间：做出方案选择的阶段
类型：决策事件 + 约束事实
深度：决策结论及其关键依据
```

它与简单搜索“方案 B”存在本质差异。

### 2.7 典型触发模式

以下是知识上的策略谱系，不是 `agents_memory` 的方案选择。

| 模式 | 特点 | 主要优点 | 主要风险 |
|---|---|---|---|
| 每轮自动召回 | 所有交互都搜索记忆 | 不易漏掉明显记忆 | 噪音、成本、隐私和错误影响高 |
| 显式或规则触发 | 出现明确历史信号才召回 | 可预测、克制 | 隐式需求容易漏召回 |
| Agent 自主触发 | 模型判断何时需要记忆 | 能处理复杂语境 | 判断不稳定，可能过度自信 |
| 分层触发 | 先判断必要性，遇到缺口再扩大 | 平衡漏召回与过度召回 | 认知链更复杂 |

不存在适用于所有场景的唯一模式。关键在于明确历史任务不漏、普通任务不滥用、推理中发现缺口时允许补召回，并尊重用户对记忆使用的限制。

### 2.8 核心难点

#### 2.8.1 当前上下文与长期记忆边界不清

“刚才说的方案”可能属于当前会话，“上个月的方案”通常属于长期记忆。两者混淆会造成无效检索或漏召回。

#### 2.8.2 把个性化当成默认目标

系统知道用户偏好简洁，不代表每个任务都必须召回并应用该偏好。当前任务目标可能比历史偏好更重要。

#### 2.8.3 隐式历史依赖没有被发现

用户省略主体或项目时，Agent 可能错误地使用常识补全，而不是恢复真正的历史上下文。

#### 2.8.4 当前态与历史态任务混淆

“现在使用什么”和“之前使用什么”可能匹配相同记忆，但要求完全不同的时间范围。

#### 2.8.5 把无结果当成无记忆

候选为空可能表示：

```text
确实没有相关记忆
或 写入阶段没有保存
或 召回意图构造错误
或 时间 / 类型范围错误
或 有效性过滤过严
```

“没有召回结果”不能直接解释为“系统确定从未发生”。

#### 2.8.6 召回后产生虚假确定性

触发阶段只判断需要历史信息，不保证记忆库能够提供充分、可信的证据。Recall 必须允许最终得到“证据不足”。

### 2.9 评测与诊断

这一阶段不能只使用后续检索命中率衡量。

| 评测维度 | 核心问题 |
|---|---|
| 召回必要性准确率 | 需要长期记忆时是否打开了 Recall？ |
| 漏触发率 | 回答依赖历史但没有触发召回的比例 |
| 过度触发率 | 无需历史信息却执行召回的比例 |
| 任务分类准确率 | 是否正确识别事实、事件、变化等任务 |
| 范围正确性 | 主体、项目、时间和类型是否正确 |
| 正确不召回率 | 普通任务是否能够保持克制 |
| 正确拒绝推断率 | 记忆不足时是否避免编造 |
| 下游增益 | 召回是否真正改善最终回答或行动 |

一个有价值的反事实判断是：

> 如果去掉此次长期记忆，回答的正确性、连续性或个性化质量是否会实质下降？

如果不会，这次召回可能没有产生实际价值。

### 2.10 阶段性结论

1. Recall Trigger 是长期记忆的认知门控，不只是技术调用开关。
2. 每轮都应隐含判断是否需要记忆，但不代表每轮都执行检索。
3. 触发可以来自用户表达、语言指代、个性化需求、推理缺口和内部认知任务。
4. Recall 可以在任务开始、推理中、回答验证、行动前和离线过程中发生。
5. 任务识别需要区分事实、偏好、事件、状态、变化、任务延续、经验迁移、综合与拒绝推断。
6. 触发阶段只确定“为什么回忆、回忆什么范围”，不负责生成最终检索 Query。
7. 无召回结果不等于不存在相关历史。
8. 在不需要召回和证据不足时保持克制，也是 Recall 的核心能力。

## 3. 召回意图构造（Recall Intent Construction）

> ✅ 已完成首轮深入

召回意图构造解决的不是“怎样搜索”，而是：

> 把用户当前表达转化为明确的历史信息需求：需要回忆谁、什么事情、哪个时间、哪种记忆，以及需要多少证据。

它位于任务识别和候选生成之间：

```text
用户表达
  ↓
任务识别：是否需要长期记忆、为什么需要
  ↓
召回意图：具体缺少什么历史信息
  ↓
候选生成：通过哪些检索路径寻找证据
```

### 3.1 四种 Intent 的边界

#### 3.1.1 用户意图

用户最终想完成什么。例如“继续之前的方案”，用户意图是继续某项工作。

#### 3.1.2 任务意图

Agent 为完成请求需要做什么，例如：

- 找到之前讨论的方案；
- 恢复已经确认的决策；
- 确认任务进度；
- 从上次停止的位置继续。

#### 3.1.3 召回意图

当前缺少哪些历史信息：

```text
当前项目
+ 最近一次被确认的方案
+ 已完成进度
+ 未完成事项
```

#### 3.1.4 检索 Query

用于寻找候选记忆的具体查询表达。一个召回意图可以拆成多个 Query：

```text
查询 1：当前项目最近确认的方案
查询 2：该方案已经完成的事项
查询 3：该方案尚未完成的下一步
```

因此，用户的一句话不必对应一个检索 Query，一个召回意图也可能需要多个证据查询。

### 3.2 召回意图不等于 Query Rewrite

用户表达往往依赖当前会话：

```text
“那之前选的是哪个？”
“还是按上次的方式。”
“他后来改了吗？”
```

这些表达单独向量化无法说明：

- “那”指哪个方案；
- “上次”属于哪个任务或项目；
- “他”指哪个实体；
- “之前”对应哪个时间范围；
- 需要事实、事件还是决策过程。

Query Rewrite 通常聚焦于改写搜索表达，召回意图构造还需要确定：

- 主体和作用域；
- 目标实体及关系；
- 当前态、历史态或变化过程；
- 单点事实还是完整事件链；
- 可接受的记忆类型；
- 支持证据与反证需求；
- 当前理解中的不确定性。

例如，“他后来换了吗？”即使改写为“他后来是否更换了模型”，仍没有解决“他是谁”“相对哪个事件而言是后来”“查询当前结果还是完整变化”等问题。

所以，召回意图首先是一种**受约束的认知表示**，然后才可能派生出检索 Query。

### 3.3 召回意图构造的七个核心过程

这些是知识过程，不代表未来必须形成七个代码步骤。

#### 3.3.1 保留用户原始语义

需要保留：

- 否定：“不是之前那个”；
- 比较：“这次和上次有什么不同”；
- 时间：“五月份”“后来”“最近一次”；
- 程度：“一直”“偶尔”“第一次”；
- 不确定性：“好像”“是不是”；
- 范围：“在这个项目里”。

过早改写容易丢失否定、时间、程度和不确定性。

#### 3.3.2 识别历史信息缺口

不是把整个用户请求送去搜索，而是识别当前工作上下文具体缺少什么。

例如，“还是按上次的方式生成文档”中的当前任务是生成文档，真正的历史信息缺口只是：

```text
“上次的文档生成方式”是什么？
```

#### 3.3.3 消解实体、指代和省略

需要处理人物、对象、项目、时间、动作和被省略的关系。消解依据应优先来自：

1. 当前用户表达；
2. 当前会话中最近、明确的上下文；
3. 当前任务状态；
4. 已确定的项目和实体范围；
5. 必要时才进入长期记忆寻找候选。

这里可能存在循环：

```text
需要知道实体才能检索记忆
但可能需要检索记忆才能知道实体
```

此时不应强行猜测，而应保留少量受约束的候选解释，进入渐进式召回。

#### 3.3.4 绑定作用域

作用域需要区分：

- 当前用户还是其他用户；
- 当前 Agent 还是共享 Agent；
- 当前项目还是历史项目；
- 当前任务还是相似任务；
- 当前会话还是跨会话；
- 私有记忆还是允许共享的记忆。

例如“上次选择 Chroma”可能在多个项目中都发生过。缺少项目范围时，语义相似度无法判断哪次选择才是用户所指。

#### 3.3.5 解释时间意图

时间不是后续排序中的 Recency 附件，而是 Query 语义的一部分。

| 时间模式 | 用户真正需要什么 |
|---|---|
| 当前态 | 现在仍然有效的事实 |
| 历史切片 | 某个指定时间点的状态 |
| 事件定位 | 某件事何时发生、发生了什么 |
| 演化过程 | 从过去到现在如何变化 |

例如：

- “现在用哪个模型？”——当前态；
- “五月份用哪个模型？”——历史切片；
- “什么时候换成 Flash 的？”——事件定位；
- “模型选型怎么变化的？”——演化过程。

相对时间还需要锚点。“最近一次”必须明确相对于哪个主体、项目、事件和当前时间。

#### 3.3.6 判断记忆形态和证据深度

不同问题需要不同的记忆产物：

- 单点事实；
- 单个历史事件；
- 多条互补证据；
- 完整时间线；
- Reflection 与原始依据；
- 支持证据和反证。

例如“用户现在偏好什么”可能主要需要当前有效 fact；“这个习惯是否稳定”则需要多个时间点的事件证据。

#### 3.3.7 保留不确定性

召回意图需要区分：

```text
用户明确表达
当前上下文已确定
系统合理推断
仍然未知
```

如果当前上下文只能确定用户在讨论 Memory，却无法确定是 Write 还是 Recall，就不能把“继续之前那个方案”直接改写成“继续之前的 Memory Recall 方案”。

### 3.4 召回意图的知识维度

以下维度用于理解一次召回意图，不预设具体数据结构：

| 维度 | 需要回答的问题 |
|---|---|
| Need | 缺少什么历史信息？ |
| Purpose | 信息将用于回答、行动、验证还是 Reflection？ |
| Subject | 记忆围绕谁或什么实体？ |
| Scope | 属于哪个用户、项目、任务或会话？ |
| Relation | 需要恢复实体之间什么关系？ |
| Temporal Mode | 当前态、历史切片、事件还是演化？ |
| Memory Type | fact、event、reflection 或组合？ |
| Evidence Depth | 单条答案、多个证据还是时间线？ |
| Confidence | 哪些部分确定，哪些只是推断？ |
| Exclusions | 哪些内容或作用域不能参与召回？ |

例如，“我们之前为什么不用方案 B？”可理解为：

```text
Need：恢复拒绝方案 B 的原因
Purpose：解释历史决策
Subject：当前项目的方案选择
Scope：当前用户 + 当前项目
Relation：方案 B → 未采用原因
Temporal Mode：历史决策事件
Memory Type：event + 约束 fact
Evidence Depth：决策结论及关键依据
Confidence：项目已确定，具体决策时间未知
Exclusions：其他项目中对方案 B 的讨论
```

这仍不是具体检索 Query，而是明确后续应该寻找什么证据。

### 3.5 多意图拆解

“上次为什么选 Chroma，现在还适用吗？”至少包含：

```text
① 上次最终选择了什么？
② 当时为什么选择 Chroma？
③ 当时约束与当前约束相比是否发生变化？
```

- ① 是历史决策恢复；
- ② 是历史原因解释；
- ③ 是跨时间比较和当前适用性判断。

如果把整句话直接 embedding，可能只召回包含“Chroma”的高相似文本，却遗漏当时约束和当前状态。

多意图拆解不是机械切分句子，而是识别不同子问题需要哪些不同证据。

### 3.6 Query Expansion 的类型

#### 3.6.1 语义扩展

纳入同一概念的不同表达，但不能混淆相近而不等价的概念。例如“会使用 Python”不等于“偏好 Python”。

#### 3.6.2 实体与别名扩展

处理全称、缩写、人名、代词、项目代号、模型版本和历史名称。主要风险是不同作用域中的别名碰撞。

#### 3.6.3 关系扩展

用户询问结果时，证据可能存在于相关决策、约束、方案缺陷或历史事件中。这种扩展适合解释型和多跳问题，但也最容易扩大范围。

#### 3.6.4 时间扩展

将“上次、最近一次、改之前、改之后”等相对时间绑定到明确的主体、项目或事件锚点。

#### 3.6.5 证据形态扩展

用户询问一个结论时，可能还需要直接事实、支持事件、反证、Reflection 或事实变化链。这是从“寻找答案”扩展到“寻找足以支持答案的证据”。

### 3.7 Expansion 与范围约束

扩展不足会漏掉别名、隐式关系和历史表达；扩展过度会引入无关主题、错误实体和错误时间。

例如，用户问“之前选择了哪个向量库”，如果扩展成“向量数据库、Embedding、RAG、Chroma、Milvus、FAISS、Memory Store”，召回目标就可能从恢复历史决策漂移成搜索所有相关技术主题。

好的扩展应满足：

1. 与原始意图存在明确关系；
2. 不引入未经证实的答案；
3. 保留主体和作用域；
4. 保留时间约束；
5. 每个扩展具有明确目的；
6. 允许后续合并和去重。

### 3.8 是否需要强制改写

不是所有 Query 都需要改写。

| Query 状态 | 知识上的处理 |
|---|---|
| 自包含且明确 | 保留原表达，只补充安全作用域 |
| 有省略但可由当前上下文解决 | 补全明确上下文 |
| 存在有限歧义 | 保留多个候选解释 |
| 关键范围未知 | 不把猜测固化为唯一意图 |
| 包含多个记忆任务 | 拆分为多个证据需求 |

例如“在 agents_memory 项目中，2026 年 7 月 24 日决定使用哪个模型？”已经包含项目、时间、关系和目标事实，强制改写反而可能引入错误。

召回意图构造不是为了让 Query 看起来更完整，而是让它更忠实、更有边界、更适合寻找证据。

### 3.9 不向用户澄清时处理歧义

不需要把用户澄清作为默认路径：

```text
当前表达
   ↓
优先使用当前会话和任务锚点
   ↓
形成少量、受约束的候选解释
   ↓
分别寻找证据
   ↓
根据实体、时间和上下文一致性消歧
   ↓
仍无法确定
   └── 保留不确定性，不猜测
```

例如“还是用之前那个吧”可能指向两个历史方案。系统可以保留两个候选解释，分别寻找其最近确认事件，再根据当前项目和任务消歧。

不向用户澄清，不代表系统必须自行猜出唯一答案。无法可靠消歧时，应保留未知、限制后续行动，不能把任一候选伪装成确定选择。

### 3.10 核心难点

1. **意图漂移**：补充上下文后偏离用户原始需求。
2. **幻觉式补全**：虚构项目、实体、时间或目标答案。
3. **答案泄漏**：把预期答案直接写进扩展 Query，后续检索只是在验证猜测。
4. **时间坍缩**：把“当时、后来、现在”压缩成同一个主题查询。
5. **实体碰撞**：多个项目或实体名称相同，作用域没有绑定。
6. **多意图压缩**：把事实恢复、原因解释和当前建议混成一个查询。
7. **上下文污染**：将整段会话拼入 Query，稀释真正的信息缺口。
8. **过度确定**：把上下文推测当作已确认范围。
9. **否定丢失**：把“不要上次那个方案”改写成“上次的方案”。

### 3.11 评测与诊断

| 评测维度 | 核心问题 |
|---|---|
| 意图忠实度 | 是否保持用户原始语义、否定和目标？ |
| 指代消解准确率 | 实体、项目、对象和动作是否解析正确？ |
| 作用域准确率 | 是否限制在正确用户、项目、任务和时间？ |
| 时间解释准确率 | 是否区分当前态、历史切片、事件和演化？ |
| 子问题覆盖度 | 多意图请求是否形成足够的证据需求？ |
| 意图漂移率 | 扩展内容是否超出原始请求和可靠上下文？ |
| 不确定性校准 | 系统是否知道哪些信息尚未确认？ |
| 下游召回增益 | 意图构造是否提高证据覆盖和最终回答质量？ |

还可以使用三类对比测试：

- **改写不变性**：用户换一种表达，是否形成等价召回意图？
- **上下文敏感性**：同一句话处于不同项目时，是否形成不同作用域？
- **时间对比性**：“现在”和“去年”是否形成不同时间模式？

### 3.12 阶段性结论

1. 召回意图是历史信息需求，不等于用户原句，也不等于检索 Query。
2. 一个用户请求可能产生多个召回子意图和多个证据查询。
3. 意图构造应先识别信息缺口，再处理实体、作用域、时间、类型和证据深度。
4. 时间是召回语义的一部分，不只是后续排序信号。
5. Query Expansion 应提高证据覆盖，不能引入未经确认的答案。
6. 明确、自包含的 Query 不需要强制改写。
7. 面对有限歧义，应保留候选解释并利用证据消歧，而不是过早猜测。
8. 不向用户澄清，不代表必须形成虚假的唯一结论。
9. 召回意图必须保留否定、排除条件和不确定性。
10. 该环节的质量决定候选生成能够达到的召回上限。

## 4. 多路径候选生成（Multi-Path Candidate Generation）

> ✅ 已完成首轮深入

候选生成解决的是：

> 在不遗漏关键证据的前提下，从不同记忆空间、不同表达方式和不同关系路径中，形成一个覆盖充分的候选集合。

这一阶段追求较高的证据覆盖率，而不是直接选出最终进入上下文的记忆。

```text
召回意图
   ↓
多个候选路径并行或逐步展开
   ↓
候选合并、身份去重、保留来源
   ↓
资格与有效性过滤
   ↓
效用评分和最终选择
```

### 4.1 候选生成与最终排序的边界

候选生成回答：

- 哪些记忆可能相关？
- 哪些路径能够找到不同类型的证据？
- 是否覆盖召回意图的各个子问题？
- 是否存在语义相似度无法发现的精确、时间或关系证据？

最终排序回答：

- 哪些候选当前最有用？
- 哪些候选仍然有效？
- 哪些候选重复、过时或存在冲突？
- 哪组候选最值得进入上下文？

候选生成可以容忍一定噪音，但不能让单条检索路径过早垄断结果。

### 4.2 多路径的三个维度

“多路径”不只是向量检索加关键词检索，它至少包含三个正交维度。

#### 4.2.1 检索信号

根据什么找到记忆：

- 语义；
- 关键词；
- 精确值；
- 时间；
- 实体；
- 关系；
- 当前任务连续性。

#### 4.2.2 记忆空间

到哪里寻找：

- 当前工作记忆；
- 长期 fact；
- 长期 event；
- Reflection；
- 任务状态或未来可能出现的程序性知识；
- 特定用户、项目或 Agent 的记忆空间。

#### 4.2.3 召回粒度

以什么单位返回：

- 原子事实；
- 单个事件；
- 对话片段；
- Session 或 Episode；
- 事件链；
- Reflection 及其来源。

例如，“使用向量路径检索 event”中，向量是检索信号，event 是记忆空间，返回单条事件还是完整 Episode 则属于召回粒度。

### 4.3 向量召回的定位

向量召回擅长发现“表达不同但含义相似”的记忆，是候选生成的重要路径，但不是唯一入口。

它的典型局限包括：

- 日期、版本号、姓名等精确信息可能不稳定；
- 时间顺序难以通过相似度表达；
- 多跳关系不一定与 Query 直接相似；
- 语义相似的记忆不一定属于同一事件；
- 相似度无法判断事实是否已经过时。

向量召回还容易混淆否定和状态变化。例如“用户喜欢 Python”与“用户不再优先使用 Python”在语义空间中可能非常接近，但事实状态相反。

### 4.4 主要候选路径

#### 4.4.1 精确匹配路径

适合唯一标识、日期、数值、文件名、版本号、项目名和明确引用的历史表达。其精度高，但无法覆盖自然语言改写。

#### 4.4.2 词法与关键词路径

适合技术名词、人名、决策关键词、否定词、错误信息和专有领域词汇。它能补充向量召回对罕见词、缩写和精确表达的不稳定性，但容易漏掉同义词和省略表达。

#### 4.4.3 语义路径

适合用户偏好、自然语言事实、相似经验和表达不同但含义相近的事件。它负责扩大表达覆盖，不负责判断事实是否仍然有效。

#### 4.4.4 结构与 Metadata 路径

根据 user、agent、project、session、memory type、event type、status 或 source 等已明确结构寻找记忆。

结构条件既可以形成候选，也可以缩小其他路径的搜索范围，但结构匹配不代表内容对当前任务有用。

#### 4.4.5 时间路径

适合寻找：

- 指定时间窗口内的事件；
- 某个时间点有效的事实；
- 某个事件发生前后的记忆；
- 第一次、最近一次或连续多次发生的事件；
- 状态变化链。

时间路径不是简单选择最新记忆，而是匹配召回意图中的时间模式。

#### 4.4.6 实体路径

围绕用户、Agent、项目、文件、模型、任务或决策对象聚合记忆，用于减少同名项目、相似任务和跨主体记忆混淆。

#### 4.4.7 关系路径

用于发现：

- 决策及其原因；
- 事件及其结果；
- 用户与偏好的关系；
- 任务与约束的关系；
- 事实的支持与反证；
- Reflection 与原始来源；
- 旧状态与新状态。

关系路径能够找到与 Query 不直接相似、但通过关系共同支持答案的记忆。它是多跳召回的重要知识方向，不意味着 `agents_memory` 必须使用图数据库。

#### 4.4.8 近期任务连续性路径

针对正在延续的任务，优先寻找最近活跃目标、已确认决策、任务进度、未完成事项和近期操作结果。

它与普通 Recency 不同：近期任务连续性关注是否属于同一工作流，而不是单纯时间接近。

### 4.5 召回粒度

#### 4.5.1 原子事实

优点是匹配准确、容易去重、上下文成本低；缺点是缺少产生事实的场景，多条原子记忆也容易碎片化。

#### 4.5.2 单个事件

保留时间和行为上下文，适合历史回顾；但单次事件不能证明长期偏好，同类事件多时也容易重复。

#### 4.5.3 Session 或 Episode

将同一任务阶段的多条交互作为整体，适合任务延续和原因解释；缺点是内容较长，相关信息可能被过程文本稀释。

#### 4.5.4 Reflection

信息密度高，适合长期模式和经验复用；但它属于派生认知，可能过度概括，需要原始来源支持。

#### 4.5.5 事件链或时间线

适合状态变化、决策演化和多阶段任务。它通常不是预先存在的一条记忆，而是由多条相关事件构成的证据集合。

不存在适用于所有任务的固定最佳粒度。过细会失去上下文，过粗会稀释检索信号和浪费上下文预算。

### 4.6 检索键与记忆内容

用于发现记忆的文本不一定等于最终返回给 Agent 的记忆内容。

例如原始记忆：

```text
2026-07-24，用户选择路线一。
```

单独看“路线一”很难跨会话召回。检索时可能需要关联：

```text
agents_memory 写入管线
整体实施路线
用户选择路线一
2026-07-24
```

需要区分：

| 内容 | 作用 |
|---|---|
| 原始记忆值 | 表达真正被保存的事实或事件 |
| 检索键 | 帮助未来通过实体、主题和时间找到记忆 |
| 关系与 Metadata | 限定主体、范围、类型和时间 |

检索键可以增强可发现性，但不能改变原始记忆含义。如果增强检索键加入未经确认的解释，后续召回可能把索引阶段的推测当作真实语义。

### 4.7 候选路径的组织方式

这些是知识上的组织模式，不是项目选型。

#### 4.7.1 并行召回

```text
语义 + 精确 + 时间 + 实体 + 关系
```

覆盖充分，不容易被单一路径限制；但候选量和冗余较大，不同路径的分数也难以直接比较。

#### 4.7.2 级联召回

```text
精确 / 结构
   ↓ 证据不足
语义 / 时间
   ↓ 证据不足
关系 / 多跳
```

简单问题可以保持克制，但前一层如果错误判断“证据已经足够”，就可能提前停止。

#### 4.7.3 迭代召回

```text
找到历史决策
  ↓
发现相关约束名称
  ↓
继续召回约束及后续变化
```

适合多跳和原因解释，但第一轮错误可能造成后续方向持续漂移，也可能产生无止境搜索。

### 4.8 跨路径分数不可直接比较

语义路径可能产生相似度，关键词路径可能产生词法分数，时间路径可能产生时间距离，关系路径可能产生连接强度。

这些分数的量纲、分布和含义不同，在不同索引或不同模型间也未必可比。

候选阶段的路径分数主要说明：

> 在当前路径内部，这条候选为什么被找到、相对位置如何。

不能因为某一路径的原始数值较大，就让它压制其他路径。跨路径的最终价值判断属于后续效用评分和集合选择。

### 4.9 候选合并与去重

多条路径可能找到同一条记忆：

```text
语义路径 ───┐
关键词路径 ─┼──→ Memory M1
时间路径 ───┘
```

此时可以按记忆身份合并成一个候选，但应保留它被哪些路径发现。多路径命中本身也是有价值的检索证据。

需要区分：

1. **同一记录被多次找到**：可以直接合并。
2. **多条内容相同的记录**：可能是写入重复，但不能只凭文本相同判断业务身份。
3. **多条语义相似记忆**：不能过早合并。

例如：

```text
用户在任务 A 中选择 Python
用户在任务 B 中选择 Python
用户三个月后再次选择 Python
```

这些事件语义相似，却可能是判断稳定偏好的重要多次证据。

> 候选生成适合身份级去重，不适合过早进行语义级事实合并。

“是否同一事件”“是否属于状态更新”应留给后续时间与关系解析。

### 4.10 路径覆盖与候选预算

如果所有路径共享简单 Top-K，语义路径可能因为候选较多而占满结果：

```text
Top 20
├── 18 条语义近义记忆
├── 1 条时间证据
└── 1 条精确证据
```

需要关注：

- 每个必要子意图是否有候选；
- 精确、时间和关系证据是否被语义结果挤出；
- 不同记忆类型是否获得适当覆盖；
- 候选总量是否超出后续可判断范围；
- 某条路径是否始终没有独特贡献。

这不意味着各路径平均分配候选，而是按召回意图保证证据覆盖。

### 4.11 范围缩小与资格过滤的边界

候选生成时可以使用已确定的作用域缩小搜索，但应区分两类约束。

#### 硬约束

不能因候选不足而放宽：

- 用户和租户隔离；
- 权限；
- 已删除状态；
- 隐私边界；
- 明确排除的记忆空间。

#### 软约束

当证据不足且意图本身存在不确定性时，可以保留调整空间：

- 推测的项目；
- 模糊时间窗口；
- 可能的记忆类型；
- 实体别名；
- 主题范围。

候选生成中的范围缩小服务于效率和初始精度；记忆最终是否有资格参与当前任务，仍属于 §5 的资格与有效性过滤。

### 4.12 空候选的解释

候选为空可能表示：

```text
确实没有记忆
或 写入时没有保存
或 检索键不足
或 召回意图错误
或 使用了不合适的路径
或 时间 / 类型范围过窄
或 资格条件排除了结果
```

面对空结果，可以检查软约束、候选路径和子意图拆解；但用户、权限、隐私和删除状态等硬边界不能因为没有结果而放宽。

### 4.13 核心难点

1. **路径单一**：语义路径承担了精确、时间和关系检索无法承担的任务。
2. **候选爆炸**：路径越多，噪音和判断成本越高。
3. **单路径垄断**：某条路径占满候选预算。
4. **跨路径分数误用**：直接比较含义不同的原始分数。
5. **过早语义去重**：把不同事件错误合并。
6. **召回粒度错误**：原子事实缺少上下文，完整 Session 又过于冗长。
7. **检索键污染**：增强键引入未经确认的推断。
8. **软硬约束混淆**：证据不足时放宽权限边界。
9. **类型隔离过度**：只召回 fact，遗漏相关 event 或 Reflection。
10. **迭代漂移**：根据错误的初始候选持续扩大错误方向。
11. **只找支持证据**：候选路径没有覆盖反证和历史变化。
12. **把空候选解释为事实不存在**。

### 4.14 评测与诊断

| 评测维度 | 核心问题 |
|---|---|
| 候选证据召回率 | 真正需要的支持证据是否进入候选集合？ |
| 多证据完整率 | 是否找齐完成任务所需的关键证据？ |
| 路径独特贡献 | 每条路径是否找到其他路径无法发现的有效候选？ |
| 候选冗余率 | 候选中有多少重复或无贡献近义内容？ |
| 子意图覆盖率 | 多意图请求中的各个证据需求是否都有候选？ |
| 类型与时间覆盖 | 是否覆盖所需记忆类型和关键时间点？ |
| 候选效率 | 为找回必要证据产生了多少无效候选？ |
| 空结果诊断 | 是否区分无记忆、意图错误、路径错误和范围过严？ |
| 安全边界 | 是否发生跨用户、跨权限或已删除记忆泄漏？ |

### 4.15 阶段性结论

1. 候选生成追求高证据覆盖，不负责决定最终使用哪些记忆。
2. 多路径包含检索信号、记忆空间和召回粒度三个维度。
3. 向量召回适合语义近似，但不能独立承担精确、时间、状态变化和关系召回。
4. 原子事实、事件、Episode 和 Reflection 具有不同的召回优势。
5. 检索键可以增强可发现性，但不能改变原始记忆含义。
6. 多路径可以并行、级联或迭代展开，各有不同的覆盖与噪音风险。
7. 不同路径的原始分数不能直接横向比较。
8. 候选阶段适合身份级去重，不应过早合并语义相似事件。
9. 候选预算应服务子意图和证据覆盖，而不是被单一路径占满。
10. 用户、权限和隐私是硬约束；主题、类型和模糊时间通常是软约束。
11. 空候选不等于历史事实不存在。
12. 候选生成上限由召回意图、检索路径和记忆粒度共同决定。

## 5. 资格与有效性过滤（Eligibility & Validity Filtering）

> ✅ 已完成首轮深入

资格与有效性过滤解决的不是“哪条记忆分数更高”，而是：

> 一条候选记忆是否有资格参与当前任务；如果可以，它应以事实、历史记录、假设、冲突证据还是内部线索的身份参与？

```text
候选记忆
   ↓
身份与权限
   ↓
生命周期状态
   ↓
时间适用性
   ↓
证据与来源状态
   ↓
用途和敏感性
   ↓
正常可用 / 条件可用 / 不可用
```

### 5.1 Eligibility、Validity 与 Utility

| 概念 | 核心问题 | 典型判断 |
|---|---|---|
| Eligibility | 有没有资格参与？ | 权限、作用域、删除、用途 |
| Validity | 能以什么知识身份参与？ | 当前事实、历史记录、假设、冲突证据 |
| Utility | 当前有多大价值？ | 相关性、重要性、上下文成本 |

低相关性通常属于评分问题；跨用户、无权限和已删除属于资格问题。

### 5.2 有效性不等于真实性证明

过滤阶段无法证明一条记忆在现实世界中绝对为真。它只能根据已有信息判断：

- 是否来自允许的作用域；
- 是否具有可接受来源；
- 是否被撤回、纠正或替代；
- 是否适用于目标时间；
- 是否足以作为确定事实使用。

一条 `active` 记忆仍可能事实上错误，只是系统尚未发现。

> Validity 表示记忆系统当前对记录可用性的判断，不是终极真理认证。

### 5.3 三态资格

#### 5.3.1 正常可用

可以按其声明的知识身份参与后续评分和上下文编排。例如当前用户明确表达的有效偏好、与目标时间匹配的历史事件，以及来源完整且仍有效的 Reflection。

#### 5.3.2 条件可用

具有价值，但不能作为无条件确定事实使用：

- 已被新状态替代，但当前查询需要历史状态；
- 低置信度推断；
- 存在未解决反证；
- Reflection 的部分来源正在重评估；
- DEFER 记忆参与内部消解；
- 敏感记忆只允许用于特定目的。

条件限制必须保留到后续阶段，不能被悄悄升级为普通事实。

#### 5.3.3 不可用

不应进入当前任务的后续处理：

- 其他用户或租户的私有记忆；
- 无访问权限；
- 已删除；
- 被明确撤回的错误记忆；
- 不允许用于当前目的的敏感信息；
- 用户明确要求排除的记忆范围。

### 5.4 身份、权限与作用域

这是最强的资格边界，需要区分 user、tenant、agent、project、session 和 shared memory space。

其他用户的记忆即使与 Query 完全匹配，也不能因为高相关性获得参与资格。

#### 5.4.1 不可跨越的硬边界

- 用户或租户隔离；
- 访问权限；
- 私有空间；
- 删除要求；
- 明确禁止的共享范围。

#### 5.4.2 由召回意图决定的任务范围

- 当前项目；
- 当前任务；
- 当前会话；
- 历史项目；
- 跨项目经验。

例如“我以前在哪些项目使用过 Chroma”需要跨项目召回；“当前项目为什么选择 Chroma”则通常不需要其他项目。

如果当前作用域没有结果，也不能自动进入其他用户或无权限空间寻找候选。空结果只能用于重新考虑软约束，不能突破安全边界。

### 5.5 生命周期状态

以下为知识上的概念状态，不表示 `agents_memory` 必须采用这些具体枚举。

| 状态 | 正常当前态查询 | 历史查询 | 内部维护 |
|---|---|---|---|
| Active | 可用 | 可用 | 可用 |
| Deferred / Ambiguous | 通常不可作为事实 | 谨慎 | 可用于消解 |
| Superseded | 不作为当前事实 | 可作为历史状态 | 可用于变化分析 |
| Retracted / Corrected | 不可作为真实事实 | 只能作为纠错记录 | 可用于审计或失效传播 |
| Expired | 取决于过期语义 | 可能可用 | 可用于维护 |
| Deleted | 不可用 | 正常 Recall 不可用 | 仅受独立审计规则约束 |
| Quarantined | 不可用 | 通常不可用 | 可供安全审查 |

#### 5.5.1 Superseded 不等于错误

```text
五月：项目使用 GLM-5
七月：项目改用 GLM-4.7-Flash
```

五月的事实过去成立，只是被后续状态替代。

- 当前态查询：五月事实不应作为当前答案；
- 五月历史查询：五月事实仍然有效；
- 变化过程查询：两条都需要参与。

#### 5.5.2 Retracted 与 Superseded 不同

- Superseded：过去成立，现在不再成立。
- Retracted：原记忆被认为记录错误。
- Corrected：错误内容已经被正确内容替代。

历史查询也不能把 Retracted 记忆描述为当时真实事实，只能把它视为系统曾经存在的错误记录。

#### 5.5.3 Expired 的语义

Expired 可能表示业务有效期结束、不再适合个性化、数据保留期结束、退出常规召回，或临时 Session 信息过期。

这些语义的资格后果不同，不能压缩成模糊的“旧了所以不用”。

### 5.6 时间适用性

同一条记忆是否有效，取决于召回意图的时间模式。

#### 5.6.1 当前态查询

要求当前仍然有效。旧状态即使高度相关，也不能作为当前答案。

#### 5.6.2 历史切片

要求在目标时间点成立。此时最新事实反而可能不适用。

#### 5.6.3 事件查询

关注事件是否发生、何时发生，需要事件证据而不只是当前状态。

#### 5.6.4 演化查询

需要旧状态、新状态以及二者之间的变化，被替代记忆在这种任务中具有重要资格。

#### 5.6.5 事件时间与记录时间

```text
事件 / 生效时间：事实何时发生或成立
记录时间：系统何时得知并写入
```

系统在七月得知用户五月已经更换模型时，事件时间是五月，记录时间是七月。只按记录时间过滤会导致历史查询错误。

#### 5.6.6 计划不等于完成

“用户计划下周切换数据库”是一条计划事件，不代表数据库已经切换。到达计划时间后，如果没有执行证据，也不能自动把计划提升为完成事实。

### 5.7 来源、证据与认知身份

#### 5.7.1 用户明确陈述

对用户偏好、目标和个人选择通常具有较高权威性，但也可能表达临时状态、使用反讽、后续改变或记错外部事实。

“用户说过”和“现实一定如此”仍需区分。

#### 5.7.2 系统观察

行为观察可以作为证据，但不能直接等同于稳定偏好：

```text
观察：用户连续三次使用 Python
推断：用户可能偏好 Python
```

后者是派生判断，不是原始事实。

#### 5.7.3 Agent 或模型推断

只能以假设、洞察或 Reflection 身份参与，不能伪装成用户明确陈述。

#### 5.7.4 外部工具结果

需要考虑工具是否成功、数据是否完整、获取时间、外部状态是否变化，以及来源是否仍可追踪。

#### 5.7.5 来源缺失

来源缺失的记忆可以作为检索线索或待验证假设，但不适合独立支撑高确定性结论。

### 5.8 DEFER 记忆的资格边界

DEFER 表示系统尚不能确定候选与已有记忆之间的关系，或者尚不能确认它是否应成为正式记忆。

| 用途 | 资格边界 |
|---|---|
| 正常用户回答 | 通常不能作为已确认事实 |
| 后续静默消解 | 可寻找同一事件、时间锚点和后续证据 |
| Reflection | 通常不宜作为稳定洞察的正式证据 |
| 证据不足判断 | 可提示内部存在未解决信息，但不必暴露具体内容 |

> DEFER 可以参与解决不确定性的内部过程，但不能因为被检索到就自动获得事实资格。

### 5.9 Reflection 的派生有效性

Reflection 的资格不仅取决于自身状态，还依赖来源记忆：

```text
Reflection R1
├── Memory M1：有效
├── Memory M2：已撤回
└── Memory M3：已被替代
```

此时需要判断：

- 剩余证据是否足以支持结论；
- 被撤回来源是否是核心证据；
- 被替代来源是历史证据还是当前事实；
- 是否存在新的反证；
- Reflection 应保持有效、降为条件可用，还是进入重评估。

```text
来源变化
   ↓
依赖 Reflection 重新评估
   ↓
保持有效 / 条件可用 / 失效
```

缺少这种传播时，错误原始记忆即使被删除，其结论仍可能通过 Reflection 继续影响 Agent。

### 5.10 用途、敏感性与最小化

相关不等于允许使用。

#### 5.10.1 目的限制

一条记忆可能允许用于当前用户的个性化、内部维护、Reflection 或安全检查，但不允许用于跨用户推荐、无关任务、对外展示或推断新的敏感属性。

#### 5.10.2 敏感记忆

身份、健康、财务、位置历史、私密关系、认证信息和用户明确要求遗忘的内容，需要更严格的必要性与用途判断。

#### 5.10.3 最小化

如果低敏感信息已经足够完成任务，就不应额外引入高敏感记忆。能够召回不代表应该召回。

### 5.11 当前表达与历史记忆冲突

如果用户当前要求“这次请详细说明”，而历史记忆是“用户偏好简洁回答”，历史偏好并未变成错误记忆，但不适合控制当前响应。

需要区分：

- 当前表达：本轮明确需求；
- 历史偏好：长期默认；
- 当前任务：局部例外还是偏好变化；
- Write Pipeline：是否需要把变化持久化。

Recall 阶段应保证当前明确表达优先于历史偏好；是否形成新的长期事实，由 Write Pipeline 判断。

### 5.12 过滤与时间、冲突解析的边界

资格过滤可以处理已经明确的状态：

- 已删除；
- 已撤回；
- 已知被替代；
- 已知有效时间范围；
- 已知来源失效。

如果候选之间的关系尚未确定，例如无法判断它们是状态更新、不同作用域事实还是不同事件，就不应在过滤阶段草率删除其中一条。

> 已知无资格可以过滤；关系尚未明确时应保留不确定性。

复杂的同一事件和时间关系判断属于后续“时间、冲突与关系解析”。

### 5.13 过滤顺序的核心原则

不讨论具体执行结构，知识上应优先保证：

```text
身份 / 权限 / 删除
    ↓
生命周期状态
    ↓
用途与敏感性
    ↓
时间适用性
    ↓
来源与证据状态
    ↓
正常可用 / 条件可用
```

- 安全边界不能依赖最终排名；
- 已删除内容不能通过其他检索路径重新进入；
- 条件可用状态必须传递到下游；
- 过滤原因应可诊断；
- 用户侧不能获知无权限候选是否存在。

### 5.14 过滤为空的解释

过滤后没有候选可能表示：

- 候选本来就为空；
- 所有候选属于错误作用域；
- 记忆已删除或撤回；
- 只存在 DEFER；
- 只有与目标时间不匹配的记忆；
- 只有低可信或缺失来源的证据；
- 当前用途不允许使用相关记忆。

这不等于“相关历史从未发生”。对用户通常只能表达当前没有可用的可靠记忆或证据不足，不能泄露无权限或已删除内容。

### 5.15 核心难点

1. **过度过滤**：有效历史证据被当作过期噪音排除。
2. **过滤不足**：跨用户、无权限或已删除内容进入后续阶段。
3. **当前有效与历史有效混淆**。
4. **Superseded 与 Retracted 混淆**。
5. **Expired 的含义不明确**。
6. **DEFER 以普通事实身份参与回答**。
7. **低置信度推断被当作明确陈述**。
8. **Reflection 来源失效后仍继续生效**。
9. **敏感信息因语义相关而被过度召回**。
10. **当前用户表达被历史偏好压制**。
11. **关系未知时过早删除候选**。
12. **过滤理由泄露受限记忆的存在**。
13. **所有有效性被压缩成单个 `active` 状态**。
14. **将无可用候选解释为事件从未发生**。

### 5.16 评测与诊断

| 评测维度 | 核心问题 |
|---|---|
| 安全隔离 | 是否发生跨用户、越权或已删除记忆召回？ |
| 生命周期正确性 | Superseded、Retracted、Expired、DEFER 是否被正确使用？ |
| 时间适用性 | 当前态、历史切片和演化查询是否获得不同资格结果？ |
| 证据身份保真 | 用户陈述、观察和 Reflection 是否保持不同身份？ |
| 派生失效传播 | 来源变化后依赖 Reflection 是否进入重评估？ |
| 过度过滤 | 有效证据被错误排除的比例 |
| 过滤不足 | 无效或无资格证据被错误放行的比例 |
| 可诊断性 | 内部能否解释原因，同时不向用户泄露受限记忆？ |

安全隔离、越权访问和已删除内容的正常召回应接近绝对零容忍。

### 5.17 阶段性结论

1. Eligibility、Validity 和 Utility 是三个不同问题。
2. 有效性表示当前可用性判断，不等于绝对真实性。
3. 过滤结果至少应区分正常可用、条件可用和不可用。
4. 用户、租户、权限、删除和隐私属于不可放宽的硬边界。
5. Superseded 是过去成立但当前失效；Retracted 是原记录错误。
6. 当前态、历史态和演化查询会赋予同一记忆不同资格。
7. 事件时间和记录时间必须分开理解。
8. DEFER 只能参与适当的内部消解，不能自动成为回答事实。
9. Reflection 的有效性依赖原始证据，需要支持失效传播。
10. 相关不等于允许使用，敏感记忆还受用途和最小化约束。
11. 当前明确表达优先于历史偏好。
12. 已知无资格可以过滤；关系尚未确定时应保留候选。
13. 过滤为空不等于历史事件从未发生。
14. 条件可用状态和过滤原因必须传递到下游，但不能泄露受限记忆。

## 6. 单条记忆效用评分（Memory Utility Scoring）

> ✅ 已完成首轮深入

单条记忆效用评分解决的是：

> 在已经通过资格过滤的候选中，某条记忆对当前召回意图具有多大的潜在使用价值？

评分不能让无资格记忆重新获得资格，高分也不代表记忆一定真实或最终必须进入上下文。

```text
候选资格
   ↓
单条记忆效用
   ↓
时间与冲突解析
   ↓
集合层面的覆盖、互补和去冗余
```

### 6.1 Utility 是条件概念

记忆效用不是固定属性，而是：

```text
Utility(memory | 当前意图、任务、主体、时间、用途)
```

例如，“2026 年 5 月，项目使用 GLM-5”对于不同问题具有不同效用：

| 问题 | 单条效用 |
|---|---|
| 项目现在使用什么模型？ | 较低，只能作为旧状态 |
| 五月份使用什么模型？ | 很高 |
| 模型选择如何变化？ | 很高，是变化链的一部分 |
| 用户喜欢什么编程语言？ | 接近无关 |

因此不能为一条记忆永久保存一个最终召回分数。

### 6.2 经典三信号的准确定位

Generative Agents 使用：

```text
Recency + Importance + Relevance
```

论文中将三种信号归一化后线性组合，实验原型使用等权重。其中 Recency 按照距离上次被检索的时间指数衰减，论文中的衰减因子是 `0.995`。

这个模型的重要价值是说明记忆召回不能只有语义相关性，还要考虑显著性和注意力延续。但它仍是特定模拟环境中的经典基线，而不是通用评分标准。

- 该 Recency 更接近最近是否处于注意力范围；
- 不等于事件发生时间；
- 不等于事实是否仍然有效；
- 不等于 Query 的目标时间；
- 等权重是实验设定，不是理论结论。

### 6.3 评分信号的四类来源

#### 6.3.1 当前任务相关信号

- Relevance；
- Task Fit；
- Temporal Fit；
- Entity / Relation Fit；
- Scope Fit。

#### 6.3.2 记忆自身先验

- Importance；
- Confidence；
- 来源质量；
- 记忆类型；
- 证据完整性。

#### 6.3.3 使用历史信号

- 最近访问时间；
- 召回频率；
- 实际使用频率；
- 是否改善过任务结果；
- 是否被用户纠正；
- 最近重新验证时间。

#### 6.3.4 风险与成本信号

- 过期风险；
- 推断风险；
- 敏感程度；
- 文本长度；
- 验证成本；
- 错误使用可能造成的影响。

这些信号不天然处于同一量纲，也不一定都适合简单相加。

### 6.4 Relevance：相关不等于能够回答

Relevance 回答的是内容与当前召回意图是否相关。它可能来自语义、关键词、实体、关系或时间等不同路径。

```text
用户喜欢 Python
用户不再喜欢 Python
```

两条记忆语义接近，但状态相反。因此相似度不能说明：

- 记忆蕴含正确答案；
- 记忆与 Query 立场一致；
- 记忆仍然有效；
- 记忆属于同一事件；
- 记忆能够独立回答问题。

还需要区分直接相关和证据相关。用户问“为什么没有选择方案 B”时，“方案 B 需要在线服务，而项目要求离线运行”与 Query 的字面相似度可能较低，却具有更高解释价值。

### 6.5 Task Fit：知识形态是否适合当前任务

Task Fit 回答一条记忆是否适合当前认知任务。

| 记忆 | “选了什么” | “为什么选择” | “现在是否适用” |
|---|---:|---:|---:|
| 最终决策事件 | 高 | 中 | 中 |
| 当时约束 | 中 | 高 | 高 |
| 当前技术栈 fact | 高 | 低 | 高 |
| 相关 Reflection | 中 | 高 | 中 |
| 另一个项目经验 | 低 | 中 | 中 |

常见任务包括事实恢复、原因解释、历史回顾、当前状态、时间变化、模式归纳、经验迁移和 Reflection 证据。

### 6.6 Temporal Fit：匹配目标时间

Temporal Fit 回答一条记忆是否属于当前问题询问的时间：

- 当前状态查询通常偏好近期且仍有效的事实；
- 历史查询应偏好目标时间范围内的记忆；
- 事件定位查询偏好目标事件发生时间附近的记录；
- 演化查询要求旧状态和新状态共同参与。

```text
Recency：距离某个“现在”有多近
Temporal Fit：是否匹配 Query 的目标时间
```

### 6.7 Recency 包含不同时间

| Recency 类型 | 含义 |
|---|---|
| Event Recency | 事件距离现在多久 |
| Record Recency | 系统多久前写入这条记忆 |
| Access Recency | 这条记忆多久前被召回 |
| Validation Recency | 这条记忆多久前被重新确认 |

#### 6.7.1 Event Recency

适合近期事件和任务连续性，但不适合对稳定 fact 统一衰减。

#### 6.7.2 Record Recency

记录晚不代表事件新，系统可能今天才得知去年的事件。

#### 6.7.3 Access Recency

表示近期注意力连续性，但容易形成自我强化：

```text
记忆因为高分被召回
→ last_accessed 更新
→ Access Recency 更高
→ 下次更容易被召回
```

#### 6.7.4 Validation Recency

对易变化事实很重要。当前工作单位最近被重新确认过，比仅仅最近被检索过更能说明它仍可靠。

### 6.8 Importance：总体显著性先验

Importance 回答不考虑当前 Query 时，一条记忆总体上有多重要。它适合表达核心身份、长期目标、关键决策、严格限制和严重经验。

但它不能替代：

- Relevance：高重要记忆可能与当前问题无关；
- Confidence：重要推断不会因此变得可信；
- Temporal Fit：过去重要的决策不一定代表当前状态；
- 精确事实：低重要细节可能正是当前问题的答案。

Importance 还可能受表达情绪、文本长度、Prompt、模型版本、记忆类型和当前会话氛围影响。同一个分值在不同用户、模型和类型之间不一定等价。

### 6.9 Confidence 与来源可信度

Confidence 回答一条记忆被正确记录和正确理解的可能性，需要区分用户陈述、系统观察、工具结果、Agent 推断、Reflection、来源缺失和反证。

Confidence 不一定适合作为普通加分项。高度相关但低置信的记忆，不应仅凭高 Relevance 补偿风险。

在知识上，Confidence 可能承担：

- 资格门槛；
- 分数上限；
- 风险惩罚；
- 上下文中的不确定性标签；
- 是否需要附带原始证据。

来源可信度还依赖任务：用户自述对个人偏好通常较权威，工具结果对外部状态可能更权威，系统观察适合说明行为，Reflection 适合提供模式假设。

### 6.10 Scope、Entity 与 Relation Fit

资格过滤保证记忆允许参与当前范围，评分还需要判断它与目标的具体适配程度。

例如跨项目经验查询允许多个项目参与，但当前项目相同、技术条件相似、目标实体相同或关系类型相同的记忆，通常具有更高效用。

```text
资格：允许跨项目寻找经验
评分：哪个项目的经验与当前情况更相似
```

### 6.11 使用历史：被召回不等于有用

| 信号 | 含义 |
|---|---|
| Retrieved | 进入过候选或上下文 |
| Read | 被下游模型看到 |
| Used | 实际影响回答或行动 |
| Helpful | 对最终结果产生正向作用 |
| Corrected | 被用户或系统指出错误 |

如果只把召回次数当作正反馈，会形成记忆的“富者愈富”：

```text
早期偶然高分
→ 多次召回
→ 访问次数增加
→ 得分继续提高
→ 冷门但正确的记忆越来越难出现
```

后续是否真正使用、是否改善任务、是否被纠正，比单纯召回次数更有意义，但这些反馈也可能含噪音，不能无界累积。

### 6.12 风险与成本

#### 6.12.1 过期风险

易变化的用户状态、项目状态和外部信息长期未验证时，需要更谨慎。

#### 6.12.2 推断风险

Reflection 或模型推断如果被错误使用，可能固化错误画像。

#### 6.12.3 敏感风险

高敏感记忆应满足更高的必要性要求，而不是只看相关性。

#### 6.12.4 Token 成本

效用相近时，更短且自包含的记忆可能更适合上下文，但不能为了长度删除否定、时间、来源、置信度或关键条件。

#### 6.12.5 验证成本

某些记忆必须连同来源或原始事件一起使用，其真实上下文成本高于记忆文本本身。

### 6.13 不同记忆类型的评分重点

#### 6.13.1 稳定 Fact

更关注实体与属性相关性、当前有效性、来源、置信度和最近验证时间。普通时间衰减不应过强。

#### 6.13.2 Event

更关注事件语义、时间适配、主体、项目、任务连续性和事件重要性。

#### 6.13.3 Reflection

更关注任务适配、来源覆盖、派生有效性、结论置信度和原始证据。不能因为 Reflection 通常 Importance 较高，就让它压制原始事实。

#### 6.13.4 DEFER

不进入正常回答评分，只在内部消解任务中判断它对解决不确定性是否有帮助。

#### 6.13.5 历史旧状态

对当前态任务效用低，对历史或演化任务效用高，不能仅根据 `superseded` 统一降分。

### 6.14 不同任务的信号重点

| 任务 | 主要信号 |
|---|---|
| 当前事实 | 当前有效性、实体匹配、最近验证、来源 |
| 历史切片 | Temporal Fit、事件时间、来源 |
| 任务延续 | 任务连续性、近期事件、未完成状态 |
| 原因解释 | Relation Fit、事件链、约束证据 |
| 偏好适配 | 稳定性、作用域、置信度、当前表达 |
| 变化过程 | 时间覆盖、旧状态与新状态 |
| 经验迁移 | 情境相似、结果质量、适用条件 |
| Reflection | 证据覆盖、反证、来源多样性 |

不存在对所有任务都正确的一组固定权重。

### 6.15 简单线性加权的边界

```text
score
= α × relevance
+ β × recency
+ γ × importance
```

线性加权适合作为透明基线，但存在：

1. **补偿效应**：高 Importance 可能补偿几乎为零的 Relevance。
2. **信号重复**：语义、实体和 Task Fit 可能重复表达同一信息。
3. **类型差异丢失**：Fact、Event、Reflection 被迫使用同一逻辑。
4. **条件限制被抵消**：低置信或过期风险被高相关性抵消。
5. **分数没有概率意义**：`0.82` 通常不表示有 82% 概率应该召回。

### 6.16 信号归一化与校准

不同信号可能处于完全不同的范围：

```text
Importance：1–10
Cosine Similarity：可能为 -1–1 或其他范围
Recency：0–1
Confidence：离散等级或概率
关键词分数：无固定上界
```

#### 6.16.1 Min-Max 的不稳定性

- 同一记忆会因其他候选变化而改变归一化分；
- 异常值会压缩其他候选差异；
- 候选很少或分数相同时容易失真；
- 不同 Query 的结果难以比较。

Generative Agents 的候选集合内 Min-Max 是透明研究基线，但不能因此认为已经完成跨任务校准。

#### 6.16.2 跨路径分布差异

语义、关键词、时间和关系分数含义不同，不能只把它们压到 `[0,1]` 就认为可比较。

#### 6.16.3 跨类型校准

Event 的 Importance 可能普遍低于核心 Fact，Reflection 又可能普遍更高。如果不校准，某一类型会长期垄断结果。

#### 6.16.4 跨用户和模型漂移

不同用户历史规模、模型版本和 Prompt 可能形成不同评分尺度。需要关注相对稳定性，而不只是一次排序效果。

### 6.17 评分组织方式的知识谱系

以下不是 `agents_memory` 的方案选择。

| 方式 | 优点 | 主要局限 |
|---|---|---|
| 线性加权 | 透明、易解释、易做信号消融 | 补偿效应强，难处理类型差异 |
| 分层或门控 | 防止无关但重要、很新但错误的记忆高排 | 边界过硬可能误伤边缘证据 |
| 学习式排序 | 能捕获非线性关系 | 依赖可靠反馈，可能学习历史偏差 |
| LLM 语义重排 | 能理解复杂任务、时间和关系 | 成本高、不稳定、可能受候选文本污染 |
| 混合判断 | 便宜信号缩小范围，再判断少量难例 | 具体边界需要实施阶段确定 |

### 6.18 单条评分不能解决的问题

即使每条记忆的效用估计准确，仍不能单独解决：

- 多条高分记忆高度重复；
- 支持证据和反证如何平衡；
- 当前态与历史态如何组合；
- 两条记忆是否属于同一事件；
- 是否已经拥有足够证据；
- 哪组记忆在 Token 预算内覆盖最完整。

这些问题属于后续时间、冲突与关系解析，以及集合选择与上下文编排。

> 单条效用表示记忆独立看具有多大的候选价值，不是它最终必须进入上下文的概率。

### 6.19 核心难点

1. 把相关性误认为效用。
2. 把 Recency、Temporal Fit 和 Validity 混为一谈。
3. 把事件时间、记录时间、访问时间和验证时间混用。
4. Importance 高的记忆长期压制低重要但精确的事实。
5. 低 Confidence 被其他高分补偿。
6. 所有记忆类型使用同一评分逻辑。
7. 不同路径原始分数直接比较。
8. Min-Max 结果随候选集合变化。
9. 被召回次数形成自我强化循环。
10. 把被召回误认为被正确使用。
11. 用户或模型版本变化造成分数漂移。
12. 高分被误解为真实性概率。
13. 单条评分提前承担集合去重和证据充分性判断。
14. 评分体系只优化检索指标，没有改善最终回答。

### 6.20 评测与诊断

#### 6.20.1 排序质量

可观察正确证据是否进入前列、第一条有效证据的排名，以及多条相关证据的整体排序。传统指标可包括 MRR、NDCG、Precision@K，但不能只看这些指标。

#### 6.20.2 时间正确性

- 当前事实是否压过旧状态；
- 历史查询是否正确提升旧记忆；
- 演化查询是否保留多个时间点。

#### 6.20.3 类型公平性

- Fact、Event、Reflection 是否存在某一类型长期垄断；
- 低 Importance 的精确事实是否有机会进入前列。

#### 6.20.4 校准与稳定性

- Query 轻微改写后排名是否剧烈变化；
- 候选集合增加异常值后是否整体失真；
- 模型或 Prompt 版本变化后分数是否漂移。

#### 6.20.5 信号消融

分别移除 Relevance、Importance、Recency、Temporal Fit、Confidence 等信号，观察哪些任务改善、哪些任务恶化，以及某信号是否只对特定记忆类型有效。

#### 6.20.6 下游价值

评分最终仍需由回答准确性、时间推理、知识更新、多会话综合、证据不足时的克制和错误记忆影响等下游结果验证。

### 6.21 阶段性结论

1. Utility 是相对于当前意图、任务、主体、时间和用途的条件价值。
2. 三信号是经典透明基线，不是固定标准；Generative Agents 的 Recency 指距离上次检索的时间。
3. Relevance 表示内容相关，不表示蕴含答案、当前有效或事实正确。
4. Task Fit 用于区分同主题记忆对不同认知任务的价值。
5. Temporal Fit 匹配目标时间，Recency 只表示某种“最近”。
6. Event、Record、Access、Validation 四类时间不能混用。
7. Importance 是总体显著性先验，不能替代相关性、可信度和时间适配。
8. Confidence 和来源限制不一定适合作为可被高分抵消的普通加分项。
9. 被召回、被读取、被使用和产生帮助是不同反馈。
10. 不同记忆类型和任务需要不同的信号重点。
11. 简单线性加权适合作为基线，但存在补偿、重复计算和类型偏差。
12. 归一化不等于校准，压缩到同一数值范围也不代表信号可比较。
13. 高效用分数不是事实概率，也不保证记忆最终进入上下文。
14. 单条评分不能解决冲突、冗余、证据充分性和集合覆盖问题。

## 7. 时间、冲突与关系解析（Temporal & Relational Resolution）

> ✅ 已完成首轮深入

这一环节不是简单地“解决冲突”，而是：

> 根据当前召回意图，把多条候选记忆组织成时间正确、关系明确、认知身份可解释的记忆视图。

它需要回答：

```text
① 这些记忆分别属于什么时间？
② 它们是否描述同一事实或同一事件？
③ 它们之间是补充、变化、纠错、并存，还是真正矛盾？
```

### 7.1 面向当前 Query 的知识投影

同一组记忆在不同问题下可以产生不同结果：

```text
M1：2026-05，项目使用 GLM-5
M2：2026-07，项目切换到 GLM-4.7-Flash
```

| Query | 需要形成的记忆视图 |
|---|---|
| 现在使用什么模型？ | 当前态：GLM-4.7-Flash |
| 五月使用什么模型？ | 历史切片：GLM-5 |
| 什么时候切换的？ | 变化事件：2026-07 |
| 模型如何变化？ | 时间线：GLM-5 → GLM-4.7-Flash |
| 是否一直使用 Flash？ | 否，并提供历史反例 |

Recall 不是为记忆计算永久正确的关系，而是根据当前问题投影出适当的时间和关系视图。

### 7.2 三类时间

#### 7.2.1 事件时间（Event Time）

事件实际发生的时间，适用于回答什么时候发生、先后顺序和事件前后变化。

#### 7.2.2 有效时间（Valid Time）

一个状态或事实在现实中成立的时间区间：

```text
项目模型 = GLM-5
valid_from：2026-05
valid_until：2026-07
```

Fact 通常更适合表达有效区间，而不是只有一个时间点。

#### 7.2.3 记录 / 知识时间（Record / Knowledge Time）

系统什么时候得知并保存了该信息。

```text
事件时间：2026-05-10
系统得知：2026-07-01
```

系统可能在七月才知道五月发生的事情。

### 7.3 三种历史问题

#### 7.3.1 当时实际发生了什么

关注 Event Time 或 Valid Time。

#### 7.3.2 当时 Agent 知道什么

关注 Record / Knowledge Time。

#### 7.3.3 现在回看，当时实际是什么

需要使用当前掌握的修正信息重新解释过去。

例如系统七月才得知五月已经切换模型：

| 问题 | 可能答案 |
|---|---|
| 五月时 Agent 知道什么？ | Agent 当时仍认为是旧模型 |
| 现在看五月实际是什么？ | 已经是新模型 |

如果只有一个 `created_at`，这两类问题无法区分。

### 7.4 相对时间与锚点

“上次、最近、后来、之前、第一次、改完以后”等表达都需要锚定到当前时间、会话、项目、事件、用户时区或任务阶段。

例如“修改以后又出过问题吗”的时间范围是：

```text
修改事件结束
    ↓
到当前查询时间之间
```

如果锚点无法确定，应保留时间范围或多个候选锚点，而不是伪造精确日期。

### 7.5 同一事件判断

两条相似记忆可能是同一事件的不同描述、不同时间重复发生的事件、不同项目中的类似事件、计划与实际执行，或者事件与其 Reflection。

#### 7.5.1 判断维度

| 维度 | 核心问题 |
|---|---|
| Participants | 是否涉及同一主体？ |
| Action / Predicate | 是否描述同一动作或状态变化？ |
| Object | 作用对象是否相同？ |
| Scope | 是否属于同一项目、任务或会话？ |
| Time | 时间点或区间是否重合？ |
| Location / Context | 场景是否一致？ |
| Cause / Outcome | 原因和结果是否属于同一事件链？ |
| Provenance | 是否来自同一段交互或同一来源？ |

不能只凭文本相似度判断。

#### 7.5.2 判断结果

```text
SAME_EVENT
DIFFERENT_EVENT
UNKNOWN
```

这些是知识语义，不代表未来必须使用这些枚举。`UNKNOWN` 表示证据不足，不能强行合并，也不能直接认定为独立事件。

### 7.6 Fact 与 Event 的关系规则

#### 7.6.1 Fact 更接近状态

Fact 可能被纠正、被新状态替代、在不同作用域并存或随时间失效，因此重点是有效区间和作用域。

#### 7.6.2 Event 更接近发生记录

后续事件通常不会覆盖先前事件，它们共同构成历史。Event 只有在原事件被误记、两条记录描述同一事件，或后续信息补充同一事件细节时，才涉及纠错或合并。

#### 7.6.3 计划、执行和结果

```text
计划切换数据库
开始切换数据库
数据库切换完成
数据库切换失败
```

它们属于同一任务链，但不是等价状态。计划不能作为完成证据，开始执行也不能推出最终成功。

### 7.7 记忆之间的主要关系

#### 7.7.1 重复或等价

表达同一事实，没有实质信息增量。

#### 7.7.2 补充

描述同一事实或事件的不同方面，例如选择结果和选择原因。

#### 7.7.3 时间演化

同一属性在不同时间发生变化。旧状态和新状态共同构成历史。

#### 7.7.4 作用域并存

同一主体在不同项目、环境或条件下具有不同取值，可以同时成立。

#### 7.7.5 纠错或撤回

后续信息否定的是原记录真实性，而不是表示普通状态变化。

#### 7.7.6 支持与派生

Reflection 来源于一组原始记忆，二者不属于独立证据。

#### 7.7.7 因果与结果

约束、决策和结果可能共同构成解释链，即使它们语义并不相似。

#### 7.7.8 未确定关系

现有信息不足以判断是重复、演化、纠错还是矛盾。

### 7.8 真正冲突的条件

两条记忆构成事实冲突，通常需要同时满足：

```text
同一主体
+ 同一属性 / 命题
+ 同一作用域
+ 有效时间重叠
+ 认知身份可比较
+ 取值互斥
```

以下情况通常不是真冲突：

- 时间不同：可能是状态变化；
- 作用域不同：可以并存；
- 条件不同：例如开发环境与生产环境；
- 认知身份不同：明确事实与低置信推断；
- 粒度不同：可能是补充关系。

### 7.9 “最新记录优先”的局限

最新写入不代表最新事实，也不必然最可信：

- 系统可能晚记录旧事件；
- 新记录可能只是低置信度推断；
- 历史查询需要旧状态；
- 新记录可能属于另一个作用域；
- 今天的纠错可能回溯修改对过去事实的理解。

应优先理解明确生效时间、事件身份、作用域、来源、纠错关系和 Query 的时间模式。“更新更晚”只能作为弱信号。

### 7.10 当前用户表达的特殊地位

历史记忆是“用户偏好简洁回答”，当前表达是“这次请详细展开”时：

- 当前任务需要详细；
- 历史偏好可能仍是默认；
- “这次”暗示局部例外；
- 是否形成长期变化由 Write Pipeline 判断。

> 当前表达优先控制当前行为，但不自动抹除历史事实。

### 7.11 `unknown + contradict`

当两条候选看似互斥，但无法确认是否同一事件、时间、作用域，或无法判断来源可靠性时：

```text
保留两条候选
   ↓
关系标记为未确定
   ↓
不生成唯一的当前事实
   ↓
寻找时间、实体、来源和后续证据
   ↓
仍无法确定
   └── 保留不确定性，不猜测
```

#### 面向正常回答

- 只使用两条都支持的共同部分；
- 表达现有记忆存在不一致；
- 任务不依赖该事实时避开不确定部分；
- 任务依赖时说明证据不足。

#### 面向内部消解

可以作为 DEFER 静默消解线索、Maintenance 重评估信号、后续 Write 的关系判断上下文，或 Reflection 的反证与排除项。

不向用户澄清不代表必须猜出唯一答案。系统可以保留受约束解释、等待后续上下文、限制高风险行动，并保持必要的不确定性。

### 7.12 开放世界：未记录不等于否定

Memory 通常遵循开放世界假设：

```text
没有记忆到 X
        ≠
X 从未发生
```

需要区分：

- 显式否定证据：“用户说自己从未使用 Rust”；
- 缺少正向证据：“没有找到使用 Rust 的记忆”。

只有前者能够直接支持否定命题，后者只能说明当前记忆不足。这对“一直、从未、所有、每次”等全称问题尤其重要。

### 7.13 Reflection 与证据独立性

```text
M1：用户要求先讨论知识
M2：用户确认讨论后再实施
R1：用户倾向先澄清知识再实施
```

R1 来源于 M1 和 M2。如果把三者视为三份独立支持，就会重复计算证据。

需要保留 Reflection 的来源、派生深度、与原始证据的重合以及可能的循环派生。Reflection 可以帮助理解模式，但不能凭派生关系制造虚假的证据多数。

### 7.14 Recall 与 Write 的职责边界

| 管线 | 主要职责 |
|---|---|
| Write | 新增、更新、重复与冲突判断、DEFER、状态和关系写回 |
| Recall | 面向 Query 的时间视图、关系解释、冲突保留、不确定性表达和证据组合 |

> Write 决定记忆库如何记录关系；Recall 决定当前问题如何理解这些关系。

Recall 发现疑似冲突时，不应因为一次查询直接修改持久化记忆。它可以产生冲突信号、重评估信号、DEFER 消解线索或 Maintenance 输入，具体变化仍由受控写入或维护流程完成。

### 7.15 关系解析的知识产物

#### 当前状态视图

```text
当前有效：GLM-4.7-Flash
历史状态：GLM-5
```

#### 历史切片

```text
截至 2026-05：GLM-5
```

#### 变化时间线

```text
2026-05：GLM-5
2026-07：GLM-4.7-Flash
```

#### 冲突证据包

```text
候选 A：支持 X
候选 B：支持非 X
当前无法确认二者关系
```

#### 派生证据图

```text
Reflection R1
├── 支持：M1、M2
└── 反证：M3
```

这些是语义产物，不表示未来必须采用特定格式。

### 7.16 核心难点

1. 只有记录时间，没有事件时间和有效时间。
2. 相对时间缺少锚点。
3. 时间粒度不同，模糊阶段难以比较。
4. 同一事件判断只依赖语义相似度。
5. 重复发生的事件被错误合并。
6. Fact 状态更新与 Event 历史累积混淆。
7. 计划、执行和完成被当作同一状态。
8. 状态变化误判成事实冲突。
9. 作用域不同的事实被错误互斥。
10. 使用最新写入优先作为统一规则。
11. 新推断覆盖旧的明确事实。
12. 未记录被解释为否定证据。
13. `unknown + contradict` 被迫选择一边。
14. Reflection 和来源记忆被重复计票。
15. Recall 为了当前回答直接修改持久化关系。
16. 时间或关系不确定性在上下文编排时丢失。

### 7.17 评测与诊断

| 评测维度 | 核心问题 |
|---|---|
| 当前态准确率 | 是否选择当前仍有效的事实？ |
| 历史切片准确率 | 是否恢复目标时间点的状态？ |
| Knowledge-Time 准确率 | 是否区分当时发生了什么和当时 Agent 知道什么？ |
| 时间线完整性 | 是否覆盖关键状态变化且顺序正确？ |
| 同一事件识别 | 是否区分同一事件描述与重复发生的类似事件？ |
| 关系分类 | 重复、补充、演化、并存、纠错、矛盾和未知是否正确？ |
| 不确定性保持 | 证据不足时是否保留 UNKNOWN？ |
| 开放世界正确性 | 是否避免将未召回解释为从未发生？ |
| 派生证据去重 | Reflection 是否与来源被错误视为独立证据？ |

### 7.18 阶段性结论

1. 时间、冲突与关系解析是在当前 Query 下构造知识视图。
2. 事件时间、有效时间和记录时间必须分开理解。
3. 当时发生了什么、当时 Agent 知道什么、现在如何理解当时是不同问题。
4. 相对时间必须绑定主体、事件和时间锚点。
5. 同一事件判断需要主体、动作、对象、作用域、时间和来源共同支持。
6. Fact 主要描述状态，Event 主要记录发生历史，两者关系规则不同。
7. 真正冲突通常要求同主体、同属性、同作用域、有效时间重叠且取值互斥。
8. 状态演化、作用域差异和认知身份差异不能误判为冲突。
9. 最新记录不等于最新事实，也不必然最可信。
10. 当前表达优先控制本轮行为，但不自动抹除历史记忆。
11. `unknown + contradict` 应保留候选、继续静默消解并避免猜测。
12. 未记录不构成否定证据，Memory 默认是开放世界。
13. Reflection 与来源不能作为独立重复证据。
14. Recall 负责面向 Query 的解释，Write 和 Maintenance 负责持久化关系变化。
15. 关系解析结果可以是当前态、历史切片、时间线、冲突证据包或派生证据图。

## 8. 集合选择与上下文编排（Set Selection & Context Assembly）

> ✅ 已完成首轮深入

这一环节解决的是：

> 在有限上下文预算下，从已经解析关系的候选中，选择一组最小但充分、互补且可正确理解的记忆证据，并按照当前任务适合的方式组织它们。

重点已经从“哪条记忆分数最高”变成“哪些记忆放在一起，才能完整、准确地支持当前任务”。

### 8.1 单条 Utility 与集合 Utility

集合效用可以从知识上理解为：

```text
Utility(S | query)
≈ 覆盖度
+ 互补性
+ 时间完整性
+ 证据独立性
+ 来源可解释性
- 冗余
- Token 成本
- 错误与敏感风险
```

这不是固定公式。

一条记忆加入集合后的价值取决于：

```text
Marginal Utility(memory | 已选集合)
```

例如“用户偏好简洁回答”“用户喜欢简短回复”“用户希望回答不要太长”单独看都相关，但选入第一条后，另外两条的新增信息已经很少。

### 8.2 Top-K 的局限

#### 8.2.1 近义结果占满预算

高相关的重复记忆可能挤掉时间、原因和反证。

#### 8.2.2 多意图覆盖不完整

用户问“上次为什么选 Chroma，现在还适用吗”，Top-K 可能全部是关于“选择 Chroma”的记忆，却遗漏当时约束、选择原因、当前状态和后续变化。

#### 8.2.3 缺少反证

支持某结论的记忆可能普遍高分，反证因表达不同被截断。

#### 8.2.4 Reflection 压制原始证据

Reflection 通常语义集中、Importance 较高，容易排在原始事件前面。

#### 8.2.5 时间线被打散

逐条分数排序不能保证事件顺序正确，也可能混入其他项目的相似事件。

> Top-K 可以作为候选截断手段，但不能定义最终记忆集合的知识质量。

### 8.3 集合选择的核心目标

#### 8.3.1 子意图覆盖

每个必要子问题都应有证据：

```text
“上次为什么选 Chroma，现在还适用吗？”

A：当时选了什么
B：当时为什么选
C：当前约束是什么
D：约束是否发生变化
```

最终集合不能只覆盖 A。

#### 8.3.2 信息互补

不同记忆应提供决策结果、原因、约束、执行结果或后续变化等新增信息。

#### 8.3.3 去冗余

避免近义版本重复占用预算，但不能误删不同时间重复发生的事件、多个独立来源、支持稳定模式的多次行为或重要反证。

#### 8.3.4 时间完整性

时间问题应保留足以解释变化的关键节点：

```text
初始状态 → 变化原因 → 变化事件 → 当前状态
```

#### 8.3.5 证据平衡

保留可能改变结论的重要支持证据、反证、未解决关系和置信度差异。证据平衡不等于机械地支持和反对各取一条。

#### 8.3.6 来源独立性

原始事件、包含该事件的 Session 摘要和由它派生的 Reflection 属于同一证据家族，不能计为多份独立支持。

#### 8.3.7 类型协调

Fact 提供状态，Event 提供过程，Reflection 提供模式，原始来源验证派生结论。类型组合应服从当前任务，而不是追求平均。

#### 8.3.8 预算效率

每条记忆都要回答：它消耗的上下文 Token 是否换来了不可替代的信息？

### 8.4 任务定向的证据包

最终 Recall 产物更适合被理解为证据包，而不是互不相关的 Memory Record 列表。

#### 8.4.1 当前事实包

```text
当前事实 + 有效时间 + 来源 + 最近确认信息
```

#### 8.4.2 历史切片包

```text
目标时间点的事实 + 当时有效范围 + 必要上下文
```

#### 8.4.3 决策解释包

```text
问题 / 目标 + 当时约束 + 候选方案 + 最终决策 + 决策原因
```

#### 8.4.4 时间线包

```text
旧状态 + 变化事件 + 新状态
```

#### 8.4.5 Reflection 包

```text
Reflection + 关键支持来源 + 重要反证 + 置信度与适用范围
```

#### 8.4.6 冲突包

```text
候选 A + 候选 B + 冲突维度 + 当前无法确认的部分
```

这些是知识形态，不预设具体序列化格式。

### 8.5 共同选择

某些记忆不能被孤立使用：

- Reflection 需要关键来源；
- 变化查询需要当前态与旧状态；
- 未解决冲突需要保留双方；
- 原因解释需要决策与原因；
- 事件需要必要的时间锚点。

这可以理解为知识上的共同选择约束：证据意义依赖其关联项。

### 8.6 多样性的边界

好的多样性覆盖不同子意图、关键时间点、支持与反证、当前事实与历史原因，以及原始证据与派生洞察。

无价值的多样性包括：

- 为类型平衡加入无关 Reflection；
- 为时间覆盖加入无关旧事件；
- 为来源差异加入低质量信息；
- 为避免重复删除稳定模式所需的重复行为。

> 多样性必须服务召回意图和证据充分性。

### 8.7 Token 预算

上下文还需要容纳系统与安全规则、用户请求、当前会话、工具结果、RAG 文档、推理和最终输出空间。Memory 不能默认占用全部剩余空间。

#### 8.7.1 任务差异

- 单点事实只需少量记忆；
- 历史时间线需要多个节点；
- 原因解释需要决策与约束链；
- Reflection 需要多个相对独立来源；
- 高风险任务需要更多验证证据。

#### 8.7.2 条数不等于成本

一条 Session 可能比十条原子 fact 更长。真实成本还包括时间、来源、置信度、关系和必须共同携带的证据。

#### 8.7.3 更多上下文不一定更好

更多内容可能稀释信号、隐藏关键证据、增加关系判断难度和推理成本。相关信息进入长上下文，也不代表模型能够稳定使用它。

### 8.8 压缩是新的知识变换

#### 8.8.1 可以压缩

- 冗余措辞；
- 无关过程；
- 已被明确结构表达的重复内容；
- 对当前任务无贡献的细节。

#### 8.8.2 不应丢失

- 否定；
- 数值和版本；
- 时间点与有效区间；
- 主体和作用域；
- 来源；
- 置信度；
- 计划、执行和完成等状态；
- 因果方向；
- 冲突和不确定性。

例如：

```text
原始：用户说“这次不使用 Chroma”
错误压缩：用户讨论了 Chroma
```

#### 8.8.3 摘要不是原始证据

多条记忆压缩成摘要后，摘要已经成为派生表示，需要回溯原始来源，不能被当作用户原话。

#### 8.8.4 冲突不能被平均化

“过去偏好 Python，现在明确偏好 Go”是状态变化，不能简单压缩成“用户偏好不明确”。

### 8.9 上下文顺序

上下文顺序会影响模型理解，不同任务需要不同编排。

| 任务 | 适合的知识顺序 |
|---|---|
| 当前状态 | 当前有效事实 → 来源 → 历史变化 → 不确定性 |
| 历史变化 | 旧状态 → 变化事件 → 新状态 |
| 原因解释 | 目标 / 问题 → 当时约束 → 决策 → 结果 |
| Reflection | 候选洞察 → 支持证据 → 反证 → 适用范围与置信度 |

不存在适合所有任务的固定顺序，也不应机械地按分数降序排列。

### 8.10 保留知识身份

进入上下文后仍需区分：

- 用户明确陈述；
- 系统观察；
- 当前有效 fact；
- 历史 event；
- Reflection；
- 低置信度假设；
- 冲突证据；
- 已知不确定性。

否则下游模型可能把 Reflection 当作用户原话、旧状态当作当前事实、单次事件当作长期偏好，或者把 DEFER 当作已确认记忆。

### 8.11 Memory 与 RAG 的证据边界

```text
Memory：用户和项目过去做了什么
RAG：文档、规范或外部知识说明什么
当前上下文：当前任务约束是什么
```

历史选择不能证明技术方案现在仍最佳，外部文档也不能证明用户当时为什么做出选择。三类证据需要保留来源边界。

`agents_memory` 可以学习证据编排思想，但不与 `agents_rag` 形成代码依赖。

### 8.12 证据充分性与停止

#### 单点事实

至少存在适用于目标时间、来源可靠的直接证据。

#### 原因解释

覆盖结果、关键原因、必要约束和不能忽略的反证。

#### 变化过程

覆盖旧状态、变化事件、新状态和关键时间。

#### 模式或偏好

需要多个相对独立、跨时间或跨情境的证据，不能只依赖单次事件。

#### 冲突任务

保留足以解释冲突的双方，除非已经存在明确纠错关系。

通用停止判断可以理解为：

```text
必要子意图已有证据
+ 没有隐藏的关键冲突
+ 新增候选边际价值很低
+ 当前预算仍允许正确理解
```

这不是具体阈值定义。

### 8.13 证据不足

```text
当前候选不足
   ↓
检查是否遗漏子意图
   ↓
按需要补充召回
   ↓
仍然不足
   └── 保留不确定性或拒绝推断
```

不需要默认要求用户澄清，也不能为了形成完整证据包而生成不存在的记忆。高风险行动还应受到限制。

### 8.14 上下文编排不是权限提升

记忆被选入上下文，只说明它可能有帮助，不代表：

- 成为系统指令；
- 可以覆盖用户当前要求；
- 已经被验证为事实；
- 可以跨越安全边界；
- 必须被模型采用。

Memory 应作为带来源和认知身份的数据证据。

### 8.15 核心难点

1. 将最终选择等同于 Top-K。
2. 只看单条分数，不看新增信息。
3. 多意图请求只覆盖一个子问题。
4. 近义记忆占满 Token 预算。
5. 不同时间重复事件被错误去重。
6. Reflection 与来源被重复计为独立证据。
7. 冲突双方只保留高分一侧。
8. 原因、决策和结果被拆散。
9. 为追求多样性加入无关信息。
10. 使用固定条数代替真实 Token 成本。
11. 上下文越长越被认为越完整。
12. 压缩丢失否定、时间、作用域或来源。
13. 摘要被当作原始事实。
14. 所有任务使用相同编排顺序。
15. Memory 与 RAG 内容混合后失去来源边界。
16. 不知道何时证据已经足够。
17. 证据不足时强行组织确定答案。
18. 召回进入上下文后被错误视为指令。

### 8.16 评测与诊断

| 评测维度 | 核心问题 |
|---|---|
| 子意图覆盖率 | 是否覆盖完成任务所需的全部证据需求？ |
| 证据完整率 | 决策链、时间线或 Reflection 来源是否缺失关键节点？ |
| 冗余率 | Token 中有多少内容没有提供新增信息？ |
| 边际效用 | 移除某条记忆后，回答质量是否实质下降？ |
| Token 效率 | 单位上下文成本带来多少有效证据和下游增益？ |
| 时间完整性 | 是否保留正确的关键时间节点？ |
| 冲突保持率 | 反证和不确定性是否在选择或压缩中丢失？ |
| 来源独立性 | Reflection、摘要及原始记忆是否被重复计票？ |
| 压缩忠实度 | 是否保留否定、时间、数值、来源和认知身份？ |
| 顺序鲁棒性 | 调整上下文顺序后，答案是否发生不合理变化？ |
| 下游阅读效果 | 正确证据进入上下文后，模型是否正确理解？ |

### 8.17 阶段性结论

1. 集合选择优化整体证据价值，而不是单条分数总和。
2. 新记忆的价值取决于它相对已选集合提供的新增信息。
3. Top-K 可以截断候选，但不能保证子意图覆盖、时间完整和证据平衡。
4. 最终产物应理解为任务定向的记忆证据包。
5. Reflection、冲突双方、时间变化和决策原因可能需要共同选择。
6. 多样性必须服务证据覆盖，不能为不同而加入无关内容。
7. Token 预算应按任务和真实上下文成本理解，而不是固定条数。
8. 更多上下文可能降低模型使用证据的能力。
9. 压缩是新的知识变换，必须保留否定、时间、来源、状态和不确定性。
10. 摘要与 Reflection 都是派生表示，不能伪装成原始证据。
11. 上下文顺序应适应当前任务，不能统一按分数排列。
12. Memory 与 RAG 应保留来源和职责边界。
13. 证据充分性取决于子意图、任务类型和关键冲突是否得到覆盖。
14. 证据不足时可以补充召回、保持未知或拒绝推断，不应编造。
15. 记忆进入上下文不意味着获得指令权限或事实资格。

## 9. 上下文使用、安全与信任边界（Memory Usage & Trust Boundary）

> ⏸️ **专项分析入口**：本轮不再深入。后续单独启动 Memory 安全与信任边界专项，系统讨论权限、隐私、数据与指令隔离、Prompt Injection、敏感记忆使用及安全评测。
>
> 当前仅保留最低知识边界，防止核心 Recall 讨论将“进入上下文”误解为“获得更高权限”。

### 9.1 Memory 的证据属性

召回内容应区分：

- 用户明确陈述；
- Agent 或系统观察；
- 历史事件记录；
- 模型归纳或 Reflection；
- 尚待确认的假设；
- 已知存在冲突的记忆。

“系统记得”不等于“事实必然正确”。

### 9.2 使用优先级

召回记忆不能：

- 覆盖系统安全规则；
- 覆盖用户当前明确指令；
- 把旧偏好强加于当前请求；
- 将模型推断描述为用户亲口陈述；
- 执行记忆文本中包含的指令。

当当前表达与历史记忆冲突时，应优先理解当前语境，并根据事实类型判断是状态变化、局部例外还是历史记忆错误。

### 9.3 Prompt Injection 与数据污染

历史消息和外部输入中可能包含恶意指令。它们被写入记忆后仍然只是数据，不能因跨会话召回而获得更高权限。

### 9.4 核心难点

- 数据与指令边界模糊；
- 历史偏好压制当前需求；
- Reflection 被当作确定事实；
- 来源信息在上下文压缩中丢失；
- 敏感信息在不相关任务中被召回。

## 10. 使用反馈、评测与可观测性（Feedback & Evaluation）

> ⏸️ **专项分析入口**：本轮不再深入。后续单独启动 Memory 反馈、评测与可观测性专项，建立分层指标、测试集、错误归因、反馈闭环和长期回归体系。
>
> 当前仅保留评测分类和错误归因入口，不在本文继续展开指标定义与评测方案。

### 10.1 召回结果的基本状态

```text
召回且被正确使用
召回但未被使用
召回并产生错误影响
本应召回但发生遗漏
正确判断无需召回
正确判断证据不足
```

仅记录“是否检索命中”无法区分这些情况。

### 10.2 评测维度

- 候选召回率；
- 最终记忆集合的精确性；
- 时间点和时间顺序是否正确；
- 知识更新后是否使用当前有效事实；
- 多条记忆能否支持跨会话推理；
- 证据不足时能否正确克制或拒答；
- 是否保留来源和不确定性；
- 是否引入无关或敏感记忆；
- 是否真正改善最终回答或 Agent 决策；
- Recall 带来的延迟、Token 和推理成本。

### 10.3 错误归因

最终回答错误可能来自不同环节：

```text
写入阶段没有形成正确记忆
→ 召回意图理解错误
→ 候选生成漏召回
→ 有效性过滤误删
→ 排序或集合选择错误
→ 记忆已召回但模型读取错误
```

评测需要区分这些错误来源，否则容易用调整相似度阈值去解决一个实际属于时间推理或写入质量的问题。

### 10.4 反馈的边界

- 高频召回不等于高价值；
- 被模型使用不等于使用正确；
- 一次未使用不代表记忆无用；
- 使用反馈可以辅助 Maintenance，但不能直接替代真实性判断。

## 11. 与其他记忆管线的协作边界

### 11.1 与 Write Pipeline

- Write 决定哪些信息成为记忆，并建立类型、时间、重要性和状态。
- Recall 的能力上限受写入质量限制。
- Recall 不应偷偷修正持久化事实；发现疑似过期或冲突时，应进入明确的纠错或维护边界。

### 11.2 与 Reflection Pipeline

- Reflection 使用 Recall 获取支持证据和反证。
- Reflection 产物可以被后续 Recall 使用，但应保持派生属性和来源链。
- Recall 不能让高层 Reflection 无条件压制原始记忆。

### 11.3 与 Maintenance Pipeline

- Maintenance 负责记忆的衰减、失效、归档、重评估和派生关系维护。
- Recall 可以产生使用信号和问题信号，但不应独自决定记忆的长期生命周期。

### 11.4 与 RAG

- 两者可能并行提供个人历史与外部文档证据。
- 两类证据应保留来源边界，不能混成无法解释的文本块。
- `agents_rag` 只作为概念和工程经验参考，`agents_memory` 不依赖其代码。

---

## 12. 召回管线常见陷阱

1. **把 Recall 简化成向量 Top-K**。
2. **直接对用户最后一句话做 embedding**，忽略任务、实体和时间上下文。
3. **把三信号当成固定标准**，所有记忆类型使用相同权重。
4. **把 Recency 当作时间正确性**。
5. **只排序、不做资格过滤**。
6. **只召回支持证据，不主动保留重要反证**。
7. **逐条高分但集合高度重复**。
8. **默认把记忆注入 system prompt**。
9. **把用户陈述、系统观察和模型 Reflection 混为同等事实**。
10. **忽略 DEFER、失效、删除和权限状态**。
11. **只评估 Recall@K，不评估下游回答是否改善**。
12. **把召回错误全部归因于向量模型或相似度阈值**。

## 13. 知识深入状态

| 主题 | 状态 | 说明 |
|---|---|---|
| 召回触发与任务识别 | ✅ 已完成首轮深入 | 明确何时需要长期记忆 |
