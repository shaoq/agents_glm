## 0. 文档定位

本文把记忆召回知识笔记中的核心认知转化为 `agents_memory` 首期 Recall 工程方案，回答：

- Recall 的系统边界、输入、输出和成功标准是什么；
- 知识笔记中的七个核心环节如何映射为工程组件；
- 多层作用域和多路径候选如何在不越权的前提下协作；
- 资格过滤、单条效用、证据解析和集合选择如何分工；
- SQLite、Chroma、Embedding 和 LLM 分别失败时如何处理；
- 如何在不影响现有 Write Pipeline 的前提下接入 Service 和 CLI；
- 首期按什么顺序实施、如何验收、做到哪里停止。

本文是实施设计，不是 OpenSpec change，也不授权直接修改应用代码。设计确认后应单独创建 OpenSpec 提案，再进入实施阶段。

`agents_memory` 是独立子项目。`agents_rag` 以及同级其他子项目只可作为工程组织思路参考，禁止导入其代码、读取其配置、复用其数据库或连接其运行时对象。

## 1. 已确认的关键决策

### 1.1 Recall 入口

首期采用显式调用：

```text
Agent / Application
        │ 决定何时需要记忆
        ▼
MemoryService.recall(...)
        ▼
MemoryRecallPipeline
```

调用方决定“何时召回”，Recall 内部负责从当前查询和有限消息上下文构建意图。首期不实现每轮对话的自动召回触发器。

### 1.2 Recall 输出

输出结构化 `RecallResult`，同时提供：

- 经解析和选择的结构化证据；
- 证据的来源、作用域、时间和冲突状态；
- 选择理由、执行状态和降级信息；
- 可直接注入模型的上下文文本。

不采用“只返回文本”或“只返回 MemoryRecord Top-K”的形式。

### 1.3 作用域策略

在同一用户边界内执行三层召回：

1. 当前会话；
2. 当前 Agent 的历史会话；
3. 用户级共享记忆。

候选生成按层分路，结果保留来源标签。任何路径都禁止跨 `user_id`。

当前持久化模型没有独立的 Agent 间可见性字段。首期将同一用户下的数据视为用户边界内可召回数据，同时允许调用方关闭较宽通道。更细粒度的私有、共享模型留待后续专项。

### 1.4 交付入口

首期同时提供：

- Python `MemoryService.recall(...)`；
- CLI `recall` 命令。

CLI 只负责参数适配和结果展示，不复制 Recall 逻辑。首期不提供 HTTP API。

### 1.5 总体路线

采用分阶段混合管线：

- LLM 负责语义理解、有限的任务贡献判断和复杂关系判断；
- 确定性代码负责用户边界、授权、有效性、时间硬约束、预算和状态；
- SQLite 是唯一真相源；
- Chroma 是派生语义索引，只生成候选；
- LLM 局部失败时走明确的确定性降级路径；
- 各阶段传递结构化对象并保留诊断依据。

## 2. 目标、职责与非职责

### 2.1 核心目标

实现一条可独立运行、可解释、可降级、可测试的 Recall 主线：

```text
RecallRequest
  → 召回意图构建
  → 分层、多路径候选生成
  → 资格与有效性过滤
  → 单条记忆效用评分
  → 时间、冲突与关系证据解析
  → 证据集合选择
  → 上下文组装
  → RecallResult
```

首期需要证明 Recall 不只是向量 Top-K，而是能够返回对当前任务真正有用、边界合法、时间语义明确且不掩盖冲突的一组证据。

### 2.2 Recall 负责

- 从当前查询和有限近期消息构建召回意图；
- 在合法作用域内执行多通道、多路径候选生成；
- 排除越权、失效、损坏或违反显式限制的记录；
- 综合语义、任务、时间、作用域、可信度等信号评价单条效用；
- 识别当前状态、历史状态、自然演化、明确修正和未解决冲突；
- 在数量及 Token 预算内选择互补证据集合；
- 生成结构化证据和忠实的 Prompt 上下文；
- 报告执行状态、充分性和降级原因。

### 2.3 Recall 不负责

- 判断每轮对话是否需要召回；
- 生成最终业务回答；
- 修改、合并、纠正或删除持久化记忆；
- 自动记录访问次数、热度或“本次被使用”；
- 创建 Write Pipeline 的 Deferred/Pending 项；
- 主动要求用户澄清；
- 调度 Reflection；
- 承担完整安全治理或完整评测体系；
- 依赖其他子项目的代码、配置和存储。

Recall 首期保持严格只读。将来如需记录使用反馈，应通过独立接口异步完成，不污染主召回语义。

### 2.4 成功标准

- 不跨越 `user_id` 边界；
- 能区分当前会话、Agent 历史和用户级来源；
- Chroma 陈旧数据不能绕过 SQLite 有效性；
- 返回经时序和冲突处理的证据集合，而非相似文本列表；
- 输出既能被程序消费，也能用于 Prompt 注入和诊断；
- LLM 局部失败时核心边界仍然成立；
- 在相同存储快照和确定性配置下，核心行为可稳定复现；
- 现有 Write Pipeline 及维护命令不发生行为回归。

## 3. 总体架构

### 3.1 七阶段主链路

```text
RecallRequest
    │
    ▼
1. RecallIntentBuilder
   理解当前真正需要什么记忆
    │
    ▼
2. MultiLaneCandidateRetriever
   会话 / Agent 历史 / 用户级，多查询、多路径召回
    │
    ▼
3. EligibilityFilter
   用户隔离、作用域授权、有效性和硬时间边界
    │
    ▼
4. UtilityScorer
   评估相关性、任务贡献、时效、可信度和作用域
    │
    ▼
5. EvidenceResolver
   处理时间、修正链、事件身份、冲突和关联证据
    │
    ▼
6. SetSelector
   在预算内选择互补、低冗余、关系完整的证据集合
    │
    ▼
7. ContextAssembler
   生成结构化证据包和可注入模型的上下文
    │
    ▼
RecallResult
```

### 3.2 编排原则

`MemoryRecallPipeline` 只负责：

- 串联阶段；
- 传递结构化中间对象；
- 收集阶段统计、耗时和降级信息；
- 统一处理领域错误；
- 执行最终状态复核；
- 保证最终数量和 Token 预算。

它不直接实现向量检索、评分公式、冲突规则或文本格式。阶段内部可继续拆分策略组件，不要求“一阶段等于一个大类”。

### 3.3 存储边界

```text
Chroma
  └─ 生成语义候选 ID，不决定最终资格

SQLite
  └─ 加载完整记录并确认当前真实状态
```

Chroma 中的记录必须回查 SQLite 后才能进入资格过滤。SQLite 不可用时不能直接返回 Chroma 文档。

Recall 不复用写入专用 `ContextLookup`：

- Write Lookup 寻找可能相同、补充或矛盾的已有记忆；
- Recall Retrieval 寻找对当前任务有用的一组证据。

两者只共享 Embedder、Repository、MemoryIndex 等基础抽象。

## 4. 领域模型与阶段契约

### 4.1 `RecallRequest`

外部请求描述调用现场：

- `user_id`：必填的安全边界；
- `agent_id`、`session_id`：当前上下文；
- 当前查询；
- 可选的有限近期消息；
- 可选任务目的；
- 可选显式时间、类型和作用域限制；
- 最大证据数、上下文 Token 预算；
- 是否返回详细诊断。

约束：

- 身份字段不得由 LLM 推断；
- 调用方可以缩小范围，不能越过系统上限扩大范围；
- 近期消息必须有硬上限；
- 请求预算受系统硬上限约束。

### 4.2 `RecallIntent`

表达“需要什么”，建议包含：

- `primary_query`；
- `purpose`；
- 少量 `query_variants`；
- `target_memory_types`；
- `temporal_need`；
- `subject_hints`；
- `relationship_need`；
- `explicit_constraints`；
- 意图置信度和不确定项。

显式约束和模型推断必须分开。后续阶段可以放宽模型推断，不能违背用户显式限制。

### 4.3 `RecallPlan`

表达“从哪些合法通道寻找”，包含：

- 检索通道；
- 各通道的 Scope、查询变体和类型；
- 各路径候选额度；
- 语义、时间和关系扩展策略；
- 全局候选上限和执行预算。

权限与配额由确定性 Planner 生成，不由 LLM 决定。

### 4.4 候选模型

`RetrievedCandidate` 保留：

- `memory_id`；
- 命中通道、查询变体和检索路径；
- 原始相似度或匹配信号；
- 多路命中及合并信息。

同一记忆按 ID 合并，但保留全部命中依据。

`EligibleCandidate` 在 SQLite 回查和硬过滤后形成，包含真实 `MemoryRecord`、已验证作用域、检索信号和资格依据。

`ScoredCandidate` 增加：

- 各评分分量；
- 综合效用；
- 评分置信度；
- 是否发生 LLM 降级；
- 暂定证据角色。

临时召回字段不得写回 `MemoryRecord`。

### 4.5 `EvidenceGroup`

证据解析阶段以组为单位：

```text
EvidenceGroup
  ├─ primary
  ├─ supporting
  ├─ historical
  ├─ conflicting
  ├─ relations
  └─ resolution
```

查询期角色至少包含：

- `CURRENT`
- `HISTORICAL`
- `EVOLVED`
- `CORRECTED`
- `SUPERSEDED`
- `SUPPORTING`
- `CONFLICTING`
- `INDEPENDENT`
- `UNKNOWN_EVENT_IDENTITY`

这些角色不取代存储层的 `Validity` 和 `RelationKind`。

### 4.6 `RecallResult`

```text
RecallResult
  ├─ context
  ├─ evidence
  └─ metadata
```

`evidence` 始终是权威结构化输出。`context` 是它的便捷表示。`metadata` 至少记录：

- 意图摘要；
- 使用的通道；
- 候选、过滤和最终数量；
- 充分性；
- 执行状态；
- 降级和预算截断；
- 管线版本及可选阶段耗时。

正常模式不返回完整淘汰过程；诊断模式才返回拒绝原因和详细评分。

## 5. 意图构建与检索计划

### 5.1 意图构建输入

只使用：

- 当前查询；
- 有限近期消息；
- 调用方显式任务目的和约束。

不把历史召回结果再次作为意图输入，避免旧记忆形成自我强化循环。

### 5.2 LLM 与规则分工

LLM 可以：

- 概括信息需求；
- 判断任务目的；
- 生成少量互补查询；
- 推断事实或事件偏好；
- 识别当前、历史、区间和演化需求；
- 提取主题及关系线索。

LLM 不可以：

- 修改身份和 Scope；
- 决定访问授权；
- 放宽显式限制；
- 直接选择最终记忆；
- 把推断伪装成用户约束。

LLM 输出必须经过 Schema 校验和确定性规范化。

### 5.3 查询变体

首期最多保留三类：

1. 原始查询；
2. 去除对话性措辞后的语义核心查询；
3. 仅在必要时生成的时间或关系补充查询。

每个变体带生成目的。避免同义改写堆积、否定词丢失、时间约束丢失以及凭常识虚构实体。

### 5.4 降级意图

LLM 超时或输出非法时：

- 只使用原始查询；
- 保留显式时间和类型约束；
- 未指定类型时检索 fact 和 event；
- 不推断实体、关系和隐含时间；
- 目的标记为通用信息恢复；
- 记录 `intent_fallback`。

降级意图宁可扩大合法候选范围，也不能错误缩小检索范围。

### 5.5 三层通道

| 通道 | 范围 | 价值 |
|------|------|------|
| `session_current` | 当前 user + agent + session | 当前任务连续性 |
| `agent_history` | 当前 user + agent，跨历史 session | Agent 长期互动 |
| `user_shared` | 当前 user 下允许的更宽记忆 | 用户级长期信息 |

规则：

- 三个通道分别配置候选额度；
- 当前会话候选不能被海量历史记录淹没；
- 最终集合不强制平均覆盖各通道；
- 调用方可以关闭较宽通道；
- 所有通道始终绑定同一 `user_id`。

## 6. 多路径候选生成

### 6.1 语义路径

- Chroma 按通道和查询变体生成候选；
- fact 和 event 可以分别分配额度；
- 保留原始距离或相似度；
- 相似度阈值只排除明显无关项，不决定最终价值。

### 6.2 结构化时间路径

当意图涉及当前状态、指定时点、区间或演化时，从 SQLite 补充满足真实时间字段的有限候选。

该路径用于支持：

- 最近一次；
- 指定日期之前或之后；
- 某一时刻的状态；
- 状态如何变化。

不得依赖内容字符串中的日期代替结构化时间。

### 6.3 关系扩展

对高质量种子候选进行有限一跳扩展：

- 修正它的记录；
- 被它修正的历史记录；
- 取代链前后节点；
- 明确关联事件。

扩展后仍要重新验证用户和作用域。关系记录只是候选，不保证进入最终集合。

### 6.4 分路配额与合并

```text
各通道、各路径独立取有限候选
        ↓
按 memory_id 合并
        ↓
保留全部命中信号
        ↓
达到全局上限时执行轻量预排序
```

轻量预排序只能使用便宜且稳定的信号，如最佳语义相似度、多路命中、作用域接近度、明确时间匹配和记忆置信度。它只控制进入昂贵阶段的数量。

### 6.5 SQLite 回查

向量候选必须批量回查：

- SQLite 不存在：丢弃并记录陈旧索引；
- 普通当前查询中已失效：丢弃；
- 历史模式中 `SUPERSEDED`：按目标时点进一步判断；
- 越权：立即丢弃；
- 合法：进入资格过滤。

`RETRACTED` 默认不作为事实证据。未来若需要审计型查询，应单独设计。

### 6.6 未同步覆盖集

为处理 SQLite 已写入、Chroma 未同步：

- 从 SQLite 获取当前作用域内有限的待索引或失败记录；
- Embedding 可用时临时计算相似度；
- Embedding 不可用时仅使用结构化条件；
- 只参与本次 Recall；
- Recall 不修改索引同步状态。

## 7. 资格过滤

### 7.1 顺序

```text
记录完整性
  → 用户边界
  → 作用域授权
  → 有效性
  → 显式类型
  → 硬时间约束
  → 可消费性
```

命中硬拒绝后停止处理。拒绝原因使用稳定枚举。

### 7.2 硬拒绝

- `user_id` 不一致；
- 请求未授权该作用域；
- 当前查询下状态不可用；
- 违反用户显式类型或时间限制；
- SQLite 记录不存在；
- 内容为空或关键字段损坏；
- 状态组合违反领域约束。

关系扩展得到的记录也必须执行完整过滤。

### 7.3 仅作为软信号

以下不能直接过滤：

- 相似度不够高；
- 来自历史会话；
- 重要性较低；
- 记录较旧；
- 来源为模型推断；
- 只被一条路径命中；
- 与其他候选相似。

时间年龄必须结合召回意图解释，不能统一衰减。

### 7.4 时间资格与时间效用

- 硬时间资格：是否满足用户明确时间范围；
- 时间效用：满足资格后，是否是当前任务最合适的时间版本。

两者分开，避免把历史查询需要的旧证据提前过滤掉。

## 8. 单条记忆效用评分

### 8.1 评分分量

- 语义相关性；
- 对当前任务的贡献度；
- 时间适配度；
- 作用域接近度；
- 来源和记忆可信度；
- 有上限的重要性；
- 多查询、多路径命中的稳健性；
- 评分依据完整度。

`importance` 表示长期保留价值，不等于当前召回价值，必须限制其贡献。

### 8.2 两级评分

第一级对全部合格候选执行确定性基础评分，使用向量、时间、Scope、置信度、重要性和命中路径。

第二级只对前部有限候选执行一次 LLM 批量复核，补充：

- 是否真正有助于当前任务；
- 是直接证据、背景还是仅主题相似；
- 是否可能误解了查询对象；
- 候选的暂定证据角色。

LLM 不能恢复已被硬过滤的候选，也不直接决定最终集合。

### 8.3 综合分

概念模型：

```text
utility =
  semantic_relevance
  + task_contribution
  + temporal_fit
  + scope_proximity
  + trust
  + hit_robustness
  + bounded_importance
```

约束：

- 分量归一到统一范围；
- 单个软信号不能垄断；
- LLM 分量缺失时重新归一；
- 保留各分量和评分模式；
- 候选间重复不在本阶段惩罚。

LLM 失败时保留确定性评分并标记 `scoring_fallback`。

## 9. 时间、冲突与关系证据解析

### 9.1 解析优先级

```text
显式持久化关系
  → 明确有效时间和事件时间
  → 结构化 EventFrame 锚点
  → 有限语义关系判断
  → 未解决冲突或相互独立
```

低层推断不能覆盖高层关系。

### 9.2 时间语义

区分：

- 事件时间；
- 事实有效时间；
- 记录写入时间。

`created_at` 只能作为弱排序依据，不能默认代替事件发生时间。

当前状态查询优先有效链头；指定时点查询选择覆盖目标时点的状态；演化查询保留关键变化节点。

### 9.3 显式关系

`SUPERSEDES` 表示旧状态曾经可能正确，后来被取代；`CORRECTS` 表示旧内容错误，后来被纠正。

因此：

- 被取代记录可以成为历史证据；
- 被纠正记录只能作为“曾记录但已纠正”的审计背景；
- 关系链需要检测缺失节点、自环和循环；
- 扩展必须受一跳深度和数量限制。

### 9.4 同一事件判断

先比较：

- 事件类型；
- 参与者或主体；
- 时间锚点及容差；
- 地点；
- 关键对象；
- 已有事件标识或关系。

明显不同时间、地点、参与者或事件次数通常表示不同事件。

锚点不足时分类为 `UNKNOWN_EVENT_IDENTITY`：

- 不强行合并；
- 不建立确定矛盾；
- 暂时作为独立证据；
- 必要时在结果中保留身份不确定性。

### 9.5 事实冲突

只有“同一主体 + 同一属性或关系 + 时间范围相交”的互斥陈述才可能构成事实冲突。

自然状态变化应归为 `EVOLVED`，不能归为 `CONFLICTING`。

首期不要求把全部事实永久转换为知识图谱三元组；只对经过类型、主题、时间和语义预分桶后的少量高价值候选对进行判断。

### 9.6 未解决冲突

高任务相关性的未解决冲突：

- 双方组成同一证据组；
- 明确标记 `CONFLICTING`；
- 使用中性措辞；
- 不替用户选择一边。

低相关冲突可以整组不进入最终上下文，但不能只保留得分更高的一方。

### 9.7 `unknown + contradictory`

当事件身份未知但内容可能矛盾：

- 保留为两个独立候选组；
- 记录潜在冲突线索；
- 同时使用时提示事件身份未确认；
- 不创建 Write Pipeline 的 `DEFER`；
- 不向用户发起澄清；
- 不写回存储。

Recall 只需避免本次查询过度结论。长期未决关系由未来 Reflection 或新证据处理。

### 9.8 解析降级

LLM 不可用时仍处理显式关系、明确时间和结构化锚点。必须依赖语义才能判断的候选默认保持独立，标记 `resolution_fallback`，不武断合并或裁决。

## 10. 集合选择

### 10.1 选择单位

基本单位是 `EvidenceGroup`，不是单条记录。原因：

- 冲突双方必须共同出现；
- 修正链需要必要上下文；
- 演化查询需要关键历史节点；
- 主证据可能依赖关联事件。

每组计算整体效用、需求覆盖、Token 成本、必要成员和与其他组的冗余。

### 10.2 边际价值

```text
marginal_value(group | selected) =
    group_utility
  + uncovered_need_coverage
  + complementary_evidence
  + necessary_context
  - redundancy
  - token_cost
  - unresolved_risk
```

首期采用可解释的贪心选择：

1. 锁定直接证据；
2. 补齐修正链、冲突对方等必要关系；
3. 覆盖尚未满足的子需求；
4. 按边际价值加入互补证据。

### 10.3 作用域平衡

候选生成阶段对不同 Scope 提供保底额度，最终结果不强制按通道平均分配。低价值记忆不能仅为“通道多样性”进入结果。

### 10.4 冲突组原子性

高相关冲突组不可拆分。预算不足时：

1. 先压缩其他支持信息；
2. 再精简双方的格式；
3. 仍不能容纳时整组不选。

禁止只选择冲突的一方。

### 10.5 历史链压缩

优先保留：

- 目标时点附近的状态；
- 当前状态；
- 实质变化节点；
- 明确修正或关键决策。

省略内容无实质变化的重复节点和对目标区间无影响的中间节点。

### 10.6 预算

- `max_evidence_items` 控制结构化证据规模；
- `max_context_tokens` 控制注入文本；
- 系统配置提供硬上限。

收缩顺序：

1. 重复及低边际价值支持证据；
2. 非必要历史节点；
3. 说明性元数据；
4. 更紧凑的字段格式；
5. 忠实片段；
6. 减少完整证据组。

不得改变否定、时间和结论含义，不得隐藏冲突或不确定性。首期不把生成式摘要作为必要依赖。

## 11. 上下文组装与结果状态

### 11.1 稳定格式

建议按实际内容输出以下分区：

```text
[当前相关记忆]
[相关历史与变化]
[支持信息]
[未解决的冲突或不确定性]
```

每项保留：

- 记忆内容；
- 当前、历史、修正或冲突角色；
- 有意义的时间；
- 来源或作用域；
- 可追溯的证据 ID。

内部总分和向量距离不注入业务 Prompt。

### 11.2 忠实性

- 记忆内容与系统说明明确分离；
- 不把证据改写为系统自己的结论；
- 推测关系不得表达成确认事实；
- 不省略改变语义的时间限制；
- 冲突双方使用对称措辞；
- 每个上下文条目都能映射到结构化证据。

### 11.3 充分性与执行状态

充分性：

- `SUFFICIENT`
- `PARTIAL`
- `CONFLICTED`
- `EMPTY`

执行状态：

- `COMPLETE`
- `DEGRADED`

示例：

- `EMPTY + COMPLETE`：成功确认没有合格证据；
- `EMPTY + DEGRADED`：部分能力失败，未找到但不能断言不存在；
- `SUFFICIENT + DEGRADED`：已有直接证据，但非关键增强阶段失败；
- `CONFLICTED + COMPLETE`：完整执行后发现关键冲突。

不可恢复错误不伪装成正常 `RecallResult`。

### 11.4 空结果

```text
context = ""
evidence = []
sufficiency = EMPTY
execution_status = COMPLETE
```

空结果是正常业务结果，不自动触发写入、Reflection、澄清或扩大用户范围。

## 12. 错误、降级与一致性

### 12.1 请求错误

缺少用户、查询为空、时间范围非法、预算非法或 Scope 模式非法时，在进入管线前拒绝。

### 12.2 不可恢复错误

- SQLite 不可用；
- 无法验证用户和作用域；
- 核心记录无法加载；
- 阶段契约损坏；
- 最终输出无法通过 Schema 校验。

SQLite 是真相源。它不可用时不能使用 Chroma 文档替代。

### 12.3 降级矩阵

| 故障点 | 降级行为 | 标记 |
|--------|----------|------|
| Intent LLM | 原始查询通用意图 | `intent_fallback` |
| 查询改写 | 只用原始查询 | `query_rewrite_fallback` |
| Embedding | 跳过语义路径 | `semantic_unavailable` |
| Chroma | SQLite 有界候选 | `vector_index_unavailable` |
| 某通道 | 保留其他通道 | `partial_lane_failure` |
| LLM 评分 | 确定性评分 | `scoring_fallback` |
| LLM 关系判断 | 显式关系和时间规则 | `resolution_fallback` |
| Tokenizer | 保守字符估算 | `token_estimation_fallback` |
| 关系断链 | 保留合法节点 | `incomplete_relation_chain` |

### 12.4 Chroma 故障回退

SQLite 回退必须：

- 绑定用户和合法作用域；
- 使用类型、有效性和时间条件；
- 按更新时间、重要性或置信度取有限候选；
- 设置每通道和全局上限；
- 禁止无界全表扫描。

高度依赖语义但语义路径不可用时，结果通常为 `PARTIAL` 或 `DEGRADED`。

### 12.5 部分通道失败

保留其他通道已验证的结果，但：

- 记录失败通道；
- 不把通道故障误报为没有数据；
- 如果失败通道是显式需求，不能报告完全充分。

### 12.6 全局截止时间

- 各阶段共享全局截止时间；
- 外部调用只允许有限重试；
- 已完成的合法结果可以保留；
- SQLite 资格检查不能跳过；
- 超时不能让未验证候选进入结果。

### 12.7 逻辑快照与最终复核

不在整个 Recall 期间持有 SQLite 长事务：

1. 候选生成后批量加载为不可变执行快照；
2. 完成评分、解析和选择；
3. 输出前复核最终记录的存在、Validity、关键时间和关系；
4. 发生漂移时移除受影响证据组并最多重选一次；
5. 第二次仍持续变化时返回并发修改错误。

记录初次加载、最终复核、状态漂移和重选信息。

### 12.8 数据与关系异常

单条记录损坏时跳过并报告数据质量问题。以下情况提高为严重错误：

- 大量候选均损坏；
- 用户或 Scope 字段缺失；
- 关系指向其他用户；
- 主要证据依赖损坏节点；
- Schema 与代码不兼容。

关系遍历维护 visited 集合并设置深度、数量上限。


### 13.2 模块职责

- `recall/models.py`：Recall 专属阶段契约和枚举；
- `recall/intent.py`：LLM 意图构建、校验、规范化和降级；
- `recall/planning.py`：权限收敛、通道和预算规划；
- `recall/retrieval.py`：语义、时间、关系和未同步候选；
- `recall/filtering.py`：确定性资格过滤；
- `recall/scoring.py`：基础评分、LLM 复核和分量组合；
- `recall/evidence.py`：时间、事件身份、关系和冲突分组；
- `recall/selection.py`：集合边际价值、预算和充分性；
- `recall/assembly.py`：结构化结果和文本渲染；
- `pipeline/recall.py`：阶段编排、统计、错误和最终复核。

使用 `evidence.py` 避免和现有面向写入的 `resolution/` 包产生职责混淆。

### 13.3 复用边界

直接复用：

- 通用 Memory 模型；
- Embedder 协议和 OpenAI 兼容实现；
- SQLite Repository 基础设施；
- Chroma 客户端和集合；
- 配置加载、Typer 和 Rich；
- 当前 GLM-4.7-Flash 客户端构建方式。

不复用：

- `ContextLookup`；
- `CandidateProcessor`；
- Write `DecisionEngine`；
- Write `RelationResolver` Prompt；
- `StorageCoordinator` 写事务；
- Deferred/Pending 流程。

### 13.4 Repository 增量能力

以只读加法方式增加：

- ID 批量加载；
- user/agent/session/type 组合的有限查询；
- 时间范围查询；
- 历史版本查询；
- 关系批量读取；
- 未同步记录有限查询；
- 最终状态及更新时间复核。

所有查询强制 `user_id` 并接受数量上限。Recall 不自行拼 SQL，也不在读取方法中顺便修复索引。

### 13.5 向量查询接口

保留现有写入接口语义，新增 Recall 专用查询契约：

```text
query(...)                 # Write 继续使用
query_candidates(...)      # Recall 使用
```

新契约表达：

- 必填 `user_id`；
- 可选 agent/session 限制；
- 一个或多个类型；
- 查询向量；
- 候选上限；
- 允许的有效性范围。

Chroma `where` 细节封装在存储适配器中。

### 13.6 Service

增加：

```text
MemoryService.recall(request: RecallRequest) -> RecallResult
```

Recall Pipeline 通过构造函数注入。Service 不自行创建 LLM、Embedder 或 Repository。Recall 未配置时，只在调用 `recall()` 时报告明确错误，不影响其他维护命令。

### 13.7 CLI

新增 `recall` 命令，覆盖：

- 查询及 user/agent/session；
- 是否包含 Agent 历史；
- 是否包含用户级共享；
- 时间范围和记忆类型；
- 最大证据数和 Token；
- `--diagnostic`；
- 可选 JSON 输出。

CLI 和 Python API 使用同一 Runtime。

### 13.8 配置

在现有 `Settings` 增加 Recall 配置：

- 意图模型及超时；
- 通道候选额度；
- 查询变体上限；
- 向量阈值和全局候选上限；
- SQLite 回退和未同步覆盖上限；
- LLM 复核候选上限；
- 评分权重；
- 关系扩展深度和数量；
- 证据和 Token 硬上限；
- 全局 Recall 超时；
- 诊断开关。

默认模型沿用 GLM-4.7-Flash，Embedding 沿用 `agents_memory` 自己的配置。增加 `validate_recall()`，只在构建 Recall Runtime 时校验。

## 16. 端到端验收场景

1. 当前会话存在明确事实，返回直接证据和 `SUFFICIENT`；
2. 从当前 Agent 历史会话恢复此前决定；
3. 从同一用户更宽范围恢复长期偏好并保留来源；
4. 当前状态查询选择有效链头；
5. 指定时点查询返回当时有效状态；
6. 演化查询返回关键变化而非伪冲突；
7. 明确修正以修正记录为主；
8. 未解决关键冲突双方共同返回；
9. 事件身份未知时不强行合并；
10. Chroma 滞留的失效记录被 SQLite 排除；
11. 未索引 ACTIVE 记录通过有限覆盖集参与；
12. LLM 全部不可用时完成确定性降级召回；
13. 部分通道失败时返回合法部分结果并标记降级；
14. 其他用户的高相似记录和关系邻居均不进入结果；
15. 大量重复候选下选择互补集合且不超预算；
16. 并发状态变化触发最终复核和一次重选；
17. 无合法证据时返回 `EMPTY + COMPLETE`。

## 17. 首期明确不做

- 自动召回触发；
- HTTP API；
- Recall 后自动更新访问状态；
- 自动写入、纠正、合并和删除；
- 自动创建 Deferred/Pending；
- 主动要求用户澄清；
- Reflection 自动调度；
- 多轮自主检索循环；
- 无限制图遍历；
- 生成式长文本压缩；
- 在线学习排序；
- Agent 间细粒度私有可见性；
- 完整安全治理专项；
- 完整离线、在线评测专项；
- 任何跨子项目运行时代码、配置或存储复用。

## 18. 主要风险与控制

### 18.1 Repository 影响面

Repository 被 Write、Service、同步和测试广泛使用。只新增只读方法，不修改现有语义；实施前执行 GitNexus 影响分析，实施后执行变更检测。

### 18.2 Chroma Scope 能力

现有接口偏精确 Scope。新增 Recall 查询契约，不破坏 Write 查询。

### 18.3 LLM 延迟

首期限定：

- 一次意图构建；
- 一次有限批量评分；
- 必要时一次有限关系判断；
- 其余阶段确定性执行；
- 全部调用受全局截止时间约束。

### 18.4 候选对爆炸

先按类型、主体、时间和语义邻近分桶，只比较有限高价值候选；关系扩展一跳。

### 18.5 用户内跨 Agent 共享

首期显式接受用户边界内共享，并允许关闭 `user_shared`。未来如需私有性，应增加持久化可见性模型，不能只调整评分。

## 19. 完成定义

首期 Recall 同时满足以下条件才算完成：

- 七阶段主链路全部交付；
- Python Service 和 CLI 均可调用；
- 端到端验收场景有自动化覆盖；
- LLM、Embedding、Chroma 降级行为可验证；
- SQLite 用户隔离和最终状态复核可验证；
- Write Pipeline 全量回归通过；
- 架构测试确认子项目间无代码、配置和存储依赖；
- 文档、配置示例和 CLI 帮助与实现一致；
- 修改现有符号前完成 GitNexus impact；
- 提交前运行 `gitnexus_detect_changes()` 并确认影响符合预期。
